# The Admin Panel never connects to Discord's gateway; event-driven features belong to ShorBot

The Admin Panel only calls Discord's REST API. Any feature that must react to Discord events, such as automatic sanctions, message logs or reaction roles, is built in ShorBot, the Bot (`GLOSSARY.md`), behind an HTTP API designed before either side writes code for it. Shor keeps a single bot connected to the gateway. Decided by Gilles on 2026-10-23, when loanspac developed ShorBot; Gilles took ShorBot over on 2026-10-28.

The panel's own Discord application (ADR 0002) does put a bot user on the Discord server, but that user never connects to the gateway: it only makes REST calls, when a staff member uses the panel. The docs call it the panel's application, never a bot. Clarified by Gilles on 2026-10-23, while grilling #7.

The panel's application may also answer interactions, which Discord sends over HTTP to the Interactions Endpoint URL set in the Developer Portal. Discord wants "an initial response within 3 seconds", and "Interaction tokens are valid for 15 minutes" for the rest (https://docs.discord.com/developers/interactions/receiving-and-responding, read 2026-10-27). That opens no gateway connection, so ShorBot stays the one bot on it, and the two ways "are mutually exclusive" for an application (same page). Anything else Discord does still reaches only the gateway, since its webhook events carry no event of a Discord server, such as a member joining or a message sent (https://docs.discord.com/developers/events/webhook-events, read 2026-10-27). Decided by Gilles on 2026-10-27, while grilling the features that follow the MVP.

Which of the two answers an interaction follows who acts. What the staff do goes through the panel: its pages, and the staff's slash commands that do what a page of the panel does, once #150 settles them. What the members do on the Discord server goes through ShorBot, the buttons and menus they click included, such as accepting the rules, opening a support ticket or picking a role from a menu. Decided by Gilles on 2026-10-28, in place of the line drawn on 2026-10-27, where a role menu of buttons on a message the panel posted was the panel's.

Of the Bot's expected features, which the POs listed and Gilles relayed on 2026-10-23 (#4), ShorBot builds the first four: the Membre role given when a member accepts the rules, the names of the two voice channels that show the game servers' state, the temporary voice channels, and support tickets. The fifth, the direct message a member gets with a sanction, is the panel's, since the staff give the sanction from the panel (#27). Decided by Gilles on 2026-10-28, the day he took ShorBot over from loanspac, in place of that morning's decision to take the tickets, the Membre role and the game servers' state into the panel: ShorBot has to stay on the gateway for the temporary voice channels anyway, since REST reads one account's voice state at a time and lists no channel's (https://docs.discord.com/developers/resources/voice, read 2026-10-28), Gilles now develops both, and the members' features gather in one bot. None of the four ran anywhere: at `ef620dc` (2026-10-27), ShorBot's `main` holds `/help` and `/ping`, and its unmerged branches `feat/ticket` (11392fd) and `feat/status` (67b8c93) a first version of the tickets, with neither a closing reason nor an archive, and slash commands that toggle the status by hand (read 2026-10-28).

## Considered Options

- **The panel's own Discord application runs a gateway bot of its own on the VPS.** Independent from loanspac, but two bots doing neighbouring jobs, and it needs sudo and Node on a shared VPS this project does not administer. The VPS stopped being a reason once Gilles administered it, and the decision holds on the first one (Gilles, 2026-10-27).
- **The panel connects to the gateway with ShorBot's token.** Two sessions for one bot, which risks handling each event twice.
- **The panel's application takes the support tickets, the Membre role, through a button, and the game servers' state, and ShorBot keeps the temporary voice channels.** Decided on the morning of 2026-10-28, because a warning, a timeout and a kick are contested through a support ticket (`docs/agents/open-questions.md`), so the sanction, its direct message, the ticket that contests it and the record of the account would have sat on two sides of an API that ShorBot does not have, and that loanspac would have had to agree to. Reversed the same day, once Gilles took ShorBot over: the direct message only names the kind of support ticket, and a warning is cancelled on the panel by a staff member who read the ticket, so the one datum that crosses is a closed ticket's archive, for the record (#197), whose link Gilles now designs on both sides; and it split the members' features over two applications, one of which has to stay on the gateway anyway.
- **The panel's application answers every interaction of the messages it posts**, as drawn on 2026-10-27. A button that accepts the rules or picks a role is the same mechanism in either application, so the members' side would sit in two places.

## Consequences

- The first feature that needs data from ShorBot, the archives of support tickets on the record (#197), brings the link between them, which goes from ShorBot to the panel: when a ticket closes, ShorBot sends its archive to a Route Handler of the panel, which knows ShorBot by a secret they share, and keeps it in its store (ADR 0004). So ShorBot listens on no port, and the panel keeps the store and what `docs/personal-data.md` asks of it. ShorBot holds no HTTP API: at `ef620dc` (2026-10-27) its `main.py` holds `/help` and `/ping` (https://github.com/ShorRP/ShorBot/blob/ef620dc/main.py). The route, the secret and what an archive holds are settled when #197 is grilled, after the store (#174, #175). Decided by Gilles on 2026-10-28, over the panel calling an API of ShorBot, which would have to listen on a public port with TLS, and over a database the two would share.
- A sanction's direct message tells the member to contest through a support ticket « ❓ Autre demande », the kind ShorBot shows, named as text, with no ID of ShorBot's channels in the panel. So the moderation section reaches production only once Shor's Discord server has that kind of ticket (#183).
- What the staff do with plain REST calls, such as AutoMod rules, roles or channels, stays in the panel.
- The panel's Interactions Endpoint comes before #150, the wave that first planned it. It must be "a public endpoint that Discord can reach", which answers a PING and checks each request's signature before the URL saves, and Discord keeps sending it "automated, routine security checks", some with invalid signatures, then removes a URL that fails them (https://docs.discord.com/developers/interactions/overview, modified 2026-07-22). An application holds one such URL, which `PATCH /applications/@me` changes (https://docs.discord.com/developers/resources/application, modified 2026-07-21). So "Shor Panel Dev" reaches `pnpm dev` through a Cloudflare quick tunnel, which needs no account and whose URL changes at each run (https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/, updated 2026-09-30), and a script points the application at it each time; its previews receive no interactions (Gilles, 2026-10-28). ngrok's free plan, which keeps one domain, was set aside: it needs an account, and its pricing calls part of it a "one-time free trial credit" (https://ngrok.com/pricing, read 2026-10-28), which **Costs** keeps out. A protected preview reached through Vercel's Protection Bypass for Automation, or one a Deployment Protection Exception makes public, was set aside too: the first secret opens every deployment of the project, and both make each try wait on a push (https://vercel.com/docs/deployment-protection, updated 2026-09-15).
