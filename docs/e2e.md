# End to end

The reference behind `.claude/rules/e2e.md`: what Next.js's test mode, Playwright, axe and the browser were seen to do, the measures behind each fixture, and the trials that showed what a flow proves. The rule says what to do; this file says how it was known. A flow that its test title says plainly has no entry: the title is its description.

The `node_modules` citations are those of Next.js 16.4.2, React DOM `19.3.0-canary-278794d7-20261002` and Playwright 1.64.1 unless a package is named: an update of a package re-reads the citations that name it (`.claude/rules/dependencies.md`, **Docs that name a version**). A run of a throwaway build or probe carries its date.

## The server and the fake Discord

- `next.onFetch`, from `next/experimental/testmode/playwright`, is declared at `node_modules/next/dist/experimental/testmode/playwright/next-fixture.d.ts:5`. The API is experimental and absent from `node_modules/next/dist/docs/`. Once `experimental.testProxy` is on (`node_modules/next/dist/server/lib/router-server.js:663`), a request that carries `next-test-proxy-port` sends the server's `fetch` calls to `localhost` (`node_modules/next/dist/experimental/testmode/context.js:26`, `node_modules/next/dist/experimental/testmode/fetch.js:102`).
- `next start` loads `next.config.ts` again (`node_modules/next/dist/server/lib/router-server.js:133`, `node_modules/next/dist/server/config.js:1306`).
- Next.js lists every experimental key a config sets, `false` included, under « Experiments (use with caution) » (`node_modules/next/dist/server/lib/app-info-log.js:111-118`), which is why `next.config.ts` sets `experimental.testProxy` only when the variable is on. A build without the variable records none (`.next/required-server-files.json`, 2026-10-25).
- `@next/env` sets no variable the environment already holds (`processEnv`, `node_modules/.pnpm/@next+env@16.4.2/node_modules/@next/env/dist/index.js`), so the placeholders of the `webServer` win over `.env.local`'s.
- Next.js's `next` fixture marks only the requests of a test that uses it (`node_modules/next/dist/experimental/testmode/playwright/next-fixture.js:23-29`), and asks the last `next.onFetch` handler first, moving on when one returns `undefined` (`:36-43`). The `abort` that the fixture answers makes the server's `fetch` throw as a network error would (`node_modules/next/dist/experimental/testmode/fetch.js:126-128`).
- Playwright calls a route handler "only for the first url if the response is a redirect" (`node_modules/.pnpm/playwright-core@1.64.1/node_modules/playwright-core/types/types.d.ts:4441`). On 2026-10-26, a probe whose page routed `discord.com` still reached the real Discord through a redirect, while Chromium kept the test headers over a redirect within one origin. That is why the `logIn` fixture routes `/login` itself (#10).

## The fixtures

- `toHaveURL` can resolve before the `load` of the page it names, so `checkAccessibility` first waits for `load`: after the reload in the flow of a member who loses the staff role, the browser loaded `/`, then requested `/login/refused` as a new document 17 ms after `/`'s `load`, and `toHaveURL` resolved 6 ms before that document's `load` (throwaway test, 2026-10-27).
- axe-core 4.14.0 tags no rule `wcag22a` (`axe.getRules()`, 2026-10-27), so the fixture lists `wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa` and `wcag22aa`, and no `wcag22a`.
- Without the wait for the animations, axe measured a throwaway test's 1 s color transition halfway, at 1.04:1 (2026-10-27), as it would the Button's `transition-all` and the Input's `transition-colors`, whose colors dark changes (inferred). The animations of a view transition's pseudo-elements are in `document.getAnimations()` until it ends (throwaway test, 2026-10-27, #134), and a finished one may stay there for good (`.claude/rules/view-transitions.md`, #211).
- Against a build whose dark values sat under shadcn/ui's `.dark` class, the body kept `lab(100 0 0)` in dark and the background check failed (#70, 2026-10-27): that check is what keeps the dark run from measuring the light theme again.
- The page has no `<title>` for about 0.3 s after some writes, and axe's `document-title` reads `document.title` (`node_modules/.pnpm/axe-core@4.14.0/node_modules/axe-core/axe.js:28513-28516`). Next.js 16.4.2 keys the `Metadata` element of the head of each dynamic response, a Server Action's `refresh()` included, with that request's ID, `requestId + 'm'`, which is new for each request (`node_modules/next/dist/server/app-render/app-render.js:320-331`, `:197-198`, `:1550-1564`), so React unmounts the old `<title>` and mounts a new one, inside a `<Suspense name="Next.Metadata">` that is new too (`node_modules/next/dist/lib/metadata/metadata.js:97-112`): when its metadata is not decoded yet, the boundary commits empty (inferred from the gaps below, not read in the Flight client).
- A throwaway Playwright probe of the blocked words' writes, 10 writes a run, logging every mutation of `<title>` and every view transition (2026-10-30), saw a new `<title>` element at every write, and 5 gaps with no `<title>` and `document.title === ""` in 150 runs, 1,500 writes, so about 0.3% of them, of 297 to 316 ms. In the 4 gaps logged with their view transitions, the update callback of the write's view transition left no `<title>`, no font or image was loading, and the next commit that mounted it came 21 to 37 ms after that view transition had finished. That React holds that commit behind the running view transition is inferred, not read in React's code. The same remount drops `<meta name="viewport">`, whose element is keyed `requestId + 'v'` (`app-render.js:327-328`), for the same moment (inferred, the probe did not read it).
- The blocked words' flow waits for that view transition and for the toast (#138, #227), which hides most of the gap and not all of it (inferred), so 200 passes of the flow prove little: `e2e/check-accessibility.test.ts` proves the title wait by taking the `<title>` away for 1 s, where 3 runs of 3 failed on `document-title` without the wait (2026-10-30, #161). Only a patch of Next.js could close the gap.
- `readToast` presses F6, which focuses the region of toasts and pauses their timers (`node_modules/@base-ui/react/toast/viewport/ToastViewport.js:61-67`, `:129-130`, Base UI 1.9.0), and Base UI hides a toast's « Fermer » from assistive technologies until the region is focused or hovered (#227).
- The flows of the sidebar and of the menu that log out failed in 6 runs of 6 on `prefetchedPaths` before the sections' links stopped prefetching, where the same prefetch failed them only now and then without that fixture (#153, 2026-10-28).
- A sanction's link goes to `/records/<id>`: its throwaway build recorded that path three times, and whether before or after the logout is not established.
- A modal Sheet hides the page behind it from the accessibility tree (Base UI), so `logOutWithScriptsHeld` was red on the audit log's flow that logs out from the bar's menu until the links it was given were found by CSS (`e2e/audit-log.test.ts`, 2026-11-03, #359).

## The browser's console

- A throwaway test that loaded an image from another origin failed on « Loading the image '…' violates the following Content Security Policy directive » (#76, 2026-10-27): Chromium logs a violation at `error`. Throwaway tests showed each of the three, an `error`, a `warning` and a `pageerror`, failing a test, and a `console.log` failing none (#63, 2026-10-25).
- #441 is the production error that React's Flight client builds for an error row of the RSC stream, whose message the server leaves out, and sets the row's digest on (`node_modules/next/dist/compiled/react-server-dom-turbopack/cjs/react-server-dom-turbopack-client.browser.production.js:1690-1693`, `:1826-1831`); its full text, « An error occurred in the Server Components render. The specific message is omitted in production builds… », is in the node build of the same client (`react-server-dom-turbopack-client.node.production.js:1906`). Next.js hands `hydrateRoot` an `onCaughtError` (`node_modules/next/dist/client/app-index.js:227`) that prints what an explicit error boundary, here `error.tsx`, catches, in production through `console.error` (`node_modules/next/dist/client/react-client-callbacks/error-boundary-callbacks.js:103`), so every read that fails brings the line.
- #419 is « The server could not finish this Suspense boundary, likely due to an error during server rendering. Switched to client rendering. » (`react-dom-client.development.js:11500`, `react-dom-client.production.js:7393`, in `node_modules/next/dist/compiled/react-dom/cjs/`). React raises it where it hydrates a Suspense boundary that the server flagged for client rendering, `$RX("B:4","<digest>")` in the streamed HTML (`react-dom-client.development.js:11479-11512`), and queues it as a hydration error (`:5736`); Next.js's `onRecoverableError` (`app-index.js:226`) hands it to `reportError` (`on-recoverable-error.js:57`, `report-global-error.js:11-12`, in `react-client-callbacks/`), which fires the `window`'s `error` event. Each carries the digest of the server's error, the one `error.tsx` shows.
- The server flags one boundary on `/audit-log` and three on `/blocked-words`, and the client raised two #419 on each in every local run, also under a CPU 8 times slower, but one on CI's runner (run 40977975608, where the flow of the error pages failed on the count), so the count follows no boundary's count and no fixed number, which is why the fixture takes each declared line once, however many times it comes.
- The two of a local run share one call stack, the `reportError` call of the loop that reports a commit's recoverable errors, 0.4 ms apart, so they are two entries of one queue of hydration errors (a throwaway probe of the streamed HTML, of `reportError` and of its stack, 2026-10-30).
- Why they come after the click and not at load, and why the queue holds two entries or one, is inferred, not traced: none comes in the 700 ms that follow the load, the DOM holds no `<!--$!-->` marker at the error page nor after the retry, and React clears its queue of hydration errors only where a hydration starts and drains it where a boundary or the root completes (`react-dom-client.development.js:5724`, `:11567`, `:12302`, `:12917`, `:13263`), so the entries that the render which threw to `error.tsx` queued probably wait for the render that « Réessayer » starts, and how many times that render reached the flagged boundary probably depends on when the `$RX` instruction came, against the hydration.
- Nor is #419 bound to the click: a flow of the error page that never clicked « Réessayer » and declared #441 alone got it once on CI's runner, at 390 px, and none in 60 local runs, 30 of them under a CPU slowdown of ×6 (run 41683657341, 2026-11-03, #362). A flow that clicks « Réessayer » got it in each of the 60 runs of the corrected flow, and the list of accounts' flow, which declares #441 alone, may meet the same (inferred, not tried).
- Failing the AutoMod rules' read for the audit log's flow raced the layout's count of blocked words, which reads the rules too: the call that came first took the one failure, which `failNext` keeps for a method, and the count swallowed it while the page rendered (#61). The count's own flow (`e2e/staff-header.test.ts`, a `DiscordError` while reading the count) fails that read by design.

## The favicon flow

- The flow of `e2e/favicon.test.ts` as it was failed with Playwright's « strict mode violation », a locator of `link[rel="icon"]` resolving to 2 elements, in 1 run of 300 (#169).
- Read in the code: Next.js wraps the metadata in a `<div hidden>` around `<Suspense name="Next.Metadata">` and says the wrapper « remains empty », since the tags are hoisted out (`node_modules/next/dist/lib/metadata/metadata.js:102-111`); `Head` is keyed by the page (`node_modules/next/dist/client/components/app-router.js:385-387`); deleting a dehydrated boundary has `clearHydrationBoundary` remove the nodes from its start comment to its end comment (`react-dom-client.development.js:23996-24047`, called at `:15530-15544`), and deleting a hoistable removes its own `stateNode` (`:15440-15454`); a client-side mount creates its hoistable `<link>` at render (`:12347-12352`), and only a hydrating one looks for a link already in the document (`:15899-15931`).
- Observed, by throwaway Playwright probes with a `MutationObserver` and a `history.pushState` hook, the CPU throttled to 4× through CDP `Emulation.setCPUThrottlingRate`, 4 workers (2026-10-29): before the click, the page held `<div hidden=""><!--$--><!--/$--></div>` and the server's link in `<head>`, written while the document parsed. Of 60 logouts, 18 held two identical links 700 ms later; in those 18, and in none of the other 42, that link had no React fiber (`__reactFiber$…` key) when `history.pushState` ran. It had none at the click, which follows `load`, in 56 of the 60, and a fiber claimed it between the click and the push in 38 of those 56. None of 60 logouts that first waited for a fiber held two links, and in a second probe 15 of 40 sessions kept the pair through four moves between sections, 500 ms apart.
- Inferred: the pair comes from navigating while the boundary is still dehydrated, so that the deletion clears nothing of the server's link, which no fiber owns, and the next page's link is created beside it; it then lasts as long as the document, since only a fiber removes a link (observed through four moves, the rest from the code); and it costs a staff member nothing, both links naming the same file (Chromium shows one icon, not checked).
- The flow then waits until `distinctIconHrefs()` holds one href among all the page's icon links, which lets two identical links through and fails two different ones (#169).
- Under the same throttle, the flow before #169 failed 26 runs of 60 and its fix none of 100 (#169). That wait alone took the staff page's link for the logged-out page's: the link stays in `<head>` for 5 to 11 ms after `history.pushState` (observed with no throttle, in 10 logouts of 10, by a throwaway probe of 2026-10-29, #169, which #263's body quotes) and, in the pair above, for the life of the document.
- Observed, by throwaway builds and tests (2026-10-30, #263): on a build whose `/login/logged-out` had `icons: { icon: [] }` in its `metadata`, so that its built HTML held no `<link rel="icon">` while `/login/failed`'s still did, the flow of #169 failed 10 runs of 10, its wait reading an empty list of hrefs; with a copy of the staff page's link appended to `<head>` before the logout by `cloneNode`, which no fiber owns, that flow passed 10 of 10, and the marking flow failed 10 of 10 with the copy as without it, and 20 of 20 under the 4× throttle with 4 workers, each time on the wait for an unmarked link. On the clean build, the marking flow passed 300 of 300 (`pnpm test:e2e e2e/favicon.test.ts --repeat-each=300`) and 60 of 60 under the throttle with 4 workers.
- Inferred: the appended copy stands for the server's link that stays, both being links no fiber owns; the flow of #169 failed on that build because the head had swapped before its wait ran, and it passes on a logged-out page with no icon link of its own only when the staff page's link stays or its wait lands in the 5 to 11 ms, a narrower gap than #263 described; and only the render of `/login/logged-out` creates an unmarked link, although a hydrating hoistable that finds no matching link also appends one (`:15932-15934`), which would be unmarked if it came after the marking, and none of the 40 runs of the marking flow on that build found one.
- An update of Next.js or React that kept one icon link across the navigation would leave `ownIcons` empty and fail the flow on a page that is right. A copy of the flow run under the same throttle tells that the tolerance can go: it finds one icon link in all after the logout and none still marked, since the unmarked link the flow reads is there whether the server's link stays or not; `servedIcon()` can then read a locator that must match one element.

## Gotchas

- With `cacheComponents`, Next.js hides the pages it preserves with React's `<Activity>`, and hidden Activity content has `display: none` but remains in the document (`node_modules/next/dist/docs/01-app/02-guides/preserving-ui-state.md:17`, `:355`): on 2026-10-27, once a click on « Journal d’audit » had reached `/audit-log`, `page.locator("h1, h2")` still found the `h1` and the `h2` of `/blocked-words` (#133).
- A page that streams while the browser posts a form natively: before the header flow waited for `load`, logging out failed it in 26 of 60 runs on 6c526f6 and 41 of 60 with the crossfade, and it then passed 179 of 180 (`--repeat-each`, 2026-10-27, #134). The posted document throws React's error #412, `Connection closed.` (`node_modules/next/dist/compiled/react-server-dom-turbopack/cjs/react-server-dom-turbopack-client.browser.development.js:4917`), or #419. A `<Suspense>` under a `<ViewTransition>` widens the window, since React's streaming runtime reveals it through `document.startViewTransition` (`node_modules/next/dist/compiled/react-dom/cjs/react-dom-server.node.production.js`).
- The skeleton test, with motion, once found no pulse right after its skeleton showed (1 run of 100, `--repeat-each 25`, 2026-10-28), so it first waits for every `link[rel="stylesheet"]` to have its `sheet`, then passed 160 runs of 160 (`--repeat-each 40`, 2026-10-28). That a skeleton can show before the stylesheets apply is inferred.
- Chromium hands assistive technologies the text of an element under `text-transform: uppercase` in capitals, while Playwright's `getByRole` names an element from the DOM's text, as written: on 2026-10-29, `Accessibility.getFullAXTree` over CDP named the search's list « 1 COMPTE COMMENCE PAR « LY » » and the sidebar's groups « ADMINISTRATION » and « MODÉRATION », for the search « ly », where `e2e/records.test.ts` found « … par « ly » » (throwaway Playwright test, #232). #324 replaced that count with the ranks, « 1–3 sur 3 », which the same test now finds and whose capitals were not read back (inferred).
- A probe of `/blocked-words` at 360 px found 11 hidden `<Suspense>` segments at `load` and none once the reveal ended (2026-11-03, #355), and the first draft of `e2e/responsive.test.ts`, which measured at `load`, passed on empty boxes.
