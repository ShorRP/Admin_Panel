# CLAUDE.md

The Admin Panel is the web app Shor's staff use to administer the Discord server: a Discord login for the staff, blocked words kept in a Discord AutoMod rule (ADR 0002), and an audit log (ADR 0004). It is a Next.js app (App Router) in TypeScript under `src/app/`, to be hosted on Vercel's free Hobby plan, on a `vercel.app` domain with no domain bought for it (Gilles, 2026-10-24, while grilling #51; the Hobby plan still waits on « Does Shor make money? » in `docs/agents/open-questions.md`), that talks to Discord's REST API only (ADR 0003). As of 2026-10-24 it serves a single French home page, on the background and text of the shadcn/ui theme (**Interface**); the repo also holds the docs and the tooling.

## How we work

## Language

Three things are in **French**: chat with the user, GitHub issues and their board (title, body, comments, and the board's descriptions and view names; see `docs/agents/issue-tracker.md`), and the panel's interface, which is French only, with no translation layer. Everything else is in **English**: docs, `GLOSSARY.md`, ADRs, PR text and PR comments, commit messages, and every word written into the codebase: file names, identifiers, logs. URLs count as file names, since each segment is a folder under `src/app/`: `/blocked-words`, not `/mots-interdits`.

## No comments

The repository holds no comments, in any file that supports them: code, tests, scripts, CSS, HTML, SQL, YAML, `.env.example`, whose variables are documented in the README. Two exceptions only: a shebang, and a tool directive the code needs to work (`eslint-disable…`, `@ts-expect-error`, `/// <reference …>`, `@vite-ignore`, `webpackIgnore`).

What a comment would say goes elsewhere: the why of a change in its commit message, a decision in an ADR, a term in `GLOSSARY.md`, an invariant in a test and its name. Code copied from elsewhere, such as skymp-heavy-rp or EsportCards, loses its comments on the way in.

`pnpm check:comments` checks every tracked or untracked, non-ignored file. A hook runs it before `gh pr create`, and CI on every PR and every push to `main`.

## Facts and docs

- **Facts apart from inferences.** Everything you write to docs, tickets or reports keeps verified facts, with their source (`file:line`, commit, URL and date, command output), visibly separate from inferences.
- **Challenge with evidence.** When the code, the docs, `GLOSSARY.md`, an ADR and the user's request disagree, name the contradiction, quote both sides, and ask which one wins. Record the answer through domain-modeling.
- **Unrecoverable why.** When nothing explains a decision or a fact the work needs, append it to `docs/agents/open-questions.md`: the question, where it shows up, who is likely to know, what is blocked on it.
- **Docs as you go.** Docs are updated the moment they become true, in the same change. `GLOSSARY.md` is a glossary and nothing else; ADRs follow domain-modeling's bar. When docs contradict the code, fix them in the same change if it takes a few lines, otherwise list them in your report.
- **Scope.** Each diff stays inside its ticket. Problems you spot nearby are loose ends: groom-backlog files them as tickets.
- **Gotchas.** When a session hits a trap the environment doesn't reveal, add one line under **Gotchas**. Delete lines that stop being true.

## Architecture

How a feature is written end to end, as Gilles decided while grilling #47 on 2026-10-23, then #49, #54, #52 and #50 for the lines that point to **Errors**, **Testing**, **Interface** and **Monitoring**. It was written before the code: each ticket that writes the code follows it.

- **Folders.** `src/app/` only routes: its `page.tsx`, `layout.tsx` and `route.ts` call a domain folder named after a `GLOSSARY.md` term, such as `src/staff/` (login, session, staff role), `src/blocked-words/` or `src/audit-log/`. A domain folder holds its logic, its components, its `actions.ts` and their tests. `src/discord/` is the adapter to Discord's REST API, `src/ui/` holds what the interface shares (**Interface**), and `src/monitoring/` the logs and the alerts (**Monitoring**). The error pages are the one exception (**Errors**).
- **The Discord seam.** `src/discord/` exposes two interfaces, one method per endpoint the panel calls but the alerts' webhook (**Monitoring**), typed with `discord-api-types`. `DiscordApi` uses the panel's application token and is bound at construction to one Discord server, so no method takes its ID: AutoMod rules, audit log, reading a member. `DiscordOAuth` uses the client ID and secret: authorize URL, code exchange, current user. The real implementations call `fetch`, with neither `@discordjs/rest` nor `@discordjs/core`. `src/discord/fake-discord.ts` keeps a Discord server's state in memory and, like Discord, adds an audit log entry on every write. Only tests import it: `pnpm dev` runs against the panel's development application, "Shor Panel Dev", and Gilles' test Discord server (#7). A `no-restricted-imports` rule of `eslint.config.mjs` refuses it and its HTTP adapter (**Testing**) anywhere in `src/` outside `*.test.*` files.
- **Entry points only wire.** Pages, layouts, `actions.ts`, Route Handlers, `proxy.ts` and `instrumentation.ts` hold no logic of their own and never read `process.env`. Those that need Discord get the real clients from `createDiscordApi()` and `createDiscordOAuth()` and pass them on, as in `addBlockedWord(discord, staffMember, word)`; tests pass the fake instead, with no `vi.mock`. The login callback's Route Handler passes `createMonitor()`'s `Monitor` the same way (**Monitoring**). Only `src/discord/` reads Discord's variables, `src/staff/` the staff's, and `src/monitoring/` its own (**Security**, **Variables**). Vitest cannot render `async` Server Components (`node_modules/next/dist/docs/01-app/02-guides/testing/vitest.md:9`), so what a page does lives in functions tested directly.
- **The staff check.** Every page but the login pages under `/login` and the error pages, and every Server Action that writes, starts with `requireStaffMember` from `src/staff/`, and every domain write takes the branded `StaffMember` it returns (ADR 0005). It never returns a failure: it redirects to `/login` without a readable session, and to `/login/refused` a member who is not on the Discord server or lacks the staff role. The login callback, which has no session yet, runs the same check by Discord user ID and redirects itself (ADR 0005). It uses `redirect` rather than `forbidden()`, which needs `experimental.authInterrupts` (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/forbidden.md:17`) and gives a Route Handler an empty body (`node_modules/next/dist/server/route-modules/app-route/module.js:259-263`).
- **Writes** are Server Actions, in their domain folder's `actions.ts`, marked `"use server"`, and end with `refresh()` once the write lands. Logging out is a Server Action too, which only ends the session. Route Handlers serve OAuth2 only: `/login` and `/login/callback`.
- **Validation** uses zod 4 throughout the repo, config included. Domain functions validate what comes from the browser, such as an action's `FormData` or the callback's query string. An invalid URL parameter counts as absent. Discord's responses are typed, not validated.
- **Components** are Server Components. `"use client"` goes only on a leaf that needs browser state or events, in its domain folder, on some components shadcn/ui's CLI copies (**Interface**), and on the two error pages Next.js requires it of (**Errors**); never on a page, a layout or anything that reaches `src/discord/`. A client leaf may hold browser state, such as `useActionState`'s, but no logic: it hands that state to a component whose output follows from its props alone (**Testing**).
- **Caching.** Nothing from Discord and nothing from the session goes through `use cache`, since the panel reads Discord back on every view (ADR 0002). Only the static shell prerenders; the part of a page that waits on Discord sits under `<Suspense>`, with a French fallback.
- **`proxy.ts`** sends a request without a readable session to `/login`, on every route but `/login`, everything under it, and static files: the callback opens no session for a member without the staff role, who would otherwise loop from `/login/refused` back through Discord. It authorizes nothing.
- **Imports** that leave their folder use `@/*`, mapped to `src/*`; imports within a folder stay relative, except in `src/ui/` (**Interface**). Vitest resolves the alias only with `resolve.tsconfigPaths: true`, which Vite 8.3.5 leaves off by default.

## Errors

How the panel fails, as Gilles decided while grilling #49 on 2026-10-23, then #53 for what a successful write returns. Like **Architecture**, it was written before the code.

- **Four kinds of failure.** _Refused input_: the staff entered something the panel refuses, or the Discord server is in a state they can fix in Discord, such as already holding 6 keyword rules. _Refused access_: no readable session, or not staff (**The staff check**). _Discord unavailable_: a 429 the panel does not retry or that comes back, a 5xx, a network error or a timeout. _Panel error_: everything else, a misconfiguration included, such as a revoked token or a missing permission; the staff can only report it.
- **`DiscordError`** is the one class every method of `DiscordApi` and `DiscordOAuth` throws, network errors and timeouts included. It carries the HTTP status, Discord's JSON `code` and `message`, the delay of a 429, the method and the route's pattern, as Discord's docs write it, such as `/guilds/{guild.id}/members/{user.id}`, never the path filled in, since Next.js prints its properties in the logs (**Monitoring**), and says whether Discord is unavailable. One absence is an answer rather than an error: `getMember` returns `null` on Unknown Member, code 10007 (https://docs.discord.com/developers/topics/opcodes-and-status-codes, read 2026-10-23).
- **Retries.** Through `DiscordApi` and `DiscordOAuth`, a 429 is retried once, after its `retry_after`, when that is 2 s or less. Nothing else is retried, since a create that got a 5xx may have landed. Every call they make gives up after 10 s, through `AbortSignal.timeout`. An alert follows its own rules (**Monitoring**). The panel tracks no rate-limit bucket: it only reacts to a 429.
- **Write results.** A domain write checks every limit Discord documents before calling it, so a 400 from Discord is a panel error. It re-reads what it changes right before writing and applies only its own change, with no conflict error: a form sends one word, never a list. It returns `{ ok: true, message }`, or `{ ok: false, message }` with each field the form sent, as typed and under its name, such as `word`: one French `message` per form, written by the domain, that says what landed, such as « « foo » est maintenant un mot interdit. », or what went wrong, for refused input and for Discord unavailable, and the fields so the form keeps them (**Interface**). The action hands that to the form as is. Anything else is thrown, a `DiscordError` from the action's `requireStaffMember` included. Reads never write: what a page needs created, the first write creates.
- **Read failures.** What a page reads from Discord is thrown on failure, with no catch on the way, and `error.tsx` replaces the page under its layout. In production it gets a generic message and the error's `digest`, never the original message (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md:106`, `:111-115`), so it shows one message for Discord unavailable and panel error alike, a « Réessayer » button that calls `retry`, and the `digest` as a reference.
- **Error pages.** `src/app/` holds `not-found.tsx`, `error.tsx` and `global-error.tsx` with their own markup, since they belong to no domain. Next.js requires `error.tsx` and `global-error.tsx` to be Client Components, and `global-error.tsx` to bring its own `<html>` and `<body>` (`error.md:21`, `:163`), here with `lang="fr"`. The login callback throws nothing: a member who is not staff goes to `/login/refused`, any other failure to `/login/failed`.
- **Messages** are the panel's own French sentences, never Discord's message, a stack or a token. A failure's message says what to do next: correct the input, retry, or report the problem in the staff's Discord channel, named in the text (`docs/agents/open-questions.md`). A success's message says what landed (**Write results**).

## Testing

What the panel's tests prove and where, as Gilles decided while grilling #54 on 2026-10-23, then #53 for the theme and accessibility, and #50 for monitoring. Like **Architecture**, it was written before the code.

- **Layers.** Domain functions carry most of the tests, in Vitest against the fake Discord. The real implementations of `src/discord/` are tested on their own (**The real implementations**). Entry points only wire (**Architecture**): Playwright covers the flows where a wiring mistake shows nowhere else (**End to end**), and nothing but the typecheck and the build checks the rest. No coverage tool, no threshold, no snapshot: a test names the text or the attribute it proves, never a class.
- **The fake.** `fake-discord.ts` implements `DiscordApi` and `DiscordOAuth`. Its constructor takes a Discord server's starting state: members and their roles, AutoMod rules, audit log entries. What happens in Discord outside the panel has methods of its own, named as in Discord, such as a member losing a role, or a member creating or editing an AutoMod rule by hand: the audit log records that rule change under the member's name, with no reason from the panel. Another method issues the OAuth2 code a test logs in with. The fake refuses what Discord refuses among the limits the MVP touches: 6 keyword rules per Discord server and, per rule, 1,000 keywords of up to 60 characters (ADR 0002); an audit log reason of 1 to 512 characters (ADR 0004). It throws the `DiscordError` of a 400 with code 50035, so a limit the domain forgets to check fails a test. `failNext(method, error)` makes that method's next call throw that `DiscordError`, once. Each test builds its own fake.
- **The HTTP adapter**, next to the fake in `src/discord/`, takes a `DiscordApi` and a `DiscordOAuth` as parameters and answers a `Request` addressed to Discord with a `Response`, in the shape of `fetch`. It imports no fake: tests and Playwright hand it one.
- **Assertions read state.** A test proves a write by what it leaves on the Discord server, read back through `DiscordApi`'s own methods, never by the calls the fake received.
- **Testing the staff check.** The check by Discord user ID (ADR 0005) is tested in Vitest against the fake, a staff role removed between two requests included. `requireStaffMember` itself is covered end to end, since it reads `cookies()`, which throws outside a request (`node_modules/next/dist/server/request/cookies.js:104`), and redirects. A `StaffMember` in a test comes only from that check, called on a fake that gives the member the staff role: no test writes `as StaffMember`. A type test in `src/staff/`, checked by `pnpm typecheck` rather than by Vitest's typecheck mode, proves that an object written by hand with the same fields is not a `StaffMember`.
- **The contract suite**, written against the `DiscordApi` interface, runs three times: on the fake, and on the real implementation over the HTTP adapter and a fake, both in `pnpm test`; then on the real implementation against Gilles' test Discord server, with "Shor Panel Dev"'s token, by `pnpm test:contract`, by hand. That last run reads the same `.env.local` as `pnpm dev`, deletes what it creates, never touches the rule `pnpm dev` manages, and passes before a PR that touches `src/discord/` merges; the PR says it ran. Running it in CI is left to #57, within **Security**'s **CI secrets**. The fake has no other tests. `DiscordOAuth` stays out of the suite, since a code exchange needs a member's consent in a browser: its fake follows Discord's docs, a Vitest test runs its real implementation over the adapter, and the first logins with "Shor Panel Dev", on `pnpm dev` and on a preview, prove the rest.
- **The real implementations** take `fetch` as a parameter, which `createDiscordApi()` and `createDiscordOAuth()` fill with `globalThis.fetch`. Tests pass a function that returns hand-written `Response`s, for what the contract suite cannot trigger on demand: a 5xx, a 429, a timeout, a network error. Delays run on real timers, with no clock injected, since the fake timers of Vitest 5.0.5 do not fake `AbortSignal` (`FakeMethod`, `node_modules/vitest/dist/chunks/index.aTZaPVhf.js:3915`): the test's `fetch` rejects with the `TimeoutError` that `AbortSignal.timeout` raises, and a 429's `retry_after` is a few milliseconds when it is retried, 2.5 s when it is not. The 10 s value itself goes untested.
- **No DOM.** Vitest keeps running without one (**Feedback loops**). The component a client leaf hands its state to (**Components**) renders with `react-dom/server`; the leaf's state and events are proven end to end. The client components copied from shadcn/ui for the MVP wrap Base UI primitives, whose logic is Base UI's (**Interface**). This is revisited with the first client component of the panel's, copied ones included, that holds logic of its own.
- **The theme.** A Vitest test reads `src/ui/globals.css` and proves each contrast pair that **Accessibility** sets (**Interface**), in light and in dark (#70). It covers what axe leaves out, since axe measures only the contrast of text (inferred, not checked against axe's rule list).
- **Testing monitoring.** Vitest proves four things (**Monitoring**). `isPanelError` says yes to a panel error and no to Discord unavailable. The alert built from a `DiscordError` of `getMember` holds the route's pattern and no member ID, and leaves out a `request.path` that carries `code` and `state`. Sending an alert, over a hand-written `fetch`, gives up after its delay, drops a 429 and never throws. The login callback's domain function, over an in-memory `Monitor`, reports a panel error at `error` and a missing `state` at `warn`; a report is its output, not a write to Discord, so the test reads what that `Monitor` holds (**Assertions read state**). End to end runs without `ALERT_WEBHOOK_URL`, so it sends no alert.
- **`proxy.ts`** is the one entry point with a Vitest test. `unstable_doesProxyMatch` and `getRedirectUrl`, from `next/experimental/testing/server` (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md:728-756`), check that everything under `/login` and static files get through, and that any other route without a readable session goes to `/login`.
- **End to end.** Playwright runs `e2e/*.test.ts` against `next start`, by `pnpm test:e2e`, in CI's job after `pnpm build`, on Chromium only, installed by `playwright install --with-deps chromium`; caching the browsers is left to #57. With `experimental.testProxy` (`node_modules/next/dist/server/lib/router-server.js:663`), `next.onFetch` from `next/experimental/testmode/playwright` (`node_modules/next/dist/experimental/testmode/playwright/next-fixture.d.ts:5`) answers the server's calls to Discord by handing each request to the HTTP adapter over that test's own fake. The API is experimental and absent from `node_modules/next/dist/docs/`, and once it is on, a request carrying `next-test-proxy-port` sends the server's `fetch` calls to `localhost` (`node_modules/next/dist/experimental/testmode/context.js:26`, `node_modules/next/dist/experimental/testmode/fetch.js:102`): `next.config.ts` turns it on only from `E2E_TEST_PROXY`, which Playwright's `webServer` alone sets and the build refuses on Vercel (**Security**). The browser's leg of OAuth, `discord.com/oauth2/authorize`, goes through `page.route`, which sends it back to `/login/callback` with a code the fake issued. E2E covers only the flows where a wiring mistake shows nowhere else: a staff member logs in; a member without the staff role is refused; a visitor without a session goes to `/login`; a member who loses the staff role mid-session lands on `/login/refused` at the next page; a blocked word is added, then removed, each write showing its message, and a refused one stays in the field; Discord unavailable during a read shows `error.tsx`, then « Réessayer » works. Every page these flows cross also passes `@axe-core/playwright`'s WCAG 2.2 A and AA rules, in light and in dark, and scrolls no wider than a 360 px viewport (#72), and reports no Content Security Policy violation (#76).

## Interface

What the panel's interface is built with, as Gilles decided while grilling #52 on 2026-10-23; the options set aside, and why, are in #52's decisions. Like **Architecture**, it was written before the code: #67 sets up the tools, then every ticket that writes a page follows it. What the tools carry, the theme's values, small screens, navigation, wording, dates, buttons, what a form shows and the accessibility level, Gilles settled while grilling #53 on 2026-10-24. The POs confirm three of his answers through #74, Shor's visual identity, the use on phones and the tone: #74 applies Shor's color and logo, and any other answer that differs from his becomes a ticket. **Code style** says how classes are sorted.

- **Framework.** React, through Next.js (#5), with no library for state, client-side fetching, forms, URL state or animation: Discord holds the state, Server Components read it, Server Actions write it, and a form sends one field. This is revisited when a client leaf must share state with another or fetch data itself. No React Compiler either, until a client leaf grows heavy.
- **Styles.** Tailwind CSS 4, through `@tailwindcss/postcss`. `src/ui/globals.css` imports Tailwind and holds the theme; `src/app/layout.tsx` and `src/app/global-error.tsx` both import it, since `global-error` receives no global styles (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md:163-165`). A class name is written whole, never built by concatenation, since Tailwind reads sources as plain text (https://tailwindcss.com/docs/detecting-classes-in-source-files, read 2026-10-23).
- **Component library.** shadcn/ui, on Base UI, in its `nova` style, with CSS variables, as `components.json` records. A ticket adds the components it is the first to use, through `pnpm exec shadcn add`. `shadcn` is a devDependency, since `shadcn init` makes `globals.css` import `shadcn/tailwind.css` from it (https://ui.shadcn.com/docs/cli, read 2026-10-23); Vercel installs devDependencies for the build (https://vercel.com/docs/builds/configure-a-build, **Install Command**, updated 2026-08-28). Components take a `className`, their variants use `cva`, and `cn` merges classes, which shadcn/ui's registry imports from the `cn` package (https://ui.shadcn.com/r/styles/base-nova/button.json, read 2026-10-23). The panel's own components follow the same shape.
- **Copied code** becomes the panel's own. Its English strings turn French, such as the Dialog's two « Close » (https://ui.shadcn.com/r/styles/base-nova/dialog.json, read 2026-10-23), and the rest stays as the CLI wrote it, but for the lines Prettier and the lint change (**Code style**), so that `shadcn add --diff` shows only what the panel changed. It gets no tests of its own.
- **`src/ui/`** holds `globals.css`, what shadcn/ui's CLI copies, and the components more than one domain uses; a component moves there when a second domain needs it. It holds no domain logic. Every alias of `components.json` points to `@/ui`, and the CLI rewrites imports through those aliases (https://ui.shadcn.com/docs/components-json, read 2026-10-23), so `src/ui/` imports itself through `@/ui/*`, never through a relative path, and nothing else through `@/`, which a `no-restricted-imports` rule of `eslint.config.mjs` enforces (Gilles, 2026-10-24, on #69). `"use client"` appears there only on a copied component that wraps a Base UI primitive, as the Dialog does; the panel's own components there have none and render from their props alone.
- **Theme.** shadcn/ui's semantic variables (`background`, `foreground`, `primary`, `muted`, `destructive`, `border`, `ring`, and the rest), set in `:root` and mapped through `@theme inline` (https://ui.shadcn.com/docs/theming, read 2026-10-23). The panel's code uses those, never a palette color such as `zinc-100`, which review checks. Tailwind's default palette stays, since copied components use it, such as the Dialog's `bg-black/10`. The panel follows the system's light or dark setting, with no toggle and no JavaScript: the `dark` variant is `@media (prefers-color-scheme: dark)`, the dark values sit under that query, with `color-scheme: light dark` (#70 moves them from the `.dark` class shadcn/ui writes). Until the POs give Shor's color and logo (#74), the colors stay `nova`'s `neutral` grays and the panel shows no logo; the color then becomes `primary` and `ring`, and the logo goes into the header and the favicon. Tailwind's preflight is the reset.
- **Fonts and icons.** The system's font stack, with no font loaded. A font `shadcn init` adds is removed; one the POs pick for Shor's identity (#74) goes through `next/font`, served from the panel's own domain (`node_modules/next/dist/docs/01-app/01-getting-started/13-fonts.md:11-13`, `:96`). Icons come from `lucide-react`, shadcn/ui's default, with the copied components that carry them; the panel's own buttons carry none, their French text is their name. A control without visible text has a French `sr-only` text.
- **Small screens.** Every page works from 360 px wide, in one column, with no horizontal scroll (#74 asks the POs whether the staff work from phones): the header wraps, and under `sm`, 640 px (`--breakpoint-sm: 40rem`, `node_modules/tailwindcss/theme.css:327`), the rows of a table stack.
- **Navigation.** Every page the staff check guards (**The staff check**) has a header, in a layout below the root one, so that the error pages, which Next.js renders under the root layout (**Read failures**), show none. The header holds « Panel de Shor », a link to `/`; one link per section, the current one with `aria-current="page"`; the member's Discord name; « Se déconnecter » (#71). `/` redirects to `/blocked-words` with a 307, not a permanent redirect, so a home page can come back. Tab titles follow `%s – Panel de Shor`, and the default stays « Panel d’administration de Shor ».
- **Wording.** The panel addresses the staff as « tu » (#74 asks the POs), and its buttons are infinitives: « Ajouter », « Retirer », « Se déconnecter », « Réessayer ». Its texts follow French typography: the apostrophe ’, « » with a no-break space U+00A0 inside, a U+00A0 before : ; ! ?, and « … » as one character, each typed as such in the source; `pnpm check:typography` is to refuse the rest (#73). Until then, the lint only refuses ' in JSX text, through `react/no-unescaped-entities` (`pnpm exec eslint --print-config src/app/page.tsx`, 2026-10-24), and sees neither strings nor spaces.
- **Dates** are absolute, on 24 hours and in Paris time, such as « 24 oct. 2026, 14:32 », from `Intl.DateTimeFormat("fr-FR", { dateStyle: "medium", timeStyle: "short", timeZone: "Europe/Paris" })` (Node 24.22.0). `timeZone` is always passed: the server renders dates, and it knows no browser's time zone. A date sits in a `<time>` whose `dateTime` holds the ISO date, and a page that shows dates says « Heures de Paris. » once.
- **Buttons.** `default` for what a form is for, such as « Ajouter » or « Réessayer »; `outline` for « Retirer »; `ghost` for « Se déconnecter » and « Se reconnecter ». The MVP uses no `destructive`, whose red text on its own tint misses 4.5:1 (#70). Removing a blocked word asks for no confirmation: adding it back undoes it, and the audit log keeps both.
- **Forms.** A form's client leaf calls `useActionState` with `null` as its initial state, and hands `state` and `pending` to a component whose output follows from its props alone. That component always renders two regions, empty for `null`: a `role="status"` one with the message of `{ ok: true }`, and a `role="alert"` one, which the field points to through `aria-describedby`, with the message of `{ ok: false }`. They exist before their text does, since a live region inserted with its text already in is announced unreliably (inferred, not checked with a screen reader). The submit button is `disabled` while `pending`; a lone form's button then reads a noun with an ellipsis, such as « Ajout… ». A list has one client leaf, which takes the items as props and hands them, with `state` and `pending`, to the list's component, and one pair of regions, outside its items, since an item's leaf would leave with it once a removal lands; each item keeps its own form, such as « Retirer » with a hidden `word` field. While one is pending, every « Retirer » is `disabled` and the status region reads « Retrait en cours… ».
- **Keeping what was typed.** React resets a `<form action>` on every submission, a failed write included, once the commit has updated the DOM (`node_modules/react-dom/cjs/react-dom-client.development.js:9326-9344`, `:16128-16129`, react-dom 19.3.1). So a failed write hands back each field as typed (**Write results**), and the field takes it as its `defaultValue`. The reset should then put the word back after a failure and empty the field after a success: that is inferred from the order above, and the blocked-word flow of **End to end** checks it.
- **Errors in forms.** An action that throws under `useActionState` rejects its state, which React throws again while rendering (`react-dom-client.development.js:8832-8845`, `:8948-8966`), so `error.tsx` takes it like a failed read.
- **No browser validation.** No `required`, `maxLength` or `pattern`: the browser would show its own bubbles instead of the domain's French message, and `maxLength` would silently cut a pasted word. The domain is the one validator (**Errors**). Nothing is built to work without JavaScript.
- **Suspense fallbacks** are a French text naming what loads, such as « Chargement des mots interdits… », in a `role="status"` element, with no skeleton and no spinner. An empty list says so in one sentence, such as « Aucun mot interdit pour l’instant. ».
- **Accessibility.** WCAG 2.2 AA (https://www.w3.org/TR/WCAG22/, Recommendation of 2024-12-12, read 2026-10-24), in light and in dark: text at 4.5:1 (1.4.3), and at 3:1 against adjacent colors what identifies a control and its state, such as an input's border or the focus indicator (1.4.11). #70 brings `nova`'s values up to it, and **Testing** proves it (**The theme**, **End to end**).
- **Accessibility lint.** `eslint.config.mjs` adds the rules of `eslint-plugin-jsx-a11y`'s `recommended` config after `eslint-config-next`'s configs (**Gotchas**), so they take its severities: error for all but the three it turns off, the six `eslint-config-next` sets as warnings included (`node_modules/eslint-config-next/dist/index.js:176-191`). #55 may revisit the severity.

## Security

How the panel protects the staff's session, its secrets and its writes, and how it reads its configuration, as Gilles decided while grilling #51 on 2026-10-24. Like **Architecture**, it was written before the code: #59 sets up the configuration, Discord's variables and `server-only`, #10 the staff's variables, the session and the login, #63 `E2E_TEST_PROXY`, #76 the headers, and #9 what lives in Vercel's dashboard. The options set aside, and why, are in #51's decisions.

- **The session** is a cookie that iron-session 9 seals, encrypted and signed, holding only the member's Discord ID (ADR 0005); no session lives on the server, since the panel stores nothing (ADR 0004). Auth.js and Better Auth are set aside: each brings its own OAuth flow, which would replace `DiscordOAuth` and the two Route Handlers. It is named `__Host-session`, with `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/`, in development too, since Chromium takes a `Secure` cookie on `http://localhost` (inferred, not tried). `Lax`, not `Strict`: the return from Discord to `/login/callback`, and a link to the panel clicked in Discord, are navigations that start on another site, which a `Strict` cookie skips. `vercel.app` is on the Public Suffix List (https://publicsuffix.org/list/public_suffix_list.dat, line 16331, read 2026-10-24), so another Vercel project is another site, which can neither set the panel's cookies nor send them on a POST; `__Host-` costs nothing, and would matter under a domain of the panel's own. iron-session 9.0.1 needs Node `>=22.13.0` and is ESM only (`npm view iron-session`, 2026-10-24).
- **Its lifetime** is 7 days from the login, written into the seal's `ttl` and the cookie's `Max-Age`, and never extended: a Server Component cannot set a cookie (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md:81`), so extending it would mean writing the cookie from `proxy.ts` or from every Server Action. A session ends when it expires, through « Se déconnecter », or, for every member at once, when `SESSION_SECRET` changes. None can be revoked on its own (iron-session 9.0.1's README, « How to invalidate sessions? », `npm view iron-session readme`, 2026-10-24): the staff check on every request is what cuts a member's access (ADR 0005), so a stolen cookie is worth at most 7 days, and only while its member holds the staff role.
- **OAuth2.** `/login` draws 32 random bytes as the `state`, in base64url, keeps them in a `__Host-oauth-state` cookie with `HttpOnly`, `Secure`, `SameSite=Lax` and a `Max-Age` of 10 minutes, and sends `prompt=consent`: Discord documents no default for `prompt`, and `none` would send a member who clicks « Se reconnecter » back as the same account (https://docs.discord.com/developers/topics/oauth2, modified 2026-10-16). The callback compares the `state` in constant time, deletes its cookie whatever the outcome, and goes to `/login/failed` when it is missing or differs, so of two logins started in two tabs, only the later one can succeed, and only if it returns first. A login always lands on `/`, with no return path in the URL, so no redirect is open. PKCE with S256, which Discord's metadata lists (`code_challenge_methods_supported`, https://discord.com/.well-known/oauth-authorization-server, read 2026-10-24) but its OAuth2 page does not document, stays only if #10's trial shows Discord refusing a wrong `code_verifier`; `state` stays either way, since RFC 9700 relies on PKCE against CSRF only once the server is known to support it (§4.7.1). The member's token is not revoked after `/users/@me`: it never leaves the callback's memory, and revoking it would revoke every token of that authorization (the OAuth2 page), for one more call and one more failure. `iss`, which Discord has returned since 2026-10-14 (https://docs.discord.com/developers/change-log), goes unchecked: Discord advises the check for a client of several providers.
- **CSRF.** Nothing beyond what Next.js and the `Lax` cookie give: no token, and no `serverActions.allowedOrigins`. A Server Action takes only POST, and its `Origin` must match `Host` (`node_modules/next/dist/docs/01-app/02-guides/data-security.md:548-550`). A POST without `Origin` passes with a warning (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverActions.md:13`), but a browser sends `Origin` on a POST, and a client that does not carries no session cookie (inferred). `/login` and `/login/callback` are GETs that write nothing to Discord, and `state` covers the login itself.
- **Headers.** `next.config.ts` sets, on every route, a Content Security Policy without nonces (ADR 0006), `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests`, with `'unsafe-eval'` added to `script-src` in development only (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md:548`), and `upgrade-insecure-requests` kept to production if #76 finds that it breaks a page served on `http://localhost`; then `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`, and `poweredByHeader: false`. HSTS is Vercel's: `max-age=63072000; includeSubDomains; preload` on `*.vercel.app` (https://vercel.com/docs/cdn-security/encryption, updated 2026-09-15). Since scripts may run inline, React's escaping is the defense against XSS, and `react/no-danger` and `react/jsx-no-script-url` are errors. The Vercel Toolbar, on by default on previews, is turned off there (#9), so previews serve production's policy rather than one opened to `vercel.live` (https://vercel.com/docs/vercel-toolbar/managing-toolbar, updated 2026-08-11).
- **Rate limiting.** One rule of the Vercel Firewall, the only one Hobby allows per project (https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting, updated 2026-08-28), set in the dashboard by #9: every path, keyed on the IP, 600 requests over a fixed window of 10 minutes, then deny. A Hobby project past an included limit waits 30 days (https://vercel.com/docs/plans/hobby, updated 2026-09-14), and a function invocation counts "regardless of request success or failure" (https://vercel.com/docs/functions/usage-and-pricing, updated 2026-06-16), so a script from one IP could take the panel down; traffic the Firewall denies counts toward no usage (https://vercel.com/docs/vercel-firewall/vercel-waf/usage-and-pricing, updated 2026-06-16). Attack Mode, free on every plan, answers a flood from many IPs (https://vercel.com/docs/vercel-firewall/attack-mode, updated 2026-08-11). The panel's code limits nothing: a write needs a session whose member holds the staff role, and Discord's 429 is handled (**Retries**).
- **Secrets.** Only `NEXT_PUBLIC_` variables reach the browser (`node_modules/next/dist/docs/01-app/02-guides/environment-variables.md:156-164`), and the panel has none. Every module that reads a secret from `process.env` or calls Discord starts with `import "server-only"`, so a client component that reaches it fails the build. Next.js resolves `server-only` itself (`node_modules/next/dist/docs/01-app/01-getting-started/05-server-and-client-components.md:602`), but Vitest does not, and the package's default entry throws, only its `react-server` condition leading to an empty module (`npm view server-only exports`, 2026-10-24): `server-only` is a dependency, and `vitest.config.mts` aliases it to that empty module. React's taint APIs stay off, being experimental (`node_modules/next/dist/docs/01-app/02-guides/data-security.md:219-236`).
- **CI secrets.** `ci.yml` holds none. "Shor Panel Dev"'s token may become a secret of a GitHub environment of its own once #57 runs the contract suite in CI: it holds only Manage Server and View Audit Log, on Gilles' test Discord server (#10, comment of 2026-10-23), and the repository is private (**Feedback loops**).
- **Configuration.** Each folder validates its own variables with zod, in a module without `server-only` that exports a function parsing the environment it is given. The folder's factories call it on `process.env` when they first run, in development as in production, and a failed parse is then a panel error (**Four kinds of failure**). When `VERCEL` is set, `next.config.ts` also calls every folder's at build, so a missing or invalid variable fails the build and Vercel keeps the previous production deployment: "Your production domains don't serve a deployment until a production deployment succeeds" (https://vercel.com/docs/deployments/environments, updated 2026-09-17). Next.js loads `.env*` before `next.config.ts` (`node_modules/next/dist/server/config.js:1263`), and Vercel gives a project's variables to its build (https://vercel.com/docs/environment-variables, updated 2026-09-17). Elsewhere the build checks nothing, since `pnpm typecheck` loads `next.config.ts` too (**Gotchas**): a fresh clone or a worktree, without `.env.local`, still typechecks and builds, and `ci.yml` needs no placeholder values. A failed parse's message names the variable, never its value: zod 4 leaves the input out of its issues (https://zod.dev/error-customization, read 2026-10-24), and the panel turns on no `reportInput` and adds no error map that would put it back.
- **Variables.** `src/discord/` reads `DISCORD_CLIENT_ID`, `DISCORD_CLIENT_SECRET` and `DISCORD_REDIRECT_URI` for `DiscordOAuth`, and `DISCORD_BOT_TOKEN` and `DISCORD_GUILD_ID` for `DiscordApi`; `src/staff/` reads `STAFF_ROLE_ID` and `SESSION_SECRET`; `src/monitoring/` reads `ALERT_WEBHOOK_URL`, and Vercel's `VERCEL_ENV` and `VERCEL_GIT_COMMIT_SHA` (**Monitoring**); `next.config.ts` reads `E2E_TEST_PROXY`. IDs are snowflakes of 17 to 20 digits (inferred from Discord's 64-bit IDs). `DISCORD_REDIRECT_URI` is a URL, `https:` except on `localhost`, set per environment; login on previews is #57's. `SESSION_SECRET` holds at least 32 characters (the same README, `password`). `ALERT_WEBHOOK_URL` is a URL under `https://discord.com/api/webhooks/`, required when `VERCEL_ENV` is `production` and left unset elsewhere, where `Monitor` only writes to the console. `VERCEL_ENV` and `VERCEL_GIT_COMMIT_SHA` are system variables, which Vercel sets once the project exposes them (#9), so they are absent outside Vercel and stay out of `.env.example`. The others are non-empty. `DISCORD_BOT_TOKEN` and `DISCORD_GUILD_ID` take Discord's names, as `src/discord/` does (`docs/agents/domain.md`): Discord files that token under its application's Bot tab and sends it as `Authorization: Bot`, though the docs call it the panel's application token (ADR 0003). `STAFF_ROLE_ID` names one role until `docs/agents/open-questions.md` says whether others make a member staff. `E2E_TEST_PROXY` is absent or `1`, and the build refuses it when `VERCEL` is set, as Vercel does at build and at runtime (https://vercel.com/docs/environment-variables/system-environment-variables, updated 2026-07-15) once the project exposes its system variables, which #9 checks. `.env.example` lists them all but Vercel's two, empty, and the README documents each one as the code that reads it arrives.

## Monitoring

What the panel logs, what it never logs, and how its maintainer learns that it broke, as Gilles decided while grilling #50 on 2026-10-24, with everything kept free. Like **Architecture**, it was written before the code: #78 writes `src/monitoring/` and `instrumentation.ts`, #59 gives `DiscordError` its route's pattern, #10 makes the login callback report what it catches, and #9 sets the webhook's variable in Vercel's dashboard. The options set aside, and why, are in #50's decisions.

- **Logs and the audit log.** Logs say why the panel failed, for whoever maintains it; the audit log says which staff member changed what (`GLOSSARY.md`, ADR 0004). So logs hold failures only: no staff action and no success, neither a write that lands, which Discord's audit log records with the panel's reason, nor a login.
- **What is logged.** Next.js prints every error thrown in a render, a Server Action or a Route Handler itself, through `console.error`, before it calls `onRequestError` (`node_modules/next/dist/server/route-modules/route-module.js:320-327`), with its message, its stack and its enumerable properties, `digest` included (`node_modules/next/dist/server/patch-error-inspect.js:437-442`); `redirect()` and `notFound()` never get there (`node_modules/next/dist/server/app-render/create-error-handler.js:52`, `:68-71`). The panel adds no line to those. An error of `proxy.ts` reaches `onRequestError` another way, with no such `console.error` on it (`node_modules/next/dist/build/templates/middleware.js:108-118`): if #78 finds that Next.js prints nothing for it further up, the panel writes that line. Beyond that, the panel writes only what the login callback catches, since the callback throws nothing (**Error pages**): a panel error at `error`, Discord unavailable and a missing or differing `state` at `warn`. Refused input and refused access leave nothing, nor does a write that returns `{ ok: false }` because Discord is unavailable, nor a 429 retried with success. `info` and `debug` go unused.
- **What is never logged**, nor sent in an alert: a secret, such as `DISCORD_BOT_TOKEN`, `DISCORD_CLIENT_SECRET`, `SESSION_SECRET` or `ALERT_WEBHOOK_URL`; a member's OAuth2 token; the callback's `code` and `state`; a cookie, or the `Authorization` and `Cookie` headers; a member's Discord ID, name or IP, since the panel stores no personal data (ADR 0004); and what the staff typed, such as a blocked word. A member who reports a failure names themself in the staff's channel. That is why a `DiscordError` carries its route's pattern, never the path filled in (**`DiscordError`**).
- **Log lines** go through `console.error` and `console.warn`, called with the error object as Next.js does, with no logging library and no JSON. Vercel's own pages disagree on whether the fields of a JSON line are searchable (https://vercel.com/docs/logs/runtime, updated 2026-08-28, against https://vercel.com/kb/guide/add-structured-application-logs-to-vercel-functions, updated 2026-05-28), and Hobby keeps runtime logs one hour (the first page), so the alert carries what matters.
- **Alerts.** Every panel error notifies Gilles, the maintainer, alone, and stays findable for at least 7 days; Discord unavailable notifies no one, since it passes. The staff get no alert: they report what they see in their channel (**Messages**), `error.tsx` with its reference, or `/login/failed`, which shows none. Alerts go through a Discord webhook into a private channel of Gilles' test Discord server (#7): it is free, needs no other account, and the panel writes every word it sends. Discord keeps a channel's messages with no expiry, which covers the 7 days (inferred, not checked against Discord's docs). Executing a webhook is a call to Discord's REST API (ADR 0003), and the one call to Discord outside `DiscordApi` and `DiscordOAuth` (**The Discord seam**). Nothing is grouped: ten failing pages send ten messages, and an alert sent during a Discord outage is lost.
- **What an alert says**, in English like the logs (**Language**): the environment and the short commit, from `VERCEL_GIT_COMMIT_SHA`; the context's `routeType` and `routePath`, the route's file path (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/instrumentation.md:109`); the `digest`, when there is one; the error's name and message; for a `DiscordError`, its method, its route's pattern, its status, and Discord's `code` and `message`; then the start of the stack, cut to Discord's limits of 2,000 characters of `content` (https://docs.discord.com/developers/resources/webhook, modified 2026-06-25) and 6,000 across embeds (https://docs.discord.com/developers/resources/message, modified 2026-10-06). Never `request.path`, which holds the query string (`instrumentation.md:103`), and so the callback's `code` and `state`, nor anything else **What is never logged** names. It goes with `allowed_mentions: { parse: [] }`, so that no error text mentions anyone, where a webhook's default parses users (the message page). It holds no time of its own: Discord shows when the message arrived.
- **Sending.** An alert never changes what the staff see. Next.js awaits `onRequestError` before it answers a Route Handler or an error that escapes a render (`node_modules/next/dist/build/templates/app-route.js:338`, `node_modules/next/dist/build/templates/app-page-runtime.js:1602`), but not for an error thrown while streaming (`create-error-handler.js:125`), and `after()` is documented for Server Components, Server Functions, Route Handlers and `proxy.ts` only (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md:8`). So the alert runs in the background, gives up after 2 s through `AbortSignal.timeout`, and never throws: a failed send is one `console.error` line. It is never retried, a 429 included: in a burst the same error repeats, so the first alerts carry it (inferred). Discord gives no figure for the rate limit of webhooks (https://docs.discord.com/developers/topics/rate-limits, modified 2026-02-06). How the send outlives the response on Vercel is #78's to check, with `waitUntil` from `@vercel/functions` as the candidate (3.10.3, `node >= 20`, `npm view @vercel/functions`, 2026-10-24).
- **`src/monitoring/`** sits outside the domain, like `src/discord/` and `src/ui/`. It exposes `Monitor`, one method per level, which `createMonitor()` builds: `error` writes the line and sends the alert, `warn` writes the line only. `isPanelError` tells whether a thrown error alerts: a `DiscordError` that says Discord is unavailable does not, anything else does. `src/instrumentation.ts` only wires: its `onRequestError` hands the error and its context to `src/monitoring/`, which sends the alert when `isPanelError` says so, and writes no line, since Next.js has written it. The login callback's domain function takes a `Monitor`, as it takes `DiscordApi` and `DiscordOAuth`. `src/monitoring/` calls `fetch`, taken as a parameter like **The real implementations**, and reads `ALERT_WEBHOOK_URL` (**Variables**), behind `import "server-only"` (**Secrets**). An in-memory `Monitor` serves the tests, and the `no-restricted-imports` rule that keeps the fake Discord in `*.test.*` files (**The Discord seam**) refuses it elsewhere too.
- **Stacks** stay as Next.js builds them, minified, since `experimental.serverMinification` defaults to `true` (`node_modules/next/dist/server/config-shared.js:203`): the panel adds neither `serverSourceMaps` nor `--enable-source-maps`. The message, the route and a `DiscordError`'s fields place most failures in a panel this small. This is revisited when a stack proves unreadable.
- **No uptime probe.** The failures that matter, such as a revoked token or a removed permission, show only when a page reads Discord, so when the staff use the panel, and the alert fires then. A failed deployment notifies its creator, on the web and by email, by default on every plan (https://vercel.com/docs/notifications, updated 2026-09-14), and Vercel keeps the previous production deployment (**Configuration**).
- **The browser reports nothing.** Client leaves hold no logic (**Components**), an action's error is thrown on the server before the browser sees it, and `connect-src` stays `'self'` (**Headers**).

## Code style

How the code is laid out, named and typed, as Gilles decided while grilling #48 on 2026-10-24. Like **Architecture**, it was written before the tooling: #80 set up Prettier as described below, and #81 sets up the lint rules and `erasableSyntaxOnly`. It lives here rather than in a `CODING_STANDARDS.md`, since code-review reads every file that documents how code is written (its `SKILL.md:36`, mattpocock/skills 1.3.1). The options set aside, Biome, oxfmt and ESLint Stylistic among them, and why, are in #48's decisions.

- **Prettier lays out** every file it knows: TypeScript, JavaScript, CSS, JSON, YAML and Markdown. It and the two plugins below are devDependencies, `prettier.config.mjs` is the source of truth for layout, and `.prettierignore` keeps out `pnpm-lock.yaml` and `.claude/skills/groom-backlog/`, the copy shared with EsportCards, which commit e885352 means to differ only by `config.json`. ESLint stays the linter and sets no layout rule (`pnpm exec eslint --print-config src/app/page.tsx`, 2026-10-24), so no `eslint-config-prettier`.
- **shadcn/ui's style.** Prettier's defaults with `semi: false` and `trailingComma: "es5"`, which are the registry's own: with them and the two plugins below, Prettier 3.9.10 leaves `src/ui/button.tsx` and the sources of 20 base-nova components unchanged (run on scratch copies of https://ui.shadcn.com/r/styles/base-nova/<name>.json, 2026-10-24). `shadcn add --diff` compares lines (`diffLines`, `node_modules/shadcn/dist/index.js:121`), so this style keeps it to the lines the panel changes (**Copied code**), where single quotes would add every line that holds a string. The width stays 80: at 100, Prettier changes 287 lines across 15 of those 20 components.
- **Classes** are sorted by prettier-plugin-tailwindcss, in Tailwind's recommended order, against `src/ui/globals.css`, in `className` and inside `cva()` and `cn()` calls. It drops duplicate classes and extra whitespace by default, and loads last among Prettier's plugins (https://github.com/tailwindlabs/prettier-plugin-tailwindcss, README, read 2026-10-24).
- **Imports** are sorted by `@ianvs/prettier-plugin-sort-imports`, in the registry's order: `node:` modules, `react`, `next`, other packages, then, after a blank line, `@/` and relative paths. A side-effect import stays where it is and the imports after it are sorted, so `import "server-only"` stays first (**Secrets**; tried on a scratch file, 2026-10-24).
- **Copied code** stays as `shadcn add` wrote it but for two kinds of line, which `--diff` then shows. Prettier reformats what the CLI's own transforms leave unformatted: its icon transform writes an icon's JSX over two lines and its `lucide-react` import after the `@/` ones, so 3 to 8 lines change in each of `combobox`, `dialog`, `select` and `sheet` (`pnpm exec shadcn add <name> --dry-run --view`, 2026-10-24). A line a lint rule refuses carries an `eslint-disable-next-line` for that rule; of the 20 components, only `sonner` asserts types, twice.
- **Enforcement.** `pnpm format:check` runs in CI, right after the comment check, and a `PostToolUse` hook of `.claude/settings.json` on `Edit|Write`, `.claude/hooks/format-after-edit.mjs`, formats the file the tool touched; those two are the whole of it, with no git hook and no editor setting. The hook calls Prettier from the project's root, since Prettier resolves a plugin's package name from the working directory (`loadPlugin`, `node_modules/prettier/index.mjs:18619-18624`). It leaves alone a file outside the project, one that `.gitignore` or `.prettierignore` lists, and one Prettier does not know, and exits 2 on a file Prettier cannot parse, so that Claude reads why (`test/format-after-edit.test.mjs`). It never sees what a `Bash` command rewrites, such as `pnpm add` or `shadcn add`: `pnpm format` and CI catch that. Code that Prettier lays out badly gets reshaped, since `prettier-ignore` is a comment like any other (**No comments**), and `pnpm check:comments` reads `.prettierignore` and `.git-blame-ignore-revs` as files of `#` comments. #80's reformatting is a commit of its own, `Tooling: format the repository with Prettier`, whose SHA `.git-blame-ignore-revs` holds for GitHub's blame (https://docs.github.com/en/repositories/working-with-files/using-files/viewing-and-understanding-files, read 2026-10-24), and `git blame` too once `blame.ignoreRevsFile` points to it (README). A merge commit keeps that SHA (**Commits, PRs, issues**); a rebase of a reformatting branch before its merge redoes the file with the new one.
- **Names.** Files and folders are kebab-case, as in Next.js's file conventions (`not-found.tsx`, `global-error.tsx`) and shadcn/ui's registry (`alert-dialog.tsx`, `dropdown-menu.tsx`). Outside the files whose names Next.js sets, a component lives in the file named after it: `blocked-word-list.tsx` exports `BlockedWordList`, beside `blocked-word-list.test.tsx`. Values and functions are camelCase; components, types and classes PascalCase; a module-level constant that holds fixed data SCREAMING_SNAKE_CASE, such as `DIRECTIVES` in `scripts/check-comments.mjs`, while other `const`s stay camelCase. An acronym is a word, `DiscordApi`, `userId`, `webhookUrl`, but for `OAuth`, as in `DiscordOAuth`, and a type takes no `I` prefix. The terms come from `GLOSSARY.md`, but in `src/discord/` (`docs/agents/domain.md`). Review checks names, since `@typescript-eslint/naming-convention` would need an exception for components; a slip that review misses becomes a check.
- **Exports** are named and written inline, `export function …`, while a copied component keeps the registry's `export { … }` at its end. A default export lives only where Next.js or a tool requires one, the files of `src/app/` and config files, the only ones `import/no-default-export` lets through. An import names the module itself, such as `@/blocked-words/add-blocked-word`, and review checks that no barrel sits in between: a barrel that re-exports a client leaf beside a `server-only` module would pull that module into the client graph (inferred, not tried).
- **TypeScript.** `type` for every object type, `import type` for what is imported as a type only, and `as const` as the one type assertion, except on the line that mints the `StaffMember` brand (ADR 0005), which carries an `eslint-disable-next-line`. Lint rules enforce the three at `error`, the severity #55 may revisit, and refuse nothing in the code of 2026-10-24 (`pnpm exec eslint --rule …`). The syntax stays erasable, with no `enum`, `namespace` or parameter property, which `erasableSyntaxOnly` refuses; `tsc --noEmit --erasableSyntaxOnly` passes today.
- **Module size** is a judgement call: a module holds one idea, with no figure and no `max-lines`, and code-review's smells, Divergent Change and Shotgun Surgery, watch it.

## Feedback loops

- Tests: `pnpm test` runs the tooling's tests, `node --test` over `test/**/*.test.mjs`, then the panel's, Vitest over `src/**/*.test.{ts,tsx}`. Vitest runs in Node, without a DOM: a test renders a component with `react-dom/server`, as the server does. One file: `node --test test/<name>.test.mjs` or `pnpm exec vitest run <path>`. No test of `pnpm test` calls the real Discord: an in-memory fake replaces it (**Testing**).
- Typecheck: `pnpm typecheck` runs `next typegen`, which writes what a fresh clone lacks, the gitignored `next-env.d.ts` and the route types behind `PageProps` and `LayoutProps`, then `tsc --noEmit`.
- Lint: `pnpm lint`, ESLint with `eslint-config-next`'s Core Web Vitals and TypeScript configs, then the rules of `eslint-plugin-jsx-a11y`'s `recommended` config and a `no-restricted-imports` that refuses, in `src/ui/`, any relative import and any `@/` import but `@/ui/*` (**Interface**), over the whole repo.
- Build: `pnpm build` (`next build`), which type-checks again. Dev server: `pnpm dev`.
- Comments: `pnpm check:comments`.
- Format: `pnpm format` lays out the repository with Prettier, `pnpm format:check` checks that it is laid out (**Code style**). One file: `pnpm exec prettier --write <path>`.
- Components: `pnpm exec shadcn add <component>` copies a shadcn/ui component into `src/ui/`, as `components.json` sets, and installs the packages it needs: read `pnpm-workspace.yaml` after (**Gotchas**). Then strip its comments and turn its English strings French (**Interface**, **Copied code**). `pnpm exec shadcn add <component> --diff` shows how a copied file differs from the registry's.
- CI: `.github/workflows/ci.yml` runs the comment check, the format check, the typecheck, the lint, the tests and the build. It is advisory: branch protection and rulesets are refused on this private repository of a free organization (HTTP 403 « Upgrade to GitHub Pro or make this repository public », checked 2026-10-23). Never merge a PR whose CI is red.

## Commits, PRs, issues

- Commit messages read `Area: what changed`, in English.
- The user is the sole author: commits carry no `Co-Authored-By` trailer, PRs carry no "Generated with" footer.
- Only the maintainer, Gilles (`docs/agents/issue-tracker.md`, **People**), merges into `main`, with a merge commit, never a squash. Vercel's Hobby plan has no team collaboration, and its forum reports blocked deploys when a private repo's commit author is not the owner's linked GitHub account; this is to be confirmed at the first deploy.
- Issues, PR descriptions and comments read like a teammate wrote them: direct, specific, complete, no filler.
- A PR that only advances a ticket names it once, as `Part of #<n>`. GitHub closes, at merge, every issue that a PR description or commit message puts right after `close`, `fix` or `resolve` (any form), even inside a negation.
- Once a PR merges, delete its local branch with `git branch -d` and run `git fetch --prune`. When `-d` refuses, the branch holds unmerged work: ask the user.

## Gotchas

- `@babel/parser`, which the comment check uses, stays on 7.x: 8.x requires Node `^22.18.0 || >=24.11.0` (`npm view @babel/parser@8 engines`, 2026-10-23), narrower than the `^22.13.0 || ^24.0.0 || >=26.0.0` that `engines` promises in `package.json`. CI would not catch the gap: its `node-version: 22` ran Node 22.23.3 on 2026-10-23 (run 39944674281), which 8.x accepts.
- `engines.node` is the intersection of the ranges the toolchain declares: Vitest 5 wants `^22.12.0 || ^24.0.0 || >=26.0.0`, ESLint 10 `^20.19.0 || ^22.13.0 || >=24` (`npm view <package> engines`, 2026-10-23). Read a new dependency's `engines` before adding it: jsdom 30, for one, wants `^22.22.2 || ^24.15.0 || >=26.0.0`.
- `typescript@7` on npm is the native compiler: its package exports no stable JavaScript API (only `./unstable/*`), so tooling that parses code cannot rely on it. That is why the comment check parses with Babel, and why TypeScript stays on `~6.0.3`: typescript-eslint, which `eslint-config-next/typescript` uses, accepts `typescript >=4.8.4 <6.1.0` (8.72.0, `npm view typescript-eslint peerDependencies`, 2026-10-23). Next.js alone would accept 7, through its `tsc` CLI (https://nextjs.org/docs/app/api-reference/config/typescript, updated 2026-08-25).
- ESLint is on 10, since 9.x reached end-of-life on 2026-08-06 (https://eslint.org/version-support, read 2026-10-23). `eslint-config-next` supports 10 since 16.4.0 (https://nextjs.org/docs/app/api-reference/config/eslint, updated 2026-10-15), but three plugins it bundles, `eslint-plugin-import`, `eslint-plugin-jsx-a11y` and `eslint-plugin-react`, still cap their `eslint` peer at `^9`: hence the `peerDependencyRules` of `pnpm-workspace.yaml`. Drop each rule once its plugin lists 10.
- pnpm 12 refuses a version published less than a day ago (`minimumReleaseAge`), and `pnpm add` of such a version writes it into `minimumReleaseAgeExclude` in `pnpm-workspace.yaml` without asking. On 2026-10-23, `pnpm add` reported doing so for Next.js 16.4.3, on npm since 13:40 UTC that day (`npm view next time`), so the panel stayed on 16.4.2. Read `pnpm-workspace.yaml` after every `pnpm add`.
- `eslint-plugin-jsx-a11y`'s `flatConfigs.recommended` registers a plugin object other than the one `eslint-config-next` registers, and ESLint 10.13.0 refuses the pair: « Cannot redefine plugin "jsx-a11y" » (2026-10-24). So `eslint.config.mjs` takes only its `rules`, on the files `eslint-config-next` registers the plugin for. A rule given only a severity keeps the options set before it, such as `alt-text`'s `img: ["Image"]` (`pnpm exec eslint --print-config src/ui/button.tsx`).
- `import/order`, from the `eslint-plugin-import` 2.32.0 that `eslint-config-next` bundles without turning the rule on, crashes on ESLint 10.13.0 once it has an import to reorder: `pnpm exec eslint --rule '{"import/order":["error",{"alphabetize":{"order":"asc"}}]}' .` stops on `.claude/skills/groom-backlog/scripts/backlog.mjs` with « TypeError: sourceCode.getTokenOrCommentBefore is not a function », while `{"import/order":"error"}` finds nothing to reorder and passes (2026-10-24). Imports are sorted by Prettier instead (**Code style**).
- In flat config, the last object that sets a rule for a file replaces its options instead of adding to them: a `no-restricted-imports` added for `src/**` drops the `src/ui/` patterns on `src/ui/` files (`eslint --print-config`, 2026-10-24). A new rule of the same name that reaches `src/ui/` repeats those patterns.
- `shadcn init --preset nova` (shadcn 4.22.1, 2026-10-24) also wrote the button to `src/components/ui/`, a `src/lib/utils.ts`, Geist through `next/font/google` in `src/app/layout.tsx`, and `--font-sans`, `--font-heading` and `html { @apply font-sans }` in `globals.css`; #67 undid them. `shadcn add button` then left `globals.css` alone. Running `init` again, for a new preset say, would presumably redo them: inferred, not tried.
- `next typegen`, and so `pnpm typecheck`, loads `next.config.ts` in the build phase (`node_modules/next/dist/cli/next-typegen.js:83`): whatever `next.config.ts` checks at build also runs at every typecheck.
- `next dev` writes an `AGENTS.md` for the coding agent it detects unless `next.config.ts` sets `agentRules: false` (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/agentRules.md`). The docs it would point to, which match the installed Next.js, are in `node_modules/next/dist/docs/`.
- The hooks of `.claude/settings.json` need `pnpm install` first: without `node_modules`, the comment check cannot run and `gh pr create` is refused, and the format hook cannot load Prettier, which shows as a non-blocking hook error after each `Edit` or `Write`.
- The API can show Auto-add to project `enabled` while it adds nothing: its filter, which the API hides, once held a stray `label:`. Only an issue that `github-project-automation` puts on the board proves it works (`docs/agents/issue-tracker.md`, **Board workflows**).
- Writes to the project board need gh's `project` scope; `read:project` only lets `backlog.mjs plan` read it. When `apply` fails on a missing scope, run `gh auth refresh -s project`, which opens a browser.
- Several sessions can share this folder. On 2026-10-23, one session's `git switch -c` took the folder off the branch another session was working on, under its uncommitted changes (`git reflog`). Before switching branches here, read `git status` and `git reflog -3`; a change that needs its own branch goes in a `git worktree`.
- A browser tab of the project board keeps its own copy of the views in `sessionStorage` (`projects-v2/session-store-v1/…/memex-views`), which survives F5. On 2026-10-23, a tab opened between two view changes kept showing the older grouping after a reload, while a new tab showed the saved one (inferred from the key's contents, not from GitHub's code). After a view changes, check it in a new tab.
