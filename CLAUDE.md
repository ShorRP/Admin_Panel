## How we work

The process lives in Matt Pocock's skills (`mattpocock/skills`). This file only adds what the skills can't know about this repo.

Reach for these yourself:

- **tdd** for every behaviour change.
- **diagnosing-bugs** for any bug that survives a first look: a tight loop that goes red on this bug comes before any theory.
- **domain-modeling** the moment a term is fuzzy, overloaded, or disagrees with `GLOSSARY.md`, and whenever a decision clears the ADR bar.
- **code-review** against the originating ticket before any commit that closes one.
- **groom-backlog** before your final report, when the session changed the repo or leaves loose ends, or once a burst of tracker writes is over: an issue created, edited, labelled, closed or re-parented, a PR opened or merged, work started on an issue. A hook reminds you after each write.

The orchestrating skills are run by the user. When you see the moment for one, suggest it in a single line, then carry on:

- non-trivial change, not grilled yet → `/grill-with-docs`
- grilled change too big for one session → `/to-spec`, then `/to-tickets`
- effort too foggy to scope → `/wayfinder`
- the answer lives in a teammate's head (the POs, the staff, loanspac) → `/to-questionnaire`
- an epic of `ready-for-agent` and `skill:implement` sub-tickets, to deliver without Gilles, its `ready-for-human` ones walked through with him in guide sessions → `/deliver-epic <n>`
- every `ready-for-agent` and `skill:implement` ticket of the backlog, to deliver without Gilles, one at a time in board order → `/deliver-backlog`

## Language

Three things are in **French**: chat with the user, GitHub issues and their board (title, body, comments, and the board's descriptions and view names; see `docs/agents/issue-tracker.md`), and the panel's interface, which is French only, with no translation layer. Everything else is in **English**: docs, `GLOSSARY.md`, ADRs, PR text and PR comments, commit messages, and every word written into the codebase: file names, identifiers, logs. URLs count as file names, since each segment is a folder under `src/app/`: `/blocked-words`, not `/mots-interdits`.

## No comments

The repository holds no comments, in any file that supports them: code, tests, scripts, CSS, HTML, Markdown, SQL, YAML, Python, PowerShell, `.env.example`, whose variables are documented in the README. Two exceptions only: a shebang, and a tool directive the code needs to work, which stands alone in its comment, with no text of its own, in the forms that `.claude/rules/eslint.md`, **Directives**, allows and in a script file only.

What a comment would say goes elsewhere: the why of a change in its commit message, a decision in an ADR, a term in `GLOSSARY.md`, an invariant in a test and its name. Code copied from elsewhere, such as shadcn/ui or EsportCards, loses its comments on the way in, and comes in only as its license allows (**Copying code from another project**).

`pnpm check:comments` runs in CI on every PR and every push to `main`, and a hook runs it before `gh pr create` and its alias `gh pr new`, so a comment stops the PR. What it reads and where it errs: `.claude/rules/check-comments.md`; its sources: `docs/check-comments.md`.

## Facts and docs

- **Facts apart from inferences.** Everything you write to docs, tickets or reports keeps verified facts, with their source (`file:line`, commit, URL and date, command output), visibly separate from inferences.
- **Challenge with evidence.** When the code, the docs, `GLOSSARY.md`, an ADR and the user's request disagree, name the contradiction, quote both sides, and ask which one wins. Record the answer through domain-modeling.
- **Agent decisions.** An agent running `deliver-epic` or `deliver-backlog` decides where this file or a skill says to ask Gilles: it applies the most acceptable option and records it under `Décisions de l'agent (à revoir par Gilles)` in the ticket and in the commit message, for Gilles to review; the docs' mark, `(decided by the agent on <date>, on #<n>, for Gilles to review)`, goes in a file of `.claude/rules/`, an ADR or `docs/`, never in this file.
- **Unrecoverable why.** When nothing explains a decision or a fact the work needs, append it to `docs/agents/open-questions.md`, created with its first entry: the question, where it shows up, who is likely to know, what is blocked on it.
- **Docs as you go.** Docs are updated the moment they become true, in the same change. This file holds only what every session needs, in its shortest form: a rule that matters only when touching some files goes to `.claude/rules/<area>.md`, scoped by `paths:`, a decision to an ADR, reference to `docs/` behind a pointer line, and a trial or a ticket trail to the commit message and the ticket. `GLOSSARY.md` is a glossary and nothing else; ADRs follow domain-modeling's bar. When docs contradict the code, fix them in the same change if it takes a few lines, otherwise list them in your report. A passage of this file or of `.claude/rules/` holds its rule, its why in one clause and a short source (`#n`, ADR, URL or commit); its measures and trials go to `docs/` or the commit message, and a moved passage keeps its agent decision mark.
- **Always-loaded context.** `CLAUDE.md` and the rules with no `paths:` load into every session and every sub-agent: keep them together under 20,000 bytes and 200 lines, and each rule scoped by `paths:` under 15,000 bytes. A hook tells you, right after an edit, that the budget is passed and by how much; a set already over it must not grow. Move the surplus where **Docs as you go** says, never just cut it. Delete a rule only when the code or a test already says it.
- **Scope.** Each diff stays inside its ticket. Problems you spot nearby are loose ends: groom-backlog files them as tickets.
- **Gotchas.** When a session hits a trap the environment doesn't reveal, add one line to the rule of the area it concerns, `.claude/rules/<area>.md`, and under **Gotchas** only a trap of the machine or the tooling that no path scopes. Delete lines that stop being true.

## Costs

No third party the panel relies on may ever send a bill or take a hidden fee, as Gilles decided on 2026-10-27, calling it a golden rule, as #9 was about to open the Vercel account (#123). It covers every service, account and tool the panel, its CI and its tooling use, today's and any to come. [`docs/costs.md`](docs/costs.md) says, for each, what the panel uses, why it cannot bill, what would make it bill, and what it can cost otherwise, with its sources.

- **No way to pay.** Every account the panel relies on stays on a free plan with no payment method on file, so that a limit reached blocks or pauses the service instead of billing it, as Vercel's Hobby and GitHub Free do (`docs/costs.md`). So nobody adds a payment method, starts a trial, upgrades a plan, or buys a domain, credits or an add-on, nor installs an integration or app that bills, on an account the panel relies on, not even for a free first month: a card added for one purchase may stay on file (inferred from one unofficial report, `docs/costs.md`, **Vercel**).
- **A paid plan** would reopen this rule: should the panel need one, as it would if Shor turned commercial, Gilles decides it in an ADR before anything is signed.
- **A new tool.** Before a new third party comes in, whether a service, an account, an integration, an app, or a package, an action or a registry that reaches a hosted service when it installs or runs, its entry goes into `docs/costs.md`, from its own pricing and terms: whether it asks for a payment method, what happens at each limit the panel could reach, and what would make it bill. One that needs a card before it can be used, or that bills past its free quota even without one, stays out. A package that only runs locally needs no entry, since the npm registry has its own (**Adding a dependency**). Neon, the store ADR 0004 picks after the MVP, gets its entry before its account opens, from the store's grilling (#175).
- **Agents** create no account, type no payment method, accept no trial or upgrade, buy nothing, and install no integration or app that bills, by any means: a terminal, a dashboard, an MCP server. Before Gilles takes such a step, they tell him what it costs, with its source, and they stop at a screen that asks for a card or offers a trial in place of the free plan.
- **Rechecked every month.** Free plans change: the monthly session (`.claude/rules/dependencies.md`, **Who and when**) reads again the pages `docs/costs.md` cites, and an entry whose facts moved is updated before anything else, or its service leaves (#97).

## Architecture

How a feature is written end to end, as Gilles decided while grilling #47 on 2026-10-23, then #49, #54, #52 and #50 for the lines that point to **Errors**, **Testing**, **Interface** and `.claude/rules/monitoring.md`. It was written before the code: each ticket that writes the code follows it.

- **Folders.** `src/app/` only routes: its `page.tsx`, `layout.tsx` and `route.ts` call a domain folder named after a `GLOSSARY.md` term, such as `src/staff/` (login, session, staff role), `src/blocked-words/` or `src/audit-log/`. A domain folder holds its logic, its components, its `actions.ts` and their tests. `src/discord/` is the adapter to Discord's REST API, `src/ui/` holds what the interface shares (**Interface**), and `src/monitoring/` the logs and the alerts (`.claude/rules/monitoring.md`). The error pages are the one exception (`.claude/rules/nextjs.md`, **Error pages**).
- **The Discord seam.** `src/discord/` is the adapter to Discord's REST API: `DiscordApi` and `DiscordOAuth`, one method per endpoint the panel calls, their real implementations, an in-memory fake that only tests import, and the HTTP adapter through which that fake answers end to end. `.claude/rules/discord.md`, **The Discord seam**, holds the rest.
- **Entry points only wire.** Pages, layouts, `actions.ts`, Route Handlers, `proxy.ts` and `instrumentation.ts` hold no logic of their own and never read `process.env`. Those that need Discord get the real clients from `createDiscordApi()` and `createDiscordOAuth()` and pass them on, as in `addBlockedWord(discord, staffMember, word)`; tests pass the fake instead, with no `vi.mock`. The login callback's Route Handler and `proxy.ts` pass `createMonitor()`'s `Monitor` the same way (`.claude/rules/monitoring.md`). The callback's Route Handler passes `createDiscordApi` and `createDiscordOAuth` themselves, which its domain function calls inside its `try`, so that a missing variable is a panel error it reports too, since the callback throws nothing (`.claude/rules/nextjs.md`, **Error pages**; Gilles, 2026-10-26, on #10). Only `src/discord/` reads Discord's variables, `src/staff/` the staff's, and `src/monitoring/` its own (`.claude/rules/env.md`, **Variables**). Vitest cannot render `async` Server Components (`node_modules/next/dist/docs/01-app/02-guides/testing/vitest.md:9`), so what a page does lives in functions tested directly.
- **The staff check.** Every page but the login pages under `/login`, the privacy policy at `/privacy` (#186) and the error pages, and every Server Action that writes, starts with `requireStaffMember` from `src/staff/`, and every domain write takes the branded `StaffMember` it returns (ADR 0005). The pages under `/records` start with `requireModerationAccess` instead, which runs `requireStaffMember`, then calls `notFound()` for a staff member who holds no role of `MODERATION_ROLE_IDS`, so that they see the not-found page rather than `/login/refused` (ADR 0005, #176), and so does the Server Action that changes a sanction, whose domain functions also throw for a `StaffMember` who does not moderate (#179, #180), or, for a ban or its lifting, who does not ban: `StaffMember`'s `opensBans` says whether they also hold a role of `BAN_ROLE_IDS` (#181). Like the staff check's redirects, it takes effect in the part of the page under `<Suspense>`, so the page's static shell shows first, and the response keeps its `200` (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/not-found.md:193`). The pages of `/records` follow `.claude/rules/records.md`, **The staff check**. The not-found page is the panel's own, in French (`.claude/rules/nextjs.md`, **Error pages**, #61). `/game-log` starts with `requireStaffMember` too, then `notFound()`s a staff member who does not view its channel on Discord, as `canViewChannel` works it out (**Channel visibility**; `.claude/rules/game-log.md`, #394), and `/bot-log` does the same for the Bot's channel (`.claude/rules/bot-log.md`, #396). `requireStaffMember` never returns a failure: it redirects to `/login` without a readable session, and to `/login/refused` a member who is not on the Discord server or lacks the staff role. The login callback, which has no session yet, runs the same check by Discord user ID and redirects itself (ADR 0005). It uses `redirect` rather than `forbidden()`, which needs `experimental.authInterrupts` (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/forbidden.md:17`) and gives a Route Handler an empty body (`node_modules/next/dist/server/route-modules/app-route/module.js:259-263`).
- **Channel visibility.** `canViewChannel(discord, staffMember, channelId)`, in `src/staff/can-view-channel.ts`, says whether a staff member views a channel of the Discord server, as Discord does, from the roles the staff check read in the `StaffMember`, the Discord server's owner and roles, and the channel's permission overwrites, in the order of the pseudocode of https://docs.discord.com/developers/topics/permissions (read 2026-11-05, #384): the owner views every channel; a staff member's base permissions are @everyone's role with the permissions of each role they hold, and with Administrator among them they view every channel; then the channel's overwrite for @everyone applies, its denies removed and its allows added, then the allows and denies of the staff member's roles, taken together, denies removed first, then the staff member's own overwrite, the same way, and the channel is viewed when View Channel is left. A timed-out staff member is computed like any other, since a timeout leaves View Channel (the same page, "Permissions For Timed Out Members": "Timed out members will temporarily lose all permissions except VIEW_CHANNEL and READ_MESSAGE_HISTORY"). An overwrite is matched by its ID alone, as the pseudocode does. The function reads a channel's own overwrites and never its category's, because Discord does: "Rather than inheritance, permissions are calculated by means of what we call Permission Syncing" (the same page), a child channel is synced to its category when it holds "the same permissions and overwrites", and changing the child de-syncs it. A deny on a category reaches a channel only as the overwrites the channel holds itself, copied from it while it was synced, and a channel de-synced from a category that denies is viewed or hidden by its own overwrites, which `src/staff/can-view-channel.test.ts` proves in both directions, so that the panel never shows a staff member more or less than Discord. #384 and the epic #380 word it as « surcharges de la catégorie et du salon », which assumes an inheritance that Discord's page does not describe (decided by the agent on 2026-11-05, on #384, for Gilles to review). A category is a channel like any other: asked for its own ID, the function computes from its own overwrites. It reads the Discord server and the channels once each, through `getGuild` and `listChannels`; `viewsChannel(guild, channel, staffMember)` is the same computation over what a caller has already read, which `canViewChannel` calls, so that a page that checks a list of channels reads both once and asks `viewsChannel` for each. A channel that `listChannels` does not give is not viewed, whoever asks, since Discord stops listing the channels the application cannot view (`.claude/rules/discord.md`, **The Discord seam**), so that a channel the application cannot view reads as hidden from the staff members Discord shows it to: the application needs View Channel on each channel a page reads, and a grant on its category reaches the channel only while the channel is synced to the category (`.claude/rules/discord.md`, **The application's permissions**; inferred from the page's Permission Syncing, not tried).
- **Writes** are Server Actions, in their domain folder's `actions.ts`, marked `"use server"`, and end with `refresh()` once the write lands. Logging out is a Server Action too, which only ends the session, then sends the member to `/login/logged-out`, a static page that says so, with « Se connecter avec Discord » (Gilles, 2026-10-26, on #10; #236). Route Handlers serve OAuth2 only: `/login` and `/login/callback`.
- **Validation** uses zod 4 throughout the repo, config included. Domain functions validate what comes from the browser, such as an action's `FormData` or the callback's query string. An invalid URL parameter counts as absent. Discord's responses are typed, not validated.
- **Components** are Server Components. `"use client"` goes only on a leaf that needs browser state or events, in its domain folder, on some components shadcn/ui's CLI copies (**Interface**), and on the two error pages Next.js requires it of (`.claude/rules/nextjs.md`, **Error pages**); never on a page, a layout or anything that reaches `src/discord/`. A client leaf may hold browser state, such as `useActionState`'s, but no logic: it hands that state to a component whose output follows from its props alone (**Testing**). There are two exceptions. One is the toast of a write that lands, which the leaf that holds `useActionState` adds, through `useSuccessToast` (`.claude/rules/ui-overlays.md`, **Toasts and failure messages**; Gilles, 2026-10-29, on #227). The other is the theme a staff member chooses: `StatefulThemeToggle`, in `src/staff/`, reads it from `data-theme` through `useSyncExternalStore`, whose server snapshot is « Auto », and on a click writes it to `data-theme` and `localStorage`, or removes both for « Auto », then hands the theme and that write to `ThemeToggle`, as #225 decided (Gilles, 2026-10-29, on #225) (**Theme**).
- **Caching** (`use cache`, the static shell, `connection()`): `.claude/rules/nextjs.md`, **Caching**.
- **`proxy.ts`** sends a request without a readable session to `/login`, on every route but `/login`, everything under it, `/privacy`, which anyone reads and which reads nothing from Discord (#186), and static files: the callback opens no session for a member without the staff role, who would otherwise loop from `/login/refused` back through Discord. It authorizes nothing.
- **Imports** that leave their folder use `@/*`, mapped to `src/*`; imports within a folder stay relative, except in `src/ui/` (**Interface**). Vitest resolves the alias only with `resolve.tsconfigPaths: true`, which Vite 8.3.5 leaves off by default.

## Errors

How the panel fails, as Gilles decided while grilling #49 on 2026-10-23, then #53 for what a successful write returns. Like **Architecture**, it was written before the code.

- **Four kinds of failure.** _Refused input_: the staff entered something the panel refuses, or the Discord server is in a state they can fix in Discord, such as already holding 6 keyword rules. _Refused access_: no readable session, or not staff (**The staff check**). _Discord unavailable_: a 429 the panel does not retry or that comes back, a 5xx, a network error or a timeout, and a 202 from the search of the Discord server's messages that comes back or whose delay is over 2 s, because Discord's index is not ready (`.claude/rules/discord.md`, **Errors and retries**, #383). _Panel error_: everything else, a misconfiguration included, such as a revoked token, a missing permission or the Server Members Intent turned off, which Discord answers on the list of members with a 403 of code 50001 (#322); the staff can only report it.
- **`DiscordError`** and what `src/discord/` retries: `.claude/rules/discord.md`, **Errors and retries**.
- **Write results.** A domain write checks every limit Discord documents before calling it, so a 400 from Discord is a panel error. It re-reads what it changes right before writing and applies only its own change, with no conflict error: a form sends one word, never a list. It returns `{ ok: true, message }`, or `{ ok: false, message }` with each field the form sent, as typed and under its name, such as `word`: one French `message` per form, written by the domain, that says what landed, such as « « foo » est maintenant un mot interdit. », or what went wrong, for refused input and for Discord unavailable, and the fields so the form keeps them (**Interface**). A blocked word's write follows `.claude/rules/blocked-words.md`, **Write results**. A sanction's results follow `.claude/rules/sanctions.md`, **Write results**. Anything else is thrown, a `DiscordError` from the action's `requireStaffMember` included. Reads never write: what a page needs created, the first write creates.
- **Read failures.** What a page reads from Discord is thrown on failure, with no catch on the way, and `error.tsx` replaces the page (`.claude/rules/nextjs.md`, **Error pages**, #53). Three reads are exempt. One is a lookup of a member's avatar in the audit log, which follows `.claude/rules/audit-log.md`, **Avatars and read failures**. Another is the count of blocked words beside « Mots interdits » in the navigation, which follows `.claude/rules/blocked-words.md`, **Read failures**. The third is the count of each request kind in the pills of `/support-tickets`. The list of accounts and a record of `/records` are reads like any other, with no exemption (`.claude/rules/account-list.md`, **Reading**; `.claude/rules/records.md`, **Reading**). The ticket archives of a record, the archives of `/support-tickets` and its tickets in progress are reads like any other, but for the exemptions of `.claude/rules/support-tickets.md`, **Read failures**. The game log is a read like any other, but for its link in the navigation, which gives no link when the read of the channels throws a `DiscordError` (`.claude/rules/game-log.md`, #394).
- **Messages** are the panel's own French sentences, never Discord's message, a stack or a token. A failure's message says what to do next: correct the input, retry, or report the problem in « #créer-ticket », the channel of Shor's Discord server where the staff report a problem of the panel, which `error.tsx` and `/login/failed` name and link (`.claude/rules/ui.md`, **The report channel's link**; Gilles, 2026-10-29, on #61). A success's message says what landed (**Write results**).

## Testing

What the panel's tests prove and where, as Gilles decided while grilling #54 on 2026-10-23, then #53 for the theme and accessibility, and #50 for monitoring. Like **Architecture**, it was written before the code.

- **Layers.** Domain functions carry most of the tests, in Vitest against the fake Discord. ## Security

The lines here add to the **Security** stop of the plugin's `deliver-epic/rules.md`, under **Stops**, on which an agent running `deliver-epic` or `deliver-backlog` stops short of the action, and they hold outside a run too: an agent asks Gilles before it touches what they name. How the panel protects the staff's session, its secrets and its writes, and how it reads its configuration, as Gilles decided while grilling #51 on 2026-10-24. Like **Architecture**, it was written before the code: #59 sets up the configuration, Discord's variables and `server-only`, #10 the staff's variables, the session and the login, #63 `E2E_TEST_PROXY`, #76 the headers, and #9 what lives in Vercel's dashboard. The options set aside, and why, are in #51's decisions.

- **The session** is a cookie that iron-session 9 seals, encrypted and signed, holding only the member's Discord ID (ADR 0005); no session lives on the server, since the panel stores nothing (ADR 0004). Auth.js and Better Auth are set aside: each brings its own OAuth flow, which would replace `DiscordOAuth` and the two Route Handlers. It is named `__Host-session`, with `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/`, in development too, since Chromium takes a `Secure` cookie on `http://localhost` (end to end, 2026-10-26). `Lax`, not `Strict`: the return from Discord to `/login/callback`, and a link to the panel clicked in Discord, are navigations that start on another site, which a `Strict` cookie skips. `vercel.app` is on the Public Suffix List (https://publicsuffix.org/list/public_suffix_list.dat, line 16331, read 2026-10-24), so another Vercel project is another site, which can neither set the panel's cookies nor send them on a POST; `__Host-` costs nothing, and would matter under a domain of the panel's own. iron-session 9.0.1 needs Node `>=22.13.0` and is ESM only (`npm view iron-session`, 2026-10-24).
- **Its lifetime** is 7 days from the login, written into the seal's `ttl` and the cookie's `Max-Age`, and never extended: a Server Component cannot set a cookie (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md:81`), so extending it would mean writing the cookie from `proxy.ts` or from every Server Action. A session ends when it expires, through « Se déconnecter », or, for every member at once, when `SESSION_SECRET` changes. None can be revoked on its own (iron-session 9.0.1's README, « How to invalidate sessions? », `npm view iron-session readme`, 2026-10-24): the staff check on every request is what cuts a member's access (ADR 0005), so a stolen cookie is worth at most 7 days, and only while its member holds the staff role.
- **OAuth2.** `/login` draws 32 random bytes as the `state`, in base64url, keeps them in a `__Host-oauth-state` cookie with `HttpOnly`, `Secure`, `SameSite=Lax` and a `Max-Age` of 10 minutes, and sends `prompt=consent`: Discord documents no default for `prompt`, and `none` would send a member who clicks « Se reconnecter » back as the same account (https://docs.discord.com/developers/topics/oauth2, modified 2026-10-16). The callback compares the `state` in constant time, deletes its cookie whatever the outcome, and goes to `/login/failed` when it is missing or differs, so of two logins started in two tabs, only the later one can succeed, and only if it returns first. A login always lands on `/`, with no return path in the URL, so no redirect is open. PKCE with S256, which Discord's metadata lists (`code_challenge_methods_supported`, https://discord.com/.well-known/oauth-authorization-server, read 2026-10-24) but its OAuth2 page does not document, stays: on 2026-10-26, against « Shor Panel Dev », Discord refused a code exchanged with a wrong `code_verifier` (`400 invalid_grant`, « Code challenge failed. ») or with none (`400 invalid_request`, « Missing "code_verifier" »), and accepted it with the right one (#10). So `/login` also draws 32 random bytes as the `code_verifier`, in base64url, sends their S256 challenge, and keeps them in the same cookie, after the `state` and a dot, for the callback's exchange. `state` stays all the same, as #51 decided, since RFC 9700 relies on PKCE against CSRF only once the server is known to support it (§4.7.1). The member's token is not revoked after `/users/@me`: it never leaves the callback's memory, and revoking it would revoke every token of that authorization (the OAuth2 page), for one more call and one more failure. `iss`, which Discord has returned since 2026-10-14 (https://docs.discord.com/developers/change-log), goes unchecked: Discord advises the check for a client of several providers.
- **CSRF.** Nothing beyond what Next.js and the `Lax` cookie give: no token, and no `serverActions.allowedOrigins`. A Server Action takes only POST, and its `Origin` must match `Host` (`node_modules/next/dist/docs/01-app/02-guides/data-security.md:548-550`). A POST without `Origin` passes with a warning (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverActions.md:13`), but a browser sends `Origin` on a POST, and a client that does not carries no session cookie (inferred). `/login` and `/login/callback` are GETs that write nothing to Discord, and `state` covers the login itself.
- **The application's permissions.** A new permission, intent or change to the panel's role is a stop for Gilles (`deliver-epic/rules.md`, **Stops**, **Security**: what the application may do on a third party, a permission or a scope): `.claude/rules/discord.md`, **The application's permissions**, and `docs/discord.md`.
- **Secrets.** Every module that reads a secret from `process.env` or calls Discord starts with `import "server-only"`, so that a client component that reaches it fails the build, and each folder alone reads its own variables (`.claude/rules/env.md`, **Variables**). The logs say only failures, and never carry a secret, a token, the callback's `code` or `state`, a cookie, a member's ID, name or IP, or what the staff typed (`.claude/rules/monitoring.md`, **What is never logged**).
- **Personal data.** A change that starts or stops processing a personal datum updates `docs/personal-data.md`, which says what the panel processes about people, why and for how long, and the privacy policy at `/privacy`, with the date it shows, in the same change (`.claude/rules/privacy-policy.md`, **Personal data**, #27).
- **Configuration.** How each folder validates its variables, what the build on Vercel checks and what each variable is: `.claude/rules/env.md`.

## Code style

- **Layout.** Prettier lays the code out and sorts its classes and imports, and ESLint sets no layout rule: `pnpm format:check` runs in CI (`.claude/rules/prettier.md`).
- **Copied code** stays as `shadcn add` wrote it but for four kinds of line: `.claude/rules/ui.md`, **shadcn/ui and copied code**.
- **Names.** Files and folders are kebab-case; outside the files whose names Next.js sets, a component lives in the file named after it, `blocked-word-list.tsx` exporting `BlockedWordList`. Values and functions are camelCase; components, types and classes PascalCase; a module-level constant that holds fixed data SCREAMING_SNAKE_CASE, while other `const`s stay camelCase. An acronym is a word, `DiscordApi`, `userId`, but for `OAuth`, and a type takes no `I` prefix. The terms come from `GLOSSARY.md`, but in `src/discord/` (`docs/agents/domain.md`). Review checks names, since `@typescript-eslint/naming-convention` would need an exception for components; a slip it misses becomes a check.
- **Exports** are named and written inline, while a copied component keeps the registry's `export { … }`; a default export lives only where Next.js or a tool requires one, the files of `src/app/` and config files (`import/no-default-export`, not yet, #81). An import names the module itself, with no barrel between, which review checks, since a barrel that re-exports a client leaf beside a `server-only` module would pull that module into the client graph (inferred).
- **TypeScript.** `type` for every object type, `import type` for what is imported as a type only, and `as const` as the one type assertion, but on the line that mints the `StaffMember` brand (ADR 0005), which takes an `eslint-disable-next-line` once #81 refuses `as`. The syntax stays erasable, with no `enum`, `namespace` or parameter property. #81 adds the lint rules and `erasableSyntaxOnly` (not yet).
- **Module size** is a judgement call: a module holds one idea, with no figure and no `max-lines`, and code-review's smells, Divergent Change and Shotgun Surgery, watch it.

## Warnings

- **Zero.** `pnpm lint` is to run `eslint --max-warnings 0` (#89), and CI to fail on a warning of the build or of Node (#87); neither is in place yet, and a `warn` does not fail `pnpm lint` today (`.claude/rules/eslint.md`, **Warnings**; `.claude/rules/ci.md`, **CI's output**).
- **The tests' console.** Under Vitest and `node --test`, a test is to fail when it writes to the console, through any method, or when Node emits a process warning, a deprecation included, unless the test captures that line and asserts it, as the test of a failed alert send does with its `console.error` (`.claude/rules/monitoring.md`, **Tests**). Not in place yet (#88): neither tool fails on the console by default (inferred). React's development warnings, such as a missing `key`, go through `console.error`, and `NODE_ENV` is `test` under Vitest, so they will fail the test that renders them (inferred), and `pnpm test` writes nothing to the console today (2026-10-24).
- **Silencing.** A warning's cause is fixed first. A warning is silenced only when it is wrong for that code, or when it comes from code the panel keeps as its source wrote it: copied code (`.claude/rules/ui.md`, **shadcn/ui and copied code**), or a dependency.
- **Directives.** On a line, the one ESLint directive is `eslint-disable-next-line` followed by rule names, with no other text, and `@ts-expect-error` stands alone; `pnpm check:comments` refuses the rest (`.claude/rules/eslint.md`, **Directives**).
- **Reasons.** A directive's why goes in the message of the commit that adds it, and code-review refuses a new directive whose commit gives none. A silence that waits on something, such as a `peerDependencyRules` entry or a CI exception, gets a line in the rule of its area that says what lets it go; a standing choice is recorded in the rule that makes it.

## Dependencies

- **Versions.** Every direct dependency names an exact version, so that `package.json` says what runs and an update shows in its diff, and a version under 7 days old is refused: without a terminal, `pnpm add` of one fails, and an exclusion goes in only for a security fix. Gilles runs the monthly update session; its rules and holds are in `.claude/rules/dependencies.md`.
- **Adding a dependency.** Before `pnpm add`, read its `engines`, which must hold `engines.node`, its `peerDependencies` and whether it is deprecated; one that reaches a hosted service when it installs or runs first gets its entry in `docs/costs.md` (**Costs**).
- **Copying code from another project.** Read its license before it comes in (#106): a permissive one adds its notice to `THIRD_PARTY_NOTICES.md`, a copyleft one keeps the code out, an unlicensed one comes in only if the maintainer wrote it alone (`.claude/rules/dependencies.md`).

## Feedback loops

- Tests: `pnpm test` runs the tooling's tests, `node --test` over `test/**/*.test.mjs`, then the panel's, Vitest over `src/**/*.test.{ts,tsx}` and `next.config.test.ts`. Vitest runs in Node, without a DOM: a test renders a component with `react-dom/server`, as the server does. One file: `node --test test/<name>.test.mjs` or `pnpm exec vitest run <path>`. No test of `pnpm test` calls the real Discord: an in-memory fake replaces it (**Testing**).
- Contract: `pnpm test:contract` runs the `DiscordApi` contract suite against the real Discord, on the test Discord server, with the values of `.env.local`: `.claude/rules/discord.md`, **The contract suite**.
- End to end: `pnpm test:e2e` runs Playwright over `e2e/*.test.ts`, on Chromium, against `next start` serving the last `pnpm build`, so build first; install Chromium once with `pnpm exec playwright install chromium`. One test: `pnpm test:e2e <path>`. The calls the server makes for a test's `page` go to that test's fake, through the HTTP adapter, never to the real Discord (`.claude/rules/e2e.md`, **The server and the fake Discord**).
- Typecheck: `pnpm typecheck` runs `next typegen`, which writes what a fresh clone lacks, the gitignored `next-env.d.ts` and the route types behind `PageProps` and `LayoutProps`, then `tsc --noEmit`.
- Lint: `pnpm lint` runs ESLint; what it refuses, and what it is meant to refuse once #89 and #81 land, is in `.claude/rules/eslint.md`.
- Build: `pnpm build` (`next build`), which type-checks again. Dev server: `pnpm dev`.
- Comments: `pnpm check:comments`.
- Context budget: `pnpm check:context-budget` measures the always-loaded context against `context-budget.json`, and `--write` lowers its ceilings (`.claude/rules/context-budget.md`).
- Format: `pnpm format` lays out the repository with Prettier, `pnpm format:check` checks that it is laid out (`.claude/rules/prettier.md`). One file: `pnpm exec prettier --write <path>`.
- Components: `pnpm exec shadcn add <component>` copies a shadcn/ui component into `src/ui/`: what to read and strip after it is in `.claude/rules/ui.md`, **shadcn/ui and copied code**.
- CI: `.github/workflows/ci.yml` runs the comment check, the context budget check, the format check, the typecheck, the lint, the tests, the build, then end to end, after installing Chromium. Its `Check` job must pass before a PR merges, through the ruleset (`docs/delivery.md`, **The rules of `main`**). Never merge a PR whose CI is red.

## Commits, PRs, issues

- Commit messages read `Area: what changed`, in English.
- A branch is named `<area>/<subject>`: the area of the commits it carries, in lower case, such as `docs`, `tooling`, `interface`, `repo` or `dependencies` (`.claude/rules/dependencies.md`, **The session's PR**), then a few English words in kebab-case, with no issue number, since the PR gives it. A session renames its branch before its first push, since the desktop app names the branches of new sessions after a prefix of its own. Review checks it (Gilles, 2026-10-25, while grilling #57).
- The user is the sole author: commits carry no `Co-Authored-By` trailer, PRs carry no "Generated with" footer. Commits carry Gilles' GitHub `noreply` address: his account refuses a push that exposes the other (`docs/delivery.md`, **The repository**).
- Only the maintainer, Gilles (`docs/agents/issue-tracker.md`, **People**), or an agent running `deliver-epic` or `deliver-backlog`, which only he starts, merges into `main`, with a merge commit, never a squash. The repository allows merge commits only, since #100 turned squash and rebase off (`docs/delivery.md`, **The rules of `main`**). Vercel's Hobby plan has no team collaboration, and deploys no private repository of a GitHub organization (https://vercel.com/docs/git, updated 2026-09-18), hence a public repository (ADR 0007). Its check that a commit's author owns the Hobby team is written for private repositories (same page, **Deploying private Git repositories**), and Gilles authors every commit anyway.
- Issues, PR descriptions and comments read like a teammate wrote them: direct, specific, complete, no filler.
- A PR that only advances a ticket names it once, as `Part of #<n>`. GitHub closes, at merge, every issue that a PR description or commit message puts right after `close`, `fix` or `resolve` (any form), even inside a negation.
- Once a PR merges, delete its local branch with `git branch -d` and run `git fetch --prune`. When `-d` refuses, run `git merge-base --is-ancestor <branch> origin/<default branch>`: `-d` also refuses a merged branch that is ahead of its upstream, or whose upstream is gone while `HEAD` does not hold it, as five branches of #34's run were (exit code 0, 2026-10-30, #272; git 2.55.0, throwaway repositories, 2026-10-30). A branch that fails the check holds unmerged work: ask the user, or, under `deliver-backlog`, list it in the run's report. Under `deliver-epic`, `finish-pbi.mjs` runs that check and deletes the branch with `-D` once it passes, and lists a branch it keeps.

## Gotchas

A trap of one area sits in that area's rule, under `.claude/rules/`, which Claude Code loads when a matching file is read or edited: `dependencies.md` (`package.json`, `pnpm-workspace.yaml`, held versions, `minimumReleaseAge`, Corepack on Vercel), `eslint.md`, `ui.md` (`shadcn add` and `shadcn init`), `discord.md` (tokens, the test Discord server, the contract suite in a worktree), `nextjs.md` (`next dev`, `next typegen`), `monitoring.md`, `next-link-prefetch.md`, `view-transitions.md`, `react-components.md` (Base UI, portals, `next/script`), `e2e.md` (the fake Discord behind the server, the fixtures, the console check, the responsive checks, and the traps of Playwright, axe and `load`), `claude-hooks.md`, `node-tests.md`, `ci.md`, `env.md` (variables on Vercel), `audit-log.md` (the audit log's page, reading and filters, which are no trap, and how a test builds a reason) and `game-log.md` (the game log's page, reading, configuration and access, which are no trap either). The traps of the project board are in `docs/agents/issue-tracker.md`, **Gotchas**. Here stay the traps of the machine and the tooling that no path scopes:

- Under Git Bash, write a path inside a script as `C:/Users/…`: Node reads `/c/Users/…` as `C:\c\Users\…`, since MSYS converts only arguments.
- A U+00A0 typed into `Write` or `Edit` can land as an ordinary space, and `Read` shows one as a space too: after writing French text, count them with `grep -c $'\xc2\xa0' <file>`, or write a placeholder and replace it with `sed 's/<placeholder>/\xc2\xa0/g'`; the escape `\u00a0` typed into a JavaScript string lands as the character itself.
- Several sessions can share this folder: before switching branches here, read `git status` and `git reflog -3`; a change that needs its own branch goes in a `git worktree`.
- The hooks of `.claude/settings.json` need `pnpm install` first: without `node_modules`, `gh pr create` and `gh pr new` are refused, and edits go unformatted. A hook added during a session may not run before the next one. In a worktree, edits stay unformatted until `pnpm format` (`.claude/rules/claude-hooks.md`, **The format hook**).
- On Windows, `git worktree remove` fails, exit code 255 and `Filename too long`, on a worktree that has run `pnpm install`, whose `node_modules` holds paths over 260 characters, and unlists it while its folder stays. Remove the folder, with `rm -rf <worktree>` from Git Bash, `Remove-Item -LiteralPath '\\?\C:\…\<worktree>' -Recurse -Force` in PowerShell, the path written in full, or Node's `fs.rmSync(<worktree>, { recursive: true, force: true })`, then run `git worktree prune`. A worktree still locked needs `git worktree unlock` first.
