## No comments

The repository holds no comments, in any file that supports them: code, tests, scripts, CSS, HTML, Markdown, SQL, YAML, Python, PowerShell, `.env.example`, whose variables are documented in the README. Two exceptions only: a shebang, and a tool directive the code needs to work, which stands alone in its comment, with no text of its own, in the forms **Directives** allows.

What a comment would say goes elsewhere: the why of a change in its commit message, a decision in an ADR, a term in `GLOSSARY.md`, an invariant in a test and its name. Code copied from elsewhere, such as skymp-heavy-rp or EsportCards, loses its comments on the way in.

`pnpm check:comments` checks every tracked or untracked, non-ignored file of the repository that holds the folder it runs from (`git rev-parse --show-toplevel`), so a subfolder or a worktree checks its own repository. A hook runs it before `gh pr create` and its alias `gh pr new`, and CI on every PR and every push to `main`. The hook runs it from the `cwd` of its input, which follows Claude into a worktree, while `$CLAUDE_PROJECT_DIR`, where the hook's own copy of the script sits, stays at the project root where the session started (https://code.claude.com/docs/en/hooks, read 2026-10-30), so a PR from a worktree gets that worktree checked (inferred from those docs and from tests in temporary repositories, since no session in a worktree has tried it). From a folder in no repository it refuses the PR, since it has nothing to check, rather than check the repository of its own copy (decided by the agent on 2026-10-30, on #19, for Gilles to review).

It reads these types (`familyOf`, in `scripts/check-comments.mjs`): script files (`.js`, `.mjs`, `.cjs`, `.jsx`, `.ts`, `.mts`, `.cts`, `.tsx`), JSON (`.json`, `.jsonc`: `//` and `/* */`), CSS (`.css`, `.scss`), markup (`.html`, `.htm`, `.svg`, `.xml`), Markdown (`.md`: `<!-- -->`), SQL (`.sql`), YAML (`.yml`, `.yaml`), Python (`.py`: `#`), PowerShell (`.ps1`: any `#` outside a string, and `<# #>`), and the files with `#` comments: `.toml`, `.sh`, `.env*`, `.gitignore`, `.gitattributes`, `.prettierignore`, `.git-blame-ignore-revs`, `.npmrc`, `.editorconfig` and `Dockerfile`. In Markdown, a fenced code block (` ``` ` or `~~~`) and an inline code span are code, not comments, so a passage may quote `<!-- -->` in either, as **The browser's console** and a line of **Gotchas** do; an indented code block is not recognised, so a comment in one is reported, and a line that opens an HTML comment ends an inline code span, as a blank line does (decided by the agent on 2026-10-30, on #22, for Gilles to review). A `#!` on the first line of a `.py` or `.ps1` file is a shebang, not a comment. In PowerShell, telling a bare word from an expression takes PowerShell's own parser, so the check takes every `#` outside a string for a comment, but for one escaped with a backtick: `echo a#b` is reported, and so is `$s = "a $("b # c") d"`, where a subexpression holds quotes, both false positives that show where a missed comment would hide (decided by the agent on 2026-10-30, on #22, for Gilles to review).

A file of any other type is reported as « unknown file type » until the script reads it or lists it as commentless, which it does for images (`.png`, `.jpg`, `.jpeg`, `.gif`, `.webp`, `.avif`, `.ico`, `.bmp`), fonts (`.woff`, `.woff2`, `.ttf`, `.otf`, `.eot`) and `pnpm-lock.yaml`: it does not tell text from binary, so a new type of either fails the check until it is listed (decided by the agent on 2026-10-30, on #22, for Gilles to review). A file it cannot parse is reported too, including a Markdown code fence, a Python `'''` or `"""`, a PowerShell `<#`, `'`, `"` or here-string that never closes, so that the rest of the file is never skipped. The script's footer counts the comments, the files it cannot parse and the files of an unknown type each on a line of its own, none for a count of 0, and gives the advice to move the why elsewhere only when it found a comment, and the PR hook's refusal asks to remove each comment, to fix each file that cannot be parsed, and to teach the check each unknown file type or list it as a type without comments, since it quotes all three kinds of line (decided by the agent on 2026-10-30, on #299, for Gilles to review).

## Facts and docs

- **Facts apart from inferences.** Everything you write to docs, tickets or reports keeps verified facts, with their source (`file:line`, commit, URL and date, command output), visibly separate from inferences.
- **Challenge with evidence.** When the code, the docs, `GLOSSARY.md`, an ADR and the user's request disagree, name the contradiction, quote both sides, and ask which one wins. Record the answer through domain-modeling.
- **Agent decisions.** An agent running `deliver-epic` or `deliver-backlog`, as those of #221's run did under its prompt, decides where this file or a skill says to ask Gilles: it applies the most acceptable option and marks it `(decided by the agent on <date>, on #<n>, for Gilles to review)` in the docs, and under `Décisions de l'agent (à revoir par Gilles)` in the ticket, for him to review (`.claude/skills/deliver-epic/rules.md`, #257).
- **Unrecoverable why.** When nothing explains a decision or a fact the work needs, append it to `docs/agents/open-questions.md`: the question, where it shows up, who is likely to know, what is blocked on it.
- **Docs as you go.** Docs are updated the moment they become true, in the same change. `GLOSSARY.md` is a glossary and nothing else; ADRs follow domain-modeling's bar. When docs contradict the code, fix them in the same change if it takes a few lines, otherwise list them in your report.
- **Scope.** Each diff stays inside its ticket. Problems you spot nearby are loose ends: groom-backlog files them as tickets.
- **Gotchas.** When a session hits a trap the environment doesn't reveal, add one line under **Gotchas**, as for a warning silenced until something changes (**Reasons**). Delete lines that stop being true.

## Costs

No third party the panel relies on may ever send a bill or take a hidden fee, as Gilles decided on 2026-10-27, calling it a golden rule, as #9 was about to open the Vercel account (#123). It covers every service, account and tool the panel, its CI and its tooling use, today's and any to come. [`docs/costs.md`](docs/costs.md) says, for each, what the panel uses, why it cannot bill, what would make it bill, and what it can cost otherwise, with its sources.

- **No way to pay.** Every account the panel relies on stays on a free plan with no payment method on file, so that a limit reached blocks or pauses the service instead of billing it, as Vercel's Hobby and GitHub Free do (`docs/costs.md`). So nobody adds a payment method, starts a trial, upgrades a plan, or buys a domain, credits or an add-on, nor installs an integration or app that bills, on an account the panel relies on, not even for a free first month: a card added for one purchase may stay on file (inferred from one unofficial report, `docs/costs.md`, **Vercel**).
- **A paid plan** would reopen this rule: should the panel need one, as it would if Shor turned commercial, Gilles decides it in an ADR before anything is signed.
- **A new tool.** Before a new third party comes in, whether a service, an account, an integration, an app, or a package, an action or a registry that reaches a hosted service when it installs or runs, its entry goes into `docs/costs.md`, from its own pricing and terms: whether it asks for a payment method, what happens at each limit the panel could reach, and what would make it bill. One that needs a card before it can be used, or that bills past its free quota even without one, stays out. A package that only runs locally needs no entry, since the npm registry has its own (**Adding a dependency**). Neon, the store ADR 0004 picks after the MVP, gets its entry before its account opens, from the store's grilling (#175).
- **Agents** create no account, type no payment method, accept no trial or upgrade, buy nothing, and install no integration or app that bills, by any means: a terminal, a dashboard, an MCP server. Before Gilles takes such a step, they tell him what it costs, with its source, and they stop at a screen that asks for a card or offers a trial in place of the free plan.
- **Rechecked every month.** Free plans change: the monthly session of **Dependencies** reads again the pages `docs/costs.md` cites, and an entry whose facts moved is updated before anything else, or its service leaves (#97).

## Architecture

How a feature is written end to end, as Gilles decided while grilling #47 on 2026-10-23, then #49, #54, #52 and #50 for the lines that point to **Errors**, **Testing**, **Interface** and **Monitoring**. It was written before the code: each ticket that writes the code follows it.

- **Folders.** `src/app/` only routes: its `page.tsx`, `layout.tsx` and `route.ts` call a domain folder named after a `GLOSSARY.md` term, such as `src/staff/` (login, session, staff role), `src/blocked-words/` or `src/audit-log/`. A domain folder holds its logic, its components, its `actions.ts` and their tests. `src/discord/` is the adapter to Discord's REST API, `src/ui/` holds what the interface shares (**Interface**), and `src/monitoring/` the logs and the alerts (**Monitoring**). The error pages are the one exception (**Errors**).
- **The Discord seam.** `src/discord/` exposes two interfaces, one method per endpoint the panel calls but the alerts' webhook (**Monitoring**), typed with `discord-api-types`. `DiscordApi` uses the panel's application token and is bound at construction to one Discord server, so no method takes its ID: AutoMod rules, audit log, reading a member, searching the members, reading a user, a ban, the bans and the roles (#176), then the Discord server itself, for its owner and its roles, the application's own user, read from `/users/@me` with that token, modifying a member, for a timeout, opening a DM channel and sending a message in it (#179), and removing a member, for a kick (#180), then creating and removing a ban (#181). Each returns the fields of `discord-api-types`' object that the panel uses, picked from it, where the method's result is bigger than the panel needs, such as `Guild` or `Message` (#179). It also exposes that server's `guildId`, a property rather than a method, from which `memberAvatarUrl`, in `src/discord/member-avatar-url.ts`, builds the URL of a member's avatar (**Avatars**, #140), as `userAvatarUrl` does an account's Discord avatar (#176). `DiscordOAuth` uses the client ID and secret: authorize URL, code exchange, current user. The real implementations call `fetch`, with neither `@discordjs/rest` nor `@discordjs/core`. `src/discord/fake-discord.ts` keeps a Discord server's state in memory and, like Discord, adds an audit log entry on every write. Only tests import it: `pnpm dev` runs against the panel's development application, "Shor Panel Dev", and Gilles' test Discord server (#7). A `no-restricted-imports` rule of `eslint.config.mjs` refuses it and its HTTP adapter (**Testing**) anywhere in `src/` outside `*.test.*` files.
- **Entry points only wire.** Pages, layouts, `actions.ts`, Route Handlers, `proxy.ts` and `instrumentation.ts` hold no logic of their own and never read `process.env`. Those that need Discord get the real clients from `createDiscordApi()` and `createDiscordOAuth()` and pass them on, as in `addBlockedWord(discord, staffMember, word)`; tests pass the fake instead, with no `vi.mock`. The login callback's Route Handler and `proxy.ts` pass `createMonitor()`'s `Monitor` the same way (**Monitoring**). The callback's Route Handler passes `createDiscordApi` and `createDiscordOAuth` themselves, which its domain function calls inside its `try`, so that a missing variable is a panel error it reports too, since the callback throws nothing (**Error pages**; Gilles, 2026-10-26, on #10). Only `src/discord/` reads Discord's variables, `src/staff/` the staff's, and `src/monitoring/` its own (**Security**, **Variables**). Vitest cannot render `async` Server Components (`node_modules/next/dist/docs/01-app/02-guides/testing/vitest.md:9`), so what a page does lives in functions tested directly.
- **The staff check.** Every page but the login pages under `/login` and the error pages, and every Server Action that writes, starts with `requireStaffMember` from `src/staff/`, and every domain write takes the branded `StaffMember` it returns (ADR 0005). The pages under `/records` start with `requireModerationAccess` instead, which runs `requireStaffMember`, then calls `notFound()` for a staff member who holds no role of `MODERATION_ROLE_IDS`, so that they see the not-found page rather than `/login/refused` (ADR 0005, #176), and so does the Server Action that changes a sanction, whose domain functions also throw for a `StaffMember` who does not moderate (#179, #180), or, for a ban or its lifting, who does not ban: `StaffMember`'s `opensBans` says whether they also hold a role of `BAN_ROLE_IDS` (#181). Like the staff check's redirects, it runs in the part of the page under `<Suspense>`, so the page's static shell shows first, and the response keeps its `200` (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/not-found.md:193`). The shell's static `metadata` stays too, so that the tab of that staff member reads « Modération – Panel de Shor » on `/records` and « Fiche – Panel de Shor » on a record, not « Page introuvable – Panel de Shor », and names the section, though the comment of #61 of 2026-10-28 asks that the page read « comme si la section n'existait pas » (`e2e/records.test.ts`, 2026-10-30, #61). This is intended (Gilles, 2026-10-30, on #269): until Discord answers, the shell's body names the section too, through the `h1`, the sentence and the search form of `/records` and the breadcrumb of a record, though no data from Discord shows (a throwaway Playwright probe over `holdDiscord`, 2026-10-30), and the one reason ADR 0005 gives for the not-found page is that `/login/refused` would tell a staff member they are not staff. A `generateMetadata` that awaited `connection()`, then ran `requireModerationAccess`, gave that staff member the not-found page's tab, and kept the static shell and the moderators' tabs, but left every staff member without a `<title>` until Discord answered, which `checkAccessibility` refused on a record's skeletons, and `error.tsx` without one once Discord failed (the same probe). The not-found page is the panel's own, in French (**Error pages**, #61). `requireStaffMember` never returns a failure: it redirects to `/login` without a readable session, and to `/login/refused` a member who is not on the Discord server or lacks the staff role. The login callback, which has no session yet, runs the same check by Discord user ID and redirects itself (ADR 0005). It uses `redirect` rather than `forbidden()`, which needs `experimental.authInterrupts` (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/forbidden.md:17`) and gives a Route Handler an empty body (`node_modules/next/dist/server/route-modules/app-route/module.js:259-263`).
- **Writes** are Server Actions, in their domain folder's `actions.ts`, marked `"use server"`, and end with `refresh()` once the write lands. Logging out is a Server Action too, which only ends the session, then sends the member to `/login/logged-out`, a static page that says so, with « Se connecter avec Discord » (Gilles, 2026-10-26, on #10; #236). Route Handlers serve OAuth2 only: `/login` and `/login/callback`.
- **Validation** uses zod 4 throughout the repo, config included. Domain functions validate what comes from the browser, such as an action's `FormData` or the callback's query string. An invalid URL parameter counts as absent. Discord's responses are typed, not validated.
- **Components** are Server Components. `"use client"` goes only on a leaf that needs browser state or events, in its domain folder, on some components shadcn/ui's CLI copies (**Interface**), and on the two error pages Next.js requires it of (**Errors**); never on a page, a layout or anything that reaches `src/discord/`. A client leaf may hold browser state, such as `useActionState`'s, but no logic: it hands that state to a component whose output follows from its props alone (**Testing**). There are two exceptions. One is the toast of a write that lands, which the leaf that holds `useActionState` adds, through `useSuccessToast` (**Forms**; Gilles, 2026-10-29, on #227). The other is the theme a staff member chooses: `StatefulThemeToggle`, in `src/staff/`, reads it from `data-theme` through `useSyncExternalStore`, whose server snapshot is « Auto », and on a click writes it to `data-theme` and `localStorage`, or removes both for « Auto », then hands the theme and that write to `ThemeToggle`, as #225 decided (Gilles, 2026-10-29, on #225) (**Theme**).
- **Caching.** Nothing from Discord and nothing from the session goes through `use cache`, since the panel reads Discord back on every view (ADR 0002). Only the static shell prerenders; the part of a page that waits on Discord sits under `<Suspense>`, with a French fallback. That part, and a Route Handler, await `connection()` before they create a client: the build prerenders a page, and a `GET` Route Handler, until it reads the request (`node_modules/next/dist/docs/01-app/01-getting-started/15-route-handlers.md:89`, `:124`), and a client created there parses variables that a build outside Vercel lacks, which failed `pnpm build` on `/` and `/login/callback` (2026-10-26). It also keeps `/login` from prerendering one `state` for every visitor. `/records/[userId]` exports `instant = false`: its `userId` is unknown at build, so the navigation's `usePathname` suspends outside `<Suspense>` there (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/use-pathname.md:75`), which failed `pnpm build`; the page then renders at each request, where nothing outside `<Suspense>` waits on Discord (2026-10-28, #176).
- **`proxy.ts`** sends a request without a readable session to `/login`, on every route but `/login`, everything under it, and static files: the callback opens no session for a member without the staff role, who would otherwise loop from `/login/refused` back through Discord. It authorizes nothing.
- **Imports** that leave their folder use `@/*`, mapped to `src/*`; imports within a folder stay relative, except in `src/ui/` (**Interface**). Vitest resolves the alias only with `resolve.tsconfigPaths: true`, which Vite 8.3.5 leaves off by default.

## Errors

How the panel fails, as Gilles decided while grilling #49 on 2026-10-23, then #53 for what a successful write returns. Like **Architecture**, it was written before the code.

- **Four kinds of failure.** _Refused input_: the staff entered something the panel refuses, or the Discord server is in a state they can fix in Discord, such as already holding 6 keyword rules. _Refused access_: no readable session, or not staff (**The staff check**). _Discord unavailable_: a 429 the panel does not retry or that comes back, a 5xx, a network error or a timeout. _Panel error_: everything else, a misconfiguration included, such as a revoked token or a missing permission; the staff can only report it.
- **`DiscordError`** is the one class every method of `DiscordApi` and `DiscordOAuth` throws, network errors and timeouts included. It carries the HTTP status, Discord's JSON `code` and `message`, the delay of a 429, the method and the route's pattern, as Discord's docs write it, such as `/guilds/{guild.id}/members/{user.id}`, never the path filled in, since Next.js prints its properties in the logs (**Monitoring**), and says whether Discord is unavailable. One absence is an answer rather than an error: `getMember` returns `null` on Unknown Member, code 10007 (https://docs.discord.com/developers/topics/opcodes-and-status-codes, read 2026-10-23).
- **Retries.** Through `DiscordApi` and `DiscordOAuth`, a 429 is retried once, after its `retry_after`, when that is 2 s or less. Nothing else is retried, since a create that got a 5xx may have landed. Every call they make gives up after 10 s, through `AbortSignal.timeout`. An alert follows its own rules (**Monitoring**). The panel tracks no rate-limit bucket: it only reacts to a 429.
- **Write results.** A domain write checks every limit Discord documents before calling it, so a 400 from Discord is a panel error. It re-reads what it changes right before writing and applies only its own change, with no conflict error: a form sends one word, never a list. It returns `{ ok: true, message }`, or `{ ok: false, message }` with each field the form sent, as typed and under its name, such as `word`: one French `message` per form, written by the domain, that says what landed, such as « « foo » est maintenant un mot interdit. », or what went wrong, for refused input and for Discord unavailable, and the fields so the form keeps them (**Interface**). The action hands that to the form as is, whose leaf then shows the message of `{ ok: true }` in a toast (**Forms**, #227). A timeout that lands returns `{ ok: true }` whatever its direct message then meets, since the sanction holds: its message says that the member did not receive the direct message when Discord refuses it, with 50007, 50278 or 40003, or may not have when Discord is unavailable, and a direct message that fails otherwise is thrown, as a bug of the panel, so that it alerts, though the timeout has landed (Gilles, 2026-10-28, on #179, whose « S'il échoue, […] le résultat dit que le membre ne l'a pas reçu » this narrows to Discord's refusals and to Discord unavailable). Discord unavailable while a timeout or its lifting is written returns `{ ok: false }`, saying that it may or may not have landed, while Discord unavailable before the write, as the panel reads the member and the role hierarchy, says it did not happen, since a read that fails changes nothing on the Discord server (#213). A kick sends its direct message first, since a kicked account no longer shares a Discord server with the application (#180): the kick then happens whatever the message met, and the result says what the message met, as for a timeout; Discord unavailable during the kick returns `{ ok: false }`, saying that the kick may or may not have landed, and that the message went, if it did, with a reminder to untick the direct message before retrying, since a retry would send it again, while Discord unavailable before the kick says it did not happen; and a panel error is thrown once the kick was tried, during the kick though the message went, or during the message though the kick landed (Gilles, 2026-10-28, on #180, whose « Si l'expulsion échoue ensuite, le résultat dit que le message est parti mais pas la sanction » this narrows to Discord unavailable, as for #179; that a message's panel error waits for the kick is inferred from #180's « Si le message échoue, l'expulsion a lieu quand même »). A ban follows the kick's rules, through the same `sanctionAfterDirectMessage` of `src/sanctions/`, its direct message sent first to a member, and none to an account absent from the Discord server, which shares none with the application; lifting a ban sends no message, since the account shares no Discord server with the application either, and Discord unavailable there says that the lift did not happen when it comes before the write and that it may or may not have landed during it, as for a timeout's (#181, #213). Anything else is thrown, a `DiscordError` from the action's `requireStaffMember` included. Reads never write: what a page needs created, the first write creates.
- **Read failures.** What a page reads from Discord is thrown on failure, with no catch on the way, and `error.tsx` replaces the page, and the layout of `(staff)` with it, since `error.tsx` sits at the root of `src/app/`, above that layout, so that no navigation shows (**Error pages**, #53). - **Framework.** React, through Next.js (#5), with no library for state, client-side fetching, forms, URL state or animation: Discord holds the state, Server Components read it, Server Actions write it, and a form sends one field. This is revisited when a client leaf must share state with another or fetch data itself. The theme toggles of the sidebar and of the Sheet share the theme chosen through the document rather than through React: each reads `data-theme`, which holds it, through `useSyncExternalStore`, and the one clicked dispatches `THEME_EVENT`, which wakes the others, so no state library comes in (decided by the agent on 2026-10-29, on #225, for Gilles to review). No React Compiler either, until a client leaf grows heavy.
- **Styles.** Tailwind CSS 4, through `@tailwindcss/postcss`. `src/ui/globals.css` imports Tailwind and holds the theme; `src/app/layout.tsx` and `src/app/global-error.tsx` both import it, since `global-error` receives no global styles (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/error.md:163-165`). A class name is written whole, never built by concatenation, since Tailwind reads sources as plain text (https://tailwindcss.com/docs/detecting-classes-in-source-files, read 2026-10-23).
- **Component library.** shadcn/ui, on Base UI, in its `nova` style, with CSS variables, as `components.json` records. A ticket adds the components it is the first to use, through `pnpm exec shadcn add`. `shadcn` is a devDependency, since `shadcn init` makes `globals.css` import `shadcn/tailwind.css` from it (https://ui.shadcn.com/docs/cli, read 2026-10-23); Vercel installs devDependencies for the build (https://vercel.com/docs/builds/configure-a-build, **Install Command**, updated 2026-08-28). Components take a `className`, their variants use `cva`, and `cn` merges classes, which shadcn/ui's registry imports from the `cn` package (https://ui.shadcn.com/r/styles/base-nova/button.json, read 2026-10-23). ## Security

How the panel protects the staff's session, its secrets and its writes, and how it reads its configuration, as Gilles decided while grilling #51 on 2026-10-24. Like **Architecture**, it was written before the code: #59 sets up the configuration, Discord's variables and `server-only`, #10 the staff's variables, the session and the login, #63 `E2E_TEST_PROXY`, #76 the headers, and #9 what lives in Vercel's dashboard. The options set aside, and why, are in #51's decisions.

- **The session** is a cookie that iron-session 9 seals, encrypted and signed, holding only the member's Discord ID (ADR 0005); no session lives on the server, since the panel stores nothing (ADR 0004). Auth.js and Better Auth are set aside: each brings its own OAuth flow, which would replace `DiscordOAuth` and the two Route Handlers. It is named `__Host-session`, with `HttpOnly`, `Secure`, `SameSite=Lax` and `Path=/`, in development too, since Chromium takes a `Secure` cookie on `http://localhost` (end to end, 2026-10-26). `Lax`, not `Strict`: the return from Discord to `/login/callback`, and a link to the panel clicked in Discord, are navigations that start on another site, which a `Strict` cookie skips. `vercel.app` is on the Public Suffix List (https://publicsuffix.org/list/public_suffix_list.dat, line 16331, read 2026-10-24), so another Vercel project is another site, which can neither set the panel's cookies nor send them on a POST; `__Host-` costs nothing, and would matter under a domain of the panel's own. iron-session 9.0.1 needs Node `>=22.13.0` and is ESM only (`npm view iron-session`, 2026-10-24).
- **Its lifetime** is 7 days from the login, written into the seal's `ttl` and the cookie's `Max-Age`, and never extended: a Server Component cannot set a cookie (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/cookies.md:81`), so extending it would mean writing the cookie from `proxy.ts` or from every Server Action. A session ends when it expires, through « Se déconnecter », or, for every member at once, when `SESSION_SECRET` changes. None can be revoked on its own (iron-session 9.0.1's README, « How to invalidate sessions? », `npm view iron-session readme`, 2026-10-24): the staff check on every request is what cuts a member's access (ADR 0005), so a stolen cookie is worth at most 7 days, and only while its member holds the staff role.
- **OAuth2.** `/login` draws 32 random bytes as the `state`, in base64url, keeps them in a `__Host-oauth-state` cookie with `HttpOnly`, `Secure`, `SameSite=Lax` and a `Max-Age` of 10 minutes, and sends `prompt=consent`: Discord documents no default for `prompt`, and `none` would send a member who clicks « Se reconnecter » back as the same account (https://docs.discord.com/developers/topics/oauth2, modified 2026-10-16). The callback compares the `state` in constant time, deletes its cookie whatever the outcome, and goes to `/login/failed` when it is missing or differs, so of two logins started in two tabs, only the later one can succeed, and only if it returns first. A login always lands on `/`, with no return path in the URL, so no redirect is open. PKCE with S256, which Discord's metadata lists (`code_challenge_methods_supported`, https://discord.com/.well-known/oauth-authorization-server, read 2026-10-24) but its OAuth2 page does not document, stays: on 2026-10-26, against « Shor Panel Dev », Discord refused a code exchanged with a wrong `code_verifier` (`400 invalid_grant`, « Code challenge failed. ») or with none (`400 invalid_request`, « Missing "code_verifier" »), and accepted it with the right one (#10). So `/login` also draws 32 random bytes as the `code_verifier`, in base64url, sends their S256 challenge, and keeps them in the same cookie, after the `state` and a dot, for the callback's exchange. `state` stays all the same, as #51 decided, since RFC 9700 relies on PKCE against CSRF only once the server is known to support it (§4.7.1). The member's token is not revoked after `/users/@me`: it never leaves the callback's memory, and revoking it would revoke every token of that authorization (the OAuth2 page), for one more call and one more failure. `iss`, which Discord has returned since 2026-10-14 (https://docs.discord.com/developers/change-log), goes unchecked: Discord advises the check for a client of several providers.
- **CSRF.** Nothing beyond what Next.js and the `Lax` cookie give: no token, and no `serverActions.allowedOrigins`. A Server Action takes only POST, and its `Origin` must match `Host` (`node_modules/next/dist/docs/01-app/02-guides/data-security.md:548-550`). A POST without `Origin` passes with a warning (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/01-next-config-js/serverActions.md:13`), but a browser sends `Origin` on a POST, and a client that does not carries no session cookie (inferred). `/login` and `/login/callback` are GETs that write nothing to Discord, and `state` covers the login itself.
- **Headers.** `next.config.ts` sets, on every route, a Content Security Policy without nonces (ADR 0006), `default-src 'self'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline'; img-src 'self' data: blob: https://cdn.discordapp.com; font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests`, with `'unsafe-eval'` added to `script-src` in development only, when `NODE_ENV` is `development` (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md:548`); then `X-Content-Type-Options: nosniff` and `Referrer-Policy: strict-origin-when-cross-origin`, all through `headers()` on `/:path*`, and `poweredByHeader: false`, so no response carries `X-Powered-By`. `img-src` allows `https://cdn.discordapp.com` for the members' avatars (**Avatars**, #140). `next.config.test.ts` proves both policies, and an end-to-end test reads the headers on `/login/logged-out` (#76). `upgrade-insecure-requests` holds in every environment: under `next start` on `http://localhost:3100`, Chromium still loaded every script and stylesheet over `http:`, and every end-to-end flow passed (throwaway test, 2026-10-27); only the target of a redirect that a `fetch` follows went to `https:` (**Gotchas**). Under `next dev`, the same flows logged no violation (throwaway Playwright config, 2026-10-27), though two failed on Next.js's own development warning « Route … is rendering with server caches disabled », which `next start` does not print, and the headers test, as it should, on the development policy. The real `pnpm dev`, logged in through « Shor Panel Dev », logged no violation either, on `/`, on `/blocked-words` and around a blocked word added then removed (Gilles, 2026-10-30, #119). HSTS is Vercel's: `max-age=63072000; includeSubDomains; preload` on `*.vercel.app` (https://vercel.com/docs/cdn-security/encryption, updated 2026-09-15). Since scripts may run inline, React's escaping is the defense against XSS, and `react/no-danger` and `react/jsx-no-script-url` are errors, the latter on `<a>` and on `next/link`'s `Link`, which it skips without being named (#76, 2026-10-27). The Vercel Toolbar, on by default on previews, is turned off there (#9), so previews serve production's policy rather than one opened to `vercel.live` (https://vercel.com/docs/vercel-toolbar/managing-toolbar, updated 2026-08-11).
- **Rate limiting.** One rule of the Vercel Firewall, the only one Hobby allows per project (https://vercel.com/docs/vercel-firewall/vercel-waf/rate-limiting, updated 2026-08-28), set in the dashboard by #9: every path, keyed on the IP, 600 requests over a fixed window of 10 minutes, then deny. A Hobby project past an included limit waits 30 days (https://vercel.com/docs/plans/hobby, updated 2026-09-14), and a function invocation counts "regardless of request success or failure" (https://vercel.com/docs/functions/usage-and-pricing, updated 2026-06-16), so a script from one IP could take the panel down; traffic the Firewall denies counts toward no usage (https://vercel.com/docs/vercel-firewall/vercel-waf/usage-and-pricing, updated 2026-06-16). Attack Mode, free on every plan, answers a flood from many IPs (https://vercel.com/docs/vercel-firewall/attack-mode, updated 2026-08-11). The panel's code limits nothing: a write needs a session whose member holds the staff role, and Discord's 429 is handled (**Retries**).

## Monitoring

What the panel logs, what it never logs, and how its maintainer learns that it broke, as Gilles decided while grilling #50 on 2026-10-24, with everything kept free. Like **Architecture**, it was written before the code: #78 wrote `src/monitoring/` and `instrumentation.ts`, #59 gave `DiscordError` its route's pattern, #10 makes the login callback report what it catches, and #9 sets the webhook's variable in Vercel's dashboard. The options set aside, and why, are in #50's decisions.

- **Logs and the audit log.** Logs say why the panel failed, for whoever maintains it; the audit log says which staff member changed what (`GLOSSARY.md`, ADR 0004). So logs hold failures only: no staff action and no success, neither a write that lands, which Discord's audit log records with the panel's reason, nor a login.
- **What is logged.** Next.js prints every error thrown in a render, a Server Action or a Route Handler itself, through `console.error`, before it calls `onRequestError` (`node_modules/next/dist/server/route-modules/route-module.js:320-327`), with its message, its stack and its enumerable properties, `digest` included (`node_modules/next/dist/server/patch-error-inspect.js:437-442`); `redirect()` and `notFound()` never get there (`node_modules/next/dist/server/app-render/create-error-handler.js:52`, `:68-71`). The panel adds no line to those. An error of `proxy.ts` takes another way to `onRequestError`, with no such `console.error` on it (`node_modules/next/dist/build/templates/middleware.js:108-118`), and that way looks for the instrumentation the edge runtime loads, `_ENTRIES.middleware_instrumentation` (`node_modules/next/dist/server/web/globals.js:27-30`, `:48-57`), while `proxy.ts` runs on Node.js only (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/proxy.md:255`). On 2026-10-25, a throwaway `proxy.ts` that threw, under `next start`, never reached `onRequestError`, and Next.js printed its error once, with its stack (inferred for Vercel, where it was not tried). So `proxy.ts` catches what it throws and hands it to `Monitor.error`, which writes the one line and sends the alert, then answers without throwing it again (Gilles, 2026-10-25, on #78), by letting the request through: `proxy.ts` authorizes nothing, and each page runs its own check, which fails the same way and alerts a second time (Gilles, 2026-10-26, on #10). Beyond that, the panel writes only what the login callback catches, since the callback throws nothing (**Error pages**): a panel error at `error`, Discord unavailable and a missing or differing `state` at `warn`. Refused input and refused access leave nothing, nor does a login the member cancels on Discord (Gilles, 2026-10-26, on #10), nor a write that returns `{ ok: false }` because Discord is unavailable, nor a 429 retried with success. `info` and `debug` go unused.
- **What is never logged**, nor sent in an alert: a secret, such as `DISCORD_BOT_TOKEN`, `DISCORD_CLIENT_SECRET`, `SESSION_SECRET` or `ALERT_WEBHOOK_URL`; a member's OAuth2 token; the callback's `code` and `state`; a cookie, or the `Authorization` and `Cookie` headers; a member's Discord ID, name or IP, since the panel stores no personal data (ADR 0004); and what the staff typed, such as a blocked word. A member who reports a failure names themself in the staff's channel. That is why a `DiscordError` carries its route's pattern, never the path filled in (**`DiscordError`**).
- **Log lines** go through `console.error` and `console.warn`, called with the error object as Next.js does, with no logging library and no JSON. Vercel's own pages disagree on whether the fields of a JSON line are searchable (https://vercel.com/docs/logs/runtime, updated 2026-08-28, against https://vercel.com/kb/guide/add-structured-application-logs-to-vercel-functions, updated 2026-05-28), and Hobby keeps runtime logs one hour (the first page), so the alert carries what matters.
- **Alerts.** Every panel error notifies Gilles, the maintainer, alone, but one that a lookup of an avatar in the audit log turns into initials, or that the read of the blocked words' count in the navigation turns into no badge (**Read failures**, #226), and stays findable for at least 7 days, one thrown in `proxy.ts` included, which `proxy.ts` reports itself (**What is logged**); Discord unavailable notifies no one, since it passes. The staff get no alert: they report what they see in their channel (**Messages**), `error.tsx` with its reference, or `/login/failed`, which shows none. Alerts go through a Discord webhook into a private channel of Gilles' test Discord server (#7): it is free, needs no other account, and the panel writes every word it sends. Discord keeps a channel's messages with no expiry, which covers the 7 days (inferred, not checked against Discord's docs). Executing a webhook is a call to Discord's REST API (ADR 0003), and the one call to Discord outside `DiscordApi` and `DiscordOAuth` (**The Discord seam**). Nothing is grouped: ten failing pages send ten messages, and an alert sent during a Discord outage is lost.
- **What an alert says**, in English like the logs (**Language**): the environment, from `VERCEL_ENV`, `local` outside Vercel, and the short commit, from `VERCEL_GIT_COMMIT_SHA`; the context's `routeType` and `routePath`, the route's file path (`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/instrumentation.md:109`), when Next.js gives one; the `digest`, when there is one; the error's name and message, which for a `DiscordError` hold its method, its route's pattern, its status, and Discord's `code` and `message` (`src/discord/discord-error.ts`); then the stack's frames. It is one `content`, with no embed, of at most Discord's 2,000 characters (https://docs.discord.com/developers/resources/webhook, modified 2026-06-25): those lines, then the error and its frames in a code block, whose end is cut, ending on `…`, when it does not fit. Never `request.path`, which holds the query string (`instrumentation.md:103`), and so the callback's `code` and `state`, nor anything else **What is never logged** names. It goes with `allowed_mentions: { parse: [] }`, so that no error text mentions anyone, where a webhook's default parses users (the message page). It holds no time of its own: Discord shows when the message arrived.
- **Sending.** An alert never changes what the staff see. Next.js awaits `onRequestError` before it answers a Route Handler or an error that escapes a render (`node_modules/next/dist/build/templates/app-route.js:338`, `node_modules/next/dist/build/templates/app-page-runtime.js:1602`), but not for an error thrown while streaming (`create-error-handler.js:125`), and `after()` is documented for Server Components, Server Functions, Route Handlers and `proxy.ts` only (`node_modules/next/dist/docs/01-app/03-api-reference/04-functions/after.md:8`). So the alert runs in the background, gives up after 2 s through `AbortSignal.timeout`, and never throws: a failed send is one `console.error` line. It is never retried, a 429 included: in a burst the same error repeats, so the first alerts carry it (inferred). Discord gives no figure for the rate limit of webhooks (https://docs.discord.com/developers/topics/rate-limits, modified 2026-02-06). What can throw is the factory: `createRequestErrorReporter()` parses the variables on every error, and so does `createMonitor()`'s `error`, once its line is written, so an invalid `ALERT_WEBHOOK_URL` makes `onRequestError` throw, which Next.js catches and prints as `Error in instrumentation.onRequestError:`, with the variable's name and not its value (`node_modules/next/dist/server/lib/router-utils/instrumentation-globals.external.js:138`; **Configuration**). A failed send's line reads `Alert not sent: ` then Discord's status, or the name of what `fetch` threw, never its message, which can hold the webhook's URL, as a `Failed to parse URL from …` would. `onRequestError` returns before the send ends, and `waitUntil` from `@vercel/functions` hands the send to the `waitUntil` of the request context Vercel's runtime keeps under `Symbol.for("@vercel/request-context")`; without that context, as under `pnpm dev` and `next start`, it does nothing, and the send runs on in a server that stays up (`node_modules/@vercel/functions/wait-until.js`, `get-context.js`, 3.10.1). Under `next start`, an error thrown while streaming and one thrown by a Route Handler each sent their alert, to a well-formed URL that Discord answered with a 404 (2026-10-25), and under `pnpm dev`, with `ALERT_WEBHOOK_URL` set by hand, a Route Handler's panel error reached the private channel of Gilles' test Discord server (Gilles, 2026-10-25). On a preview, the send of an error thrown while streaming reached its end too: on 2026-10-30, a throwaway page under `/login/`, `◐` in the build's list, whose component under `<Suspense>` threw after `connection()`, put an alert in that channel with `preview`, the commit, `render /login/probe-alert`, the `digest` and frames under `/var/task/` (Gilles, on #78). That its response had already left is read under `next start`, where `curl` got the page's `200` and its shell in 27 ms, the boundary flagged in the stream, and inferred on Vercel, and whether the send would have ended without `waitUntil` was not tried. Each render that fails sends its own alert: that trial's « Réessayer » sent a second one with the same `digest`, as a load and a click on it sent two in a browser under `next start` (2026-10-30).
- **`src/monitoring/`** sits outside the domain, like `src/discord/` and `src/ui/`. It exposes `Monitor`, one method per level, which `createMonitor()` builds, in `monitor.ts`, without reading its variables: `error` writes the line, then reads them and sends the alert, `warn` writes the line only. So a request that reports nothing, through `proxy.ts` say, never fails on `ALERT_WEBHOOK_URL` (#10). `isPanelError`, in `panel-error.ts`, tells whether a thrown error alerts: a `DiscordError` that says Discord is unavailable does not, anything else does. It knows a `DiscordError` by its `name` and its `unavailable`, not by `instanceof`, since `instrumentation.ts` gets a copy of the class of its own (**Gotchas**). `src/instrumentation.ts` only wires: its `onRequestError` hands the error, the request and the context to the reporter that `createRequestErrorReporter()` builds, in `request-error.ts`, which sends the alert when `isPanelError` says so, and writes no line, since Next.js has written it. The login callback's domain function takes a `Monitor`, as it takes `DiscordApi` and `DiscordOAuth`, and so does what `proxy.ts` calls. `alert-message.ts` lays out the alert, and `alert.ts` sends it, over a `fetch` and a `waitUntil` taken as parameters, like **The real implementations**, which the two factories fill with `globalThis.fetch` and `@vercel/functions`' `waitUntil`, behind `import "server-only"` (**Secrets**). `env.ts` reads `ALERT_WEBHOOK_URL`, `VERCEL_ENV` and `VERCEL_GIT_COMMIT_SHA` (**Variables**). `InMemoryMonitor`, in `in-memory-monitor.ts`, keeps each report with its level for the tests, and the `no-restricted-imports` rule that keeps the fake Discord in `*.test.*` files (**The Discord seam**) refuses it elsewhere too.
- **Stacks** stay as Next.js builds them, minified, since `experimental.serverMinification` defaults to `true` (`node_modules/next/dist/server/config-shared.js:203`): the panel adds neither `serverSourceMaps` nor `--enable-source-maps`. The message, the route and a `DiscordError`'s fields place most failures in a panel this small. This is revisited when a stack proves unreadable.
- **No uptime probe.** The failures that matter, such as a revoked token or a removed permission, show only when a page reads Discord, so when the staff use the panel, and the alert fires then. A failed deployment notifies its creator, on the web and by email, by default on every plan (https://vercel.com/docs/notifications, updated 2026-09-14), and Vercel keeps the previous production deployment (**Configuration**).
- **The browser reports nothing.** Client leaves hold no logic (**Components**), an action's error is thrown on the server before the browser sees it, and `connect-src` stays `'self'` (**Headers**).

## Code style

How the code is laid out, named and typed, as Gilles decided while grilling #48 on 2026-10-24. Like **Architecture**, it was written before the tooling: #80 set up Prettier as described below, and #81 sets up the lint rules and `erasableSyntaxOnly`. It lives here rather than in a `CODING_STANDARDS.md`, since code-review reads every file that documents how code is written (its `SKILL.md:36`, mattpocock/skills 1.3.1). The options set aside, Biome, oxfmt and ESLint Stylistic among them, and why, are in #48's decisions.

- **Prettier lays out** every file it knows: TypeScript, JavaScript, CSS, JSON, YAML and Markdown. It and the two plugins below are devDependencies, `prettier.config.mjs` is the source of truth for layout, and `.prettierignore` keeps out `pnpm-lock.yaml`, `.claude/skills/groom-backlog/`, the copy shared with EsportCards, which commit e885352 means to differ only by `config.json`, and `.claude/skills/deliver-epic/`, shared with EsportCards the same way (#257). `pnpm-workspace.yaml` stays in: in two tries with pnpm 12.9.1, a plain `pnpm add` left it alone, and a `pnpm add` of a version under a day old wrote its `minimumReleaseAgeExclude` entry in double quotes, which Prettier accepts (tried, then reverted, 2026-10-24). If a later `pnpm add` undoes Prettier's layout there, the file joins `.prettierignore` (#48's decisions). ESLint stays the linter and sets no layout rule (`pnpm exec eslint --print-config src/app/page.tsx`, 2026-10-24), so no `eslint-config-prettier`.
- **shadcn/ui's style.** Prettier's defaults with `semi: false` and `trailingComma: "es5"`, which are the registry's own: with them and the two plugins below, Prettier 3.9.10 leaves `src/ui/button.tsx` and the sources of 20 base-nova components unchanged (run on scratch copies of https://ui.shadcn.com/r/styles/base-nova/<name>.json, 2026-10-24). `shadcn add --diff` compares lines (`diffLines`, `node_modules/shadcn/dist/index.js:121`), so this style keeps it to the lines the panel changes (**Copied code**), where single quotes would add every line that holds a string. The width stays 80: at 100, Prettier changes 287 lines across 15 of those 20 components.
- **Classes** are sorted by prettier-plugin-tailwindcss, in Tailwind's recommended order, against `src/ui/globals.css`, in `className` and inside `cva()` and `cn()` calls. It drops duplicate classes and extra whitespace by default, and loads last among Prettier's plugins (https://github.com/tailwindlabs/prettier-plugin-tailwindcss, README, read 2026-10-24).
- **Imports** are sorted by `@ianvs/prettier-plugin-sort-imports`, in the registry's order: `node:` modules, `react`, `next`, other packages, then, after a blank line, `@/` and relative paths. - **Actions** name their full version tag, such as `pnpm/action-setup@v6.1.0`: it reads without a comment (**No comments**), and an update shows in the diff, where a major tag can lag, as `pnpm/action-setup`'s `v6` still pointed to v6.0.10, which predates its pnpm 12 support (pnpm/action-setup#288 and #289, 2026-10-25). A workflow whose job holds a secret pins its actions by SHA instead, as `contract.yml` does, while `ci.yml` keeps its tags (**Delivery**). `pnpm outdated --include-github-actions` lists them with the packages (`pnpm help outdated`).
- **Advisories.** GitHub's dependency graph reads no lockfile of two YAML documents, which pnpm 12 writes, so it raises no Dependabot alert (https://github.blog/changelog/2026-10-20-dependabot-now-supports-npm-12-pnpm-11-and-12-and-bun-1-4/); #94 turns the graph and the alerts on all the same, for the day it does, but not Dependabot's security updates. CI runs `pnpm audit` and `pnpm audit signatures` after the install, on every PR and every push to `main`, and once a day on `main`, which notifies "the user who initially created the workflow" (https://docs.github.com/en/actions/concepts/workflows-and-actions/notifications-for-workflow-runs, read 2026-10-25). `pnpm audit` covers every dependency, devDependencies included, and fails on any advisory at its default level, `low` (https://pnpm.io/cli/audit, read 2026-10-25; https://github.com/pnpm/pnpm/blob/v12.9.1/pnpm/crates/cli/src/cli_args/audit.rs#L392-L402). An advisory is fixed by an update. It is ignored, through `--ignore <GHSA>`, which writes it under `auditConfig.ignoreGhsas` in `pnpm-workspace.yaml` (pnpm 12.9.1, 2026-10-25), only when the panel cannot reach the vulnerable code, with its **Gotchas** line, and the `overrides` that `pnpm audit --fix` writes are a last resort, with theirs (**Reasons**). An advisory published while a PR is open should turn it red with no change of code, as a warning that follows the date does (**CI's output**; inferred).
- **One copy.** CI runs `pnpm dedupe --check` after the install, which fails when two copies of a package could be one (`pnpm help dedupe`). `typescript-eslint`, which #89 makes a direct devDependency at the version `eslint-config-next` uses (**Type-aware lint**), moves in the same commit as `eslint-config-next`, which declares `^8.56.0` (`npm view eslint-config-next@16.4.3 dependencies.typescript-eslint`, 2026-10-25).
- **Transitive dependencies** are refreshed at each session by `pnpm update`, in a commit of its own. With exact direct versions, it should move only the transitive ones, within their ranges, since its `--depth` defaults to unlimited (`pnpm help update`; inferred, #97 tries it first). The release age guards it.
- **Deprecated packages.** pnpm prints a deprecation only at `pnpm add` and `pnpm update` (**Warnings**), and records it as a `deprecated:` field of `pnpm-lock.yaml`, which held none on 2026-10-25. The session reads both: a deprecated direct dependency becomes a ticket to replace it, and a transitive one waits for its parent to move, unless `pnpm audit` flags it or it raises a warning in CI.
- **The registry.** Each session runs `pnpm exec shadcn add <component> --diff` on every copied component. What the registry changed comes in like a minor update, and the panel's own lines stay (**Copied code** of **Interface** and of **Code style**).
- **Adding a dependency.** Before `pnpm add`, its `engines`, which must hold `engines.node` (**Gotchas**), its `peerDependencies`, and whether it is deprecated, are read, and one that reaches a hosted service when it installs or runs first gets its entry in `docs/costs.md` (**Costs**). After it, the version is exact, its build script stays refused in `allowBuilds` unless it cannot work without one, which its commit then explains, `pnpm-workspace.yaml` is read again, and `pnpm audit` and `pnpm dedupe --check` pass.
- **The session's PR.** One per session for all but the majors, on `dependencies/<yyyy-mm>`. It holds a commit per package, or per set that must move together, such as Next.js and `eslint-config-next`, or React and its types, with the docs that package changes: `Dependencies: update next and eslint-config-next to 16.4.3`. The refresh of transitive dependencies follows, as `Dependencies: refresh the lockfile`. For each package, the PR gives the versions it moves between, what was read, what changes for the panel, and the citations re-read.

## Delivery

How code goes from a branch to production, where it runs on the way, and what CI checks, as Gilles decided while grilling #57 on 2026-10-25; the options set aside, and why, are in #57's decisions and in ADR 0007. Like **Architecture**, it was written before the code: #101 and #100 open the repository, #96 and #95 set CI's Node and runner, #103 the build cache, #102 `contract.yml`, #9 the Vercel project and #13 the first production deploy.

- **The repository** has been public since 2026-10-27, because Vercel's Hobby plan deploys no private repository of a GitHub organization, and ADR 0007 lists what going private again would break. #100 published it once a secret scan of the whole history, pull requests' refs included, found nothing; once the passages Gilles chose to withhold from the issues were rewritten and their earlier versions deleted (#100), since "anyone with read access to a repository can view a comment's edit history" (https://docs.github.com/en/communities/moderating-comments-and-conversations/tracking-changes-in-a-comment, read 2026-10-27); and once the POs and loanspac, owners of the organization like Gilles (`gh api orgs/ShorRP/members?role=admin`, 2026-10-25), agreed. ## Commits, PRs, issues

- Commit messages read `Area: what changed`, in English.
- A branch is named `<area>/<subject>`: the area of the commits it carries, in lower case, such as `docs`, `tooling`, `interface`, `repo` or `dependencies` (**Dependencies**), then a few English words in kebab-case, with no issue number, since the PR gives it. A session renames its branch before its first push, since the desktop app names the branches of new sessions after a prefix of its own. Review checks it (Gilles, 2026-10-25, while grilling #57).
- The user is the sole author: commits carry no `Co-Authored-By` trailer, PRs carry no "Generated with" footer.
- Only the maintainer, Gilles (`docs/agents/issue-tracker.md`, **People**), or an agent running `deliver-epic` or `deliver-backlog`, which only he starts, merges into `main`, with a merge commit, never a squash. The repository allows merge commits only, since #100 turned squash and rebase off (**The rules of `main`**). Vercel's Hobby plan has no team collaboration, and deploys no private repository of a GitHub organization (https://vercel.com/docs/git, updated 2026-09-18), hence a public repository (ADR 0007). Its check that a commit's author owns the Hobby team is written for private repositories (same page, **Deploying private Git repositories**), and Gilles authors every commit anyway.
- Issues, PR descriptions and comments read like a teammate wrote them: direct, specific, complete, no filler.
- A PR that only advances a ticket names it once, as `Part of #<n>`. GitHub closes, at merge, every issue that a PR description or commit message puts right after `close`, `fix` or `resolve` (any form), even inside a negation.
- Once a PR merges, delete its local branch with `git branch -d` and run `git fetch --prune`. When `-d` refuses, the branch holds unmerged work: ask the user, or, under `deliver-epic` or `deliver-backlog`, list it in the run's report.

## Gotchas

- `@babel/parser`, which the comment check uses, stays on 7.x: 8.x requires Node `^22.18.0 || >=24.11.0` (`npm view @babel/parser@8 engines`, 8.0.8, 2026-10-29), which leaves out 24.0.0 to 24.10.x, within the `^24.0.0` that `engines` promises in `package.json`. CI would not catch the gap: it runs the latest 24.x (**CI**), 24.22.1 on 2026-10-29 (run 40898070133), which 8.x accepts. The hold goes once 8.x accepts the whole of 24, or `engines.node` starts at 24.11.0.
- `engines.node` names the one major the panel runs on, `^24.0.0` (**Node**), and each range the toolchain declares must hold it whole: Vitest 5 wants `^22.12.0 || ^24.0.0 || >=26.0.0`, ESLint 10 `^20.19.0 || ^22.13.0 || >=24` (`npm view <package> engines`, 2026-10-29). Read a new dependency's `engines` before adding it: jsdom 30, for one, wants `^22.22.2 || ^24.15.0 || >=26.0.0`, which leaves out 24.0.0 to 24.14.x (30.1.3, 2026-10-29).
- `typescript@7` on npm is the native compiler: its package exports no stable JavaScript API (only `./unstable/*`), so tooling that parses code cannot rely on it. That is why the comment check parses with Babel, and why TypeScript stays on `~6.0.3`: typescript-eslint, which `eslint-config-next/typescript` uses, accepts `typescript >=4.8.4 <6.1.0` (8.72.0, `npm view typescript-eslint peerDependencies`, 2026-10-23). Next.js alone would accept 7, through its `tsc` CLI (https://nextjs.org/docs/app/api-reference/config/typescript, updated 2026-08-25).
- ESLint is on 10, since 9.x reached end-of-life on 2026-08-06 (https://eslint.org/version-support, read 2026-10-23). `eslint-config-next` supports 10 since 16.4.0 (https://nextjs.org/docs/app/api-reference/config/eslint, updated 2026-10-15), but three plugins it bundles, `eslint-plugin-import`, `eslint-plugin-jsx-a11y` and `eslint-plugin-react`, still cap their `eslint` peer at `^9`: hence the `peerDependencyRules` of `pnpm-workspace.yaml`. Drop each rule once its plugin lists 10.
- pnpm 12's `minimumReleaseAge` defaults to 1,440 minutes, and stays non-strict until the setting is written down (https://github.com/pnpm/pnpm/blob/v12.9.1/pnpm/crates/config/src/registry_options.rs#L200-L212). Non-strict, when no version old enough fits, as for an exact `next@16.4.3`, pnpm takes the young version and writes it into `minimumReleaseAgeExclude` in `pnpm-workspace.yaml` without asking, then says « (set minimumReleaseAgeStrict to true to gate these updates with a prompt) » (`minimum_release_age.rs:146-191`, same tag, under `pnpm/crates/package-manager/src/`). On 2026-10-23, `pnpm add` reported doing so for Next.js 16.4.3, on npm since 13:40 UTC that day (`npm view next time`), so the panel stayed on 16.4.2. Read `pnpm-workspace.yaml` after every `pnpm add`, until #92 writes the setting down, which makes pnpm ask at a TTY and fail without one (**Release age**).
- `eslint-plugin-jsx-a11y`'s `flatConfigs.recommended` registers a plugin object other than the one `eslint-config-next` registers, and ESLint 10.13.0 refuses the pair: « Cannot redefine plugin "jsx-a11y" » (2026-10-24). So `eslint.config.mjs` takes only its `rules`, on the files `eslint-config-next` registers the plugin for. A rule given only a severity keeps the options set before it, such as `alt-text`'s `img: ["Image"]` (`pnpm exec eslint --print-config src/ui/button.tsx`).
- `import/order`, from the `eslint-plugin-import` 2.32.0 that `eslint-config-next` bundles without turning the rule on, crashes on ESLint 10.13.0 once it has an import to reorder: `pnpm exec eslint --rule '{"import/order":["error",{"alphabetize":{"order":"asc"}}]}' .` stops on `.claude/skills/groom-backlog/scripts/backlog.mjs` with « TypeError: sourceCode.getTokenOrCommentBefore is not a function », while `{"import/order":"error"}` finds nothing to reorder and passes (2026-10-24). A script that must run before the body is read is a plain `<script>` in the root layout's `<head>`, whose text React writes as it is.
