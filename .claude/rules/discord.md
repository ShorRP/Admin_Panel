# Discord

The panel's client for Discord's REST API (ADR 0003, #47, #59, #63): `DiscordApi` and `DiscordOAuth`, their real implementations, an in-memory fake, the HTTP adapter that serves it end to end, and the contract suite. What Discord was measured to do, what the fake copies of it and where the application stands on Shor are in `docs/discord.md`: read it before adding a method, a read of a channel or a permission.

## The Discord seam

- One method per endpoint the panel calls, but the alerts' webhook (`.claude/rules/monitoring.md`), typed with `discord-api-types`. The real implementations call `fetch`, with neither `@discordjs/rest` nor `@discordjs/core` (#47).
- `DiscordApi` uses the application's token and is bound at construction to one Discord server, so no method takes its ID and `guildId` is a property, from which `member-avatar-url.ts` builds avatar URLs (`.claude/rules/records.md`, **Avatars and the link to a record**). `DiscordOAuth` uses the client ID and secret.
- A method whose result is bigger than the panel needs returns the fields it uses, picked from the object of `discord-api-types`, such as `Guild`, `Message` or `GuildChannel` (#179, #384): `Guild` and `GuildChannel` keep what `canViewChannel` reads (`CLAUDE.md`, **Channel visibility**).
- `listMembers` reads 1,000 a call at most, from the highest ID of the previous page, and needs the Server Members Intent (#322); a search by name runs in memory over it (#324). `listMessages` reads 100 a call at most, from the newest, before a given message; the tickets in progress read it (`src/support-tickets/read-open-support-tickets.ts:143`).
- From 2026-11-16 Discord leaves out of `listChannels` the channels the application lacks View Channel on, so `canViewChannel` takes a channel that `listChannels` does not give as not viewable (#384; `CLAUDE.md`, **Channel visibility**; `docs/discord.md`, **The Discord seam**).
- `searchMessages` (#383) gives the `total_results` and the messages found, flat, and needs the Message Content intent and Read Message History on the channels it searches (**The application's permissions**). ADR 0010 holds what it reads and serves, and what it costs.

## Errors and retries

- `DiscordError` is the one class every method of `DiscordApi` and `DiscordOAuth` throws, network errors and timeouts included. It carries the HTTP status, Discord's JSON `code` and `message`, the delay of a 429, the method and the route's pattern as Discord's docs write it, never the path filled in, since Next.js prints its properties in the logs (`docs/monitoring.md`, **What Next.js prints**), and says whether Discord is unavailable. An absence is an answer, not an error: `getMember`, `getUser` and `getBan` return `null` on Unknown Member (code 10007), Unknown User and Unknown Ban.
- A 429 is retried once, after its `retry_after`, when that is 2 s or less (`MAX_RETRY_AFTER_S` of `rest.ts`); a longer one, or one that comes back, is a `DiscordError` that counts as Discord unavailable. Nothing else is retried, since a create that got a 5xx may have landed. Every call gives up after 10 s, through `AbortSignal.timeout`. The panel tracks no rate-limit bucket: it only reacts to a 429.
- `searchMessages` is retried the same way when Discord answers `202`, "Index not yet available. Try again later", code 110000: after its `retry_after`, or after 0.25 s when that is shorter, since the docs ask for "a short delay" at 0 (decided by the agent on 2026-11-05, on #383, for Gilles to review). A `202` that comes back, or whose delay is over 2 s, is a `DiscordError` with the status 202, which counts as Discord unavailable.

## The fake

`fake-discord.ts` implements `DiscordApi` and `DiscordOAuth`, keeps a Discord server's state in memory and, like Discord, adds an audit log entry on every write. Each test builds its own. Only tests import it, and a `no-restricted-imports` rule of `eslint.config.mjs` refuses it and the HTTP adapter anywhere in `src/` outside `*.test.*` files, since `pnpm dev` runs against "Shor Panel Dev" and the test Discord server (#7). The helpers that pose another domain's messages and channels sit with that domain, and the same rule keeps them in test files.

- It refuses what Discord refuses among the limits the panel touches, with the `DiscordError` Discord gave, so that a limit the domain forgets to check fails a test (AutoMod's limits, whom a timeout, a kick or a ban may reach, a direct message's refusals, a search's limits; `docs/discord.md`, **The fake**). It copies what Discord was seen to do, never more, since a stricter fake fails a test on what Discord takes: `custom_message` stops at the 300 characters Discord enforces (decided by the agent on 2026-11-02, on #325, for Gilles to review).
- The application is always a member. A ban in the state has no audit log entry unless the state poses its entry too, so a record reads it as given in Discord (#285). `@everyone` has no permission unless a role is given for the Discord server's own ID, which then is that `@everyone` (#384). `listMembers` gives the application and the members of the state, by ascending ID, after an ID if one is given, and one member unless asked for more (#322); a test that stands for the Server Members Intent turned off makes it fail once with the 403 of code 50001 (#317).
- What happens in Discord outside the panel has methods of its own, named as in Discord, such as a member losing a role, creating or editing an AutoMod rule, or timing out, kicking or banning by hand. The audit log records an AutoMod rule change under the member's name with no reason from the panel, and the rest with the reason the member typed, if any; each entry stays that member's even when the reason follows the panel's format, since its `user_id` is the member's, not the application's (#210). A timeout, a kick, a ban and their lifting are the entries `MEMBER_UPDATE`, `MEMBER_KICK`, `MEMBER_BAN_ADD` and `MEMBER_BAN_REMOVE`, and a kick or a ban leaves an account that is not on the Discord server (#177, #218). An AutoMod timeout is one `AUTO_MODERATION_USER_COMMUNICATION_DISABLED` entry, with no end and no `MEMBER_UPDATE`, for any rule (#209, #327; `.claude/rules/sanctions.md`, **Notices and history**).
- `directMessagesTo(userId)` reads what an account received, and `deletedMessageSecondsOf(userId)` the seconds a ban asked to delete, as no method of `DiscordApi` does (#179, #181). An audit log reason keeps its first 512 characters and an empty one is no reason, as at Discord, so that a test that reads a reason back sees the cut (ADR 0004; Gilles, 2026-10-25, on #59).
- A channel is given by its ID alone, a text channel with no parent and no overwrite, or in full. A message posed in it is the application's unless another author is named, and gets the next ID, minted from its `sentAt` when a test gives one, so that a search bounded by two IDs keeps the messages of a period (#386, #388). `listChannels` leaves no channel out, so a test that stands for a channel the application cannot view leaves it out of `channels` (#384; **The Discord seam**).
- `searchMessages` (#383) finds the whole words of a text, whatever their case and with their accents, in the content or in one text of an embed at a time. Words split at everything that is no letter, digit or emoji, and an apostrophe, U+2019 alone, joins the letters around it (`search-words.ts`). Two words match within 2 words of one another, in any order. It has none of Discord's index lag, nor its 202 and its 429s: `failNext` makes it fail once.
- `messageContentIntent: false`, on by default, stands for the Message Content intent turned off: `listMessages` and `searchMessages` give another author's message with its content and embeds emptied, unless the application wrote it or it mentions the application, and no text matches it (`docs/discord.md`, **The fake**).
- `failNext(method, error)` makes that method's next call throw that `DiscordError`, once. A test that needs a method to fail with anything else, as a bug in the panel would, or to answer some calls and fail the others, subclasses the fake in its own file and overrides that method (#141, #231).
- Another method issues the OAuth2 code a test logs in with, for the code challenge, and the exchange refuses the code with another code verifier, or none, as Discord did (`CLAUDE.md`, **OAuth2**).

## The HTTP adapter

`httpAdapter`, in `http-adapter.ts`, next to the fake, takes a `DiscordApi` and a `DiscordOAuth` and answers a `Request` addressed to Discord with a `Response`, in the shape of `fetch`. It imports no fake: tests and Playwright hand it one.

- A `DiscordError` is answered with its status and Discord's JSON error body, `retry_after` included; an absent member, user or ban with Unknown Member, Unknown User or Unknown Ban; a route the panel does not call with Discord's 404. A `DiscordError` without a status, and any other error, rejects, as `fetch` does on a network error.
- `/users/@me` is answered by its `Authorization`: `Bot` with the application user, `Bearer` with `DiscordOAuth`'s current user (#179). A kick, a ban and a ban's lifting get Discord's 204 and no body (#180, #181). The search of the messages is answered with each message found in an array of its own, as Discord does (#383).

## The real implementations

They take `fetch` as a parameter, which `createDiscordApi()` and `createDiscordOAuth()` fill with `globalThis.fetch`. Tests pass a function that returns hand-written `Response`s, for what the contract suite cannot trigger on demand: a 5xx, a 429, a timeout, a network error. Delays run on real timers, with no clock injected, since Vitest's fake timers do not fake `AbortSignal` (`docs/discord.md`, **The real implementations**): the test's `fetch` rejects with the `TimeoutError` that `AbortSignal.timeout` raises, and a 429's `retry_after` is a few milliseconds when it is retried, 2.5 s when it is not. The 10 s value itself goes untested.

## The contract suite

`discord-api-contract.ts` is written against the `DiscordApi` interface and runs three times: on the fake, and on the real implementation over the HTTP adapter and a fake, both in `pnpm test`; then on the real implementation against Gilles' test Discord server, with "Shor Panel Dev"'s token, by `pnpm test:contract`, whose files, `src/**/*.contract.test.ts`, `pnpm test`'s config leaves out (`vitest.config.mts:15`). `contract.yml`, which is to run it in CI (`CLAUDE.md`, **Delivery**), does not exist yet (#102). Its tests name each case; `docs/discord.md`, **The contract suite**, holds the measures.

- Until `contract.yml` exists, the last run is by hand: it loads `.env.local` through `process.loadEnvFile`, which leaves a variable the environment already sets alone, and fails before calling Discord when a variable is missing. It passes before a PR that touches `src/discord/` merges, and the PR says it ran by hand.
- It cleans up whatever the outcome and never touches the rule `pnpm dev` manages: it deletes the AutoMod rules it creates, all named `Contract …`, and the direct message it sends `CONTRACT_MEMBER_ID`, and lifts the timeouts it gives that member and the ban it gives `CONTRACT_ABSENT_USER_ID`, which must not be banned when it starts (#179, #181). It needs room on the test Discord server for one keyword rule, which it holds disabled and one at a time, so that `pnpm dev` keeps its own, 6 keyword rules at most, and at least one category, which its list of channels reads (#384). It tries again after a 429, up to three times (`patiently`).
- A timeout is given 28 days less a minute and refused at 28 days and a minute (decided by the agent on 2026-11-02, on #246, for Gilles to review; the why is in `docs/discord.md`, **The contract suite**).
- The search tests post six messages once, in the first text channel of the Discord server in which the application reads the history and posts, which they find themselves through `listChannels` and `listMessages`, since `contract.yml`'s environment holds no variable for a channel and adding one is a step for Gilles (decided by the agent on 2026-11-05, on #383, for Gilles to review), and delete them at the end. Discord's index lags, so each expectation of what a search finds is retried while it fails, and only a negative that follows a positive of the same fixture is asserted at once (`docs/discord.md`, **The contract suite**; ADR 0010).
- The kick, a member's ban and `DiscordOAuth` stay out of the suite: only the account can undo a kick or a ban, by joining again through an invite (#181), and a code exchange needs a member's consent in a browser. Vitest tests run the real implementation over the adapter and the fake, and a trial proves the rest (#180, #218; `docs/discord.md`, **The contract suite**).

## The application's permissions

- The panel's application never holds Administrator. Each feature adds the Discord permissions and privileged intents it needs, and no more, in the same change as the README's list of them, and the panel's role sits just above the roles it manages. Whoever holds the application's token holds all of them, so each one widens what a leak costs.
- A new permission, a new intent or a change to the role is a stop for Gilles, in the Developer Portal or on the Discord server: an agent tells him what to grant and why, and acts nowhere there (`deliver-epic/rules.md` of the agent-workflow plugin, **Stops**, **Security**: what the application may do on a third party, a permission or a scope, which the **Security** intro of `CLAUDE.md` names).
- The application is the Bot's too since ADR 0008, so the Bot's permissions join its role. Both applications hold the Server Members Intent, which `listMembers` needs (#318), and the Message Content intent, which the search needs (#382, ADR 0010); neither brings an event, since the panel opens no gateway connection (ADR 0003).
- A page that reads a channel needs View Channel and Read Message History for the application on that channel itself, and a grant on a category reaches it only while the channel is synced to the category (`CLAUDE.md`, **Channel visibility**).
- The role, the intents and what each feature needs, on Shor and on the test Discord server: `docs/discord.md`, **The application's permissions**, to read before a page reads a new channel or an action asks for a permission.

## Traps

- Discord's tokens don't say which application they belong to, and another application's token fails every AutoMod route of `pnpm test:contract`: `.claude/rules/blocked-words.md`, **Traps**.
- A worktree has no `.env.local`, which git ignores, so `pnpm test:contract` there fails before calling Discord (**The contract suite**). `node --env-file=<main checkout>/.env.local node_modules/vitest/vitest.mjs run --config vitest.contract.config.mts` runs it on the main checkout's values, with no copy of the file (`docs/discord.md`, **The contract suite**).
