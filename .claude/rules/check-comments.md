# The comment check

`pnpm check:comments` (`scripts/check-comments.mjs`) keeps the repository free of comments (`CLAUDE.md`, **No comments**). `test/check-comments.test.mjs` names each case a reader handles: a test is cited below by its title, and `shell files: …` stands for the tests whose title starts so. The runs behind the limits and the quotes of the docs the readers follow are in `docs/check-comments.md`: read it before changing how a file type is read.

## What it checks

- It checks every tracked or untracked, non-ignored file of the repository that holds the folder it runs from, so a subfolder or a worktree checks its own repository (`repositoryRoot`, `repositoryFiles`; "the script checks the repository that holds the folder it runs from, a subfolder included"). It reports `file:line:column snippet`, exits 1 on a comment, a file it cannot parse or a file of an unknown type, and exits 2 outside any repository, with one line that names the folder ("the script, run in a folder that is in no repository, fails with one line that names the folder").
- `familyOf` picks the reader from the extension, or from the name for the files with `#` comments. Script files go through `@babel/parser`, which leaves alone the tool directives of `DIRECTIVES` (`CLAUDE.md`, **Directives**).
- `.sh`, `.toml` and `.env*` files have a reader of their own, since a string, a here-document or a quoted value can run over many lines and hold a `#` that is no comment (#33). YAML goes through its parser first, which masks a quoted scalar that runs over many lines; the other files with `#` comments are read line by line, where a quote ends with its line (`hashComments`).
- A file of a type `familyOf` does not read is reported as « unknown file type » until the script reads it or `COMMENTLESS_EXTENSIONS` or `COMMENTLESS_FILES` lists it as commentless. It does not tell text from binary, so a new type of either, an image or a font, fails the check until it is listed (decided by the agent on 2026-10-30, on #22, for Gilles to review).
- A file the reader cannot follow to its end is reported as « cannot be parsed », never skipped, so that the rest of a file is never hidden: a Markdown code fence or YAML header, a Python `'''` or `"""`, a SQL `'` or `"` string, a PowerShell `<#`, `'`, `"` or here-string, a shell or TOML quote, a shell here-document, `$(` or backtick substitution that never closes ("a quote that is never closed hides no comment: the file is reported as unparsable" and the tests titled "… that never closes is reported as unparsable").
- The footer counts the comments, the files it cannot parse and the files of an unknown type, each on a line of its own, none for a count of 0, and gives the advice to move the why elsewhere only when it found a comment. The PR hook's refusal asks to remove each comment, to fix each file that cannot be parsed, and to teach the check each unknown file type or list it as a type without comments, since it quotes all three kinds of line (decided by the agent on 2026-10-30, on #299, for Gilles to review; "the script's footer counts comments, files that cannot be parsed and unknown types each on its own line" and "the PR hook's refusal does not call a file it cannot read a comment, and says what to do with each kind of line").
- Where only the language's own parser could tell a comment from text, the check reports the doubtful `#` and accepts the false positive, so that it shows where a missed comment would hide (decided by the agent on 2026-11-12, on #446, for Gilles to review).

## Markdown

- A fenced code block (three backticks or `~~~`) and an inline code span are code, not comments, so a passage may quote `<!-- -->` in either. An indented code block is not recognised, so a comment in one is reported, and a line that opens an HTML comment ends an inline code span, as a blank line does (decided by the agent on 2026-10-30, on #22, for Gilles to review).
- A link definition whose destination is `#` or `<>` and that carries a title, such as `[//]: # (why)` or `[comment]: # "why"`, is a comment, since it shows nothing in a rendering and its title is all it holds (inferred); an ordinary definition is not. It is reported when it fills a line, after a quote or list marker too, and right after a line of a paragraph, where CommonMark would render it as text (inferred; the tests titled "markdown files: a link definition …"). So `[top]: # "Top"` is a false positive.
- A definition cut over several lines, with its destination or its title on the next line, its title across lines, or a `\]` in its label, goes unreported (decided by the agent on 2026-10-30, on #297, for Gilles to review).
- The YAML header is the lines between a `---` on the very first line and the next `---` line, provided that at least one of them is a `key:` line (`yamlHeaderOf`; "markdown files: a # comment of the YAML header is found"). A header is read as a `.yml` file is, so a `#` there is a comment. A header that is not valid YAML is read line by line with its quotes ignored, rather than reported as unparsable: a `#` after a space counts as a comment there even inside quotes, a false positive ("markdown files: a YAML header that is not valid YAML is read line by line, quotes ignored").
- A file that opens with a `---` rule, holds a line such as `Note: text` and has a second `---` further down is read as a header, and the same file without a second one is reported as unparsable, the price of telling a header from a rule by its `key:` line (inferred from the code) (decided by the agent on 2026-10-30, on #298, for Gilles to review).

## SQL

- `--` and `/* */` are comments. A `$$…$$` or `$tag$…$tag$` body is read as SQL up to its closing delimiter, the first one after the opening one, with the tag case sensitive, as PostgreSQL ends the string there (`docs/check-comments.md`, **SQL**), so its comments are reported and a nested body with another tag is read to its own delimiter (the tests titled "sql files: …").
- A `'` or `"` left open in a body, and a delimiter never closed, make the file unreadable: write a text with a lone apostrophe as a `'don''t'` string, not `$$don't$$` (#309). A `$` opens no delimiter right after an identifier character, nor as a parameter, `$1`, nor without a closing `$` ("sql files: a $ that opens no delimiter opens none").
- The check judges that from the one character before the `$`, where PostgreSQL's lexer follows whole identifiers (decided by the agent on 2026-10-30, on #309, for Gilles to review).

## Shell

- `$((…))` and `((…))` are skipped as arithmetic, so that their `<<` is a shift and not a here-document (decided by the agent on 2026-10-30, on #33, for Gilles to review).
- The reader follows `$(…)` and backtick substitutions, even inside double quotes, where a `#` after a blank is a comment ("shell files: a command substitution inside double quotes is shell, with its own quotes and comments"). It follows a `${…}` as one unit, so that a `)` or a `#` inside it neither ends the substitution around it nor counts as a comment ("shell files: a ) inside ${…} does not end the command substitution around it" and "shell files: a # inside ${…} is no comment"); `$$` as one token, so that the `{` after it opens no parameter and a `#` after a blank is a comment ("shell files: $$ is one token, so the { after it opens no parameter"); and the patterns of a `case` inside a `$(…)`, so that the `)` of a pattern does not end it ("shell files: the ) that ends a case pattern does not end the command substitution around it"). A `'` in a `${…}` opens a quote even inside double quotes, so that a `${` or a quote that never closes makes the file unreadable ("shell files: a ${ that is never closed is reported as unparsable").
- Check a new construct against bash itself, `bash -n` then `bash -c`, before the reader follows it; the runs behind the current ones are in `docs/check-comments.md`, **Shell** (decided by the agent on 2026-11-12, on #446, for Gilles to review).
- A `case` is followed where a command starts: at the start of a file or substitution, after a newline, `;`, `&`, `|`, `(` or `)`, after a `{` or a `!` followed by a blank, and after `time`, `then`, `do`, `else`, `elif`, `if`, `while`, `until` and the `in` that opens a `case` (`SHELL_KEYWORD`, `followShellKeyword`; "shell files: a case is found after every word that starts a command") (the words that start a command decided by the agent on 2026-10-30, on #302, for Gilles to review).

## TOML and `.env*`

- In TOML, any `#` outside a string is a comment, so `a = 1#c` is reported (decided by the agent on 2026-10-30, on #33, for Gilles to review). A `"""` or `'''` string runs over many lines, and a `"` or `'` one must close on its line, or the file is unreadable. `#!` is a comment there and in `.env*`.
- In a `.env*` file, a quote (`"`, `'` or a backtick) opens a value only right after `KEY=`, `export KEY=` or `KEY: `, and closes where the `LINE` expression of dotenv 17.4.2 closes it (`dotenvValueEnd`), so a quoted value may run over many lines and a quote anywhere else is a plain character: the `#` of `KEY=a "b # c"` is reported (decided by the agent on 2026-10-30, on #33, for Gilles to review). A `#` starts a comment at the start of a line, after whitespace or right after a closing quote: `KEY=a #b` and `KEY="a"#b` hold one, `KEY=a#b` none.
- A quote that never closes in a `.sh` or `.toml` file makes the file unreadable rather than hiding the rest of it, as for YAML, while in a `.env*` file it is a plain character, as dotenv takes it, and the lines after it are still read (decided by the agent on 2026-10-30, on #33, for Gilles to review; "a quote that is never closed hides no comment: the file is reported as unparsable").

## PowerShell

- Any `#` outside a string is a comment, but for one escaped with a backtick, and `<# #>` too: telling a bare word from an expression takes PowerShell's own parser, so `echo a#b` is reported, and so is `$s = "a $("b # c") d"`, where a subexpression holds quotes, both false positives (decided by the agent on 2026-10-30, on #22, for Gilles to review).

## Known limits

- The `)` of the first pattern of a `case` that the reader does not take for one ends a `$(…)` inside double quotes early, and the comments after it, up to the closing quote, are missed, where the same without quotes reports them. Three forms do it, all valid in bash: a `case` after a word the reader does not know to leave a command starting, such as the `-p` of `time -p`; a pattern spelled `case` with a blank after it; and a pattern spelled `esac` in parentheses, `(esac)`. They stay unfixed, since telling a pattern from a command takes a state that follows each `;;`, for forms nothing in the repository meets (decided by the agent on 2026-10-30, on #302, for Gilles to review).
- Neither `$[…]` nor `.envrc` is read as shell (decided by the agent on 2026-10-30, on #33, for Gilles to review). A `.sh` file that holds the old arithmetic `$[…]` with a `<<` is reported unreadable, since the reader takes the `<<` for a here-document that never closes, which shows. A `.envrc` stays on the `.env*` reader, though direnv loads it into a bash sub-shell: the `#` of a here-document in it is reported, and a comment inside a `KEY="$(…)"` that spans lines is missed.
- Inside double quotes the reader takes `$$` for one token with no claim of exactness.

## The PR hook

`.claude/hooks/check-comments-before-pr.mjs`, which `.claude/settings.json` registers as a `PreToolUse` hook on `Bash` and `PowerShell` calls, runs the check before a PR is created and denies the call with the report when the check exits 1, or with its reason when it cannot run; a call it cannot read is denied too (the tests titled "the PR hook …").

- It recognises `gh pr create` and its alias `gh pr new` with the repository chosen by `-R` or `--repo`, before `pr` or between `pr` and the verb, in the five spellings tried on `gh pr view` (`CREATE_PR`; `docs/check-comments.md`, **The PR hook**). Any other verb passes.
- It recognises them too when a backslash, or a backtick for PowerShell, at the end of a line splits the command, since it joins those lines before it looks (inferred for the backtick; "the PR hook refuses a PR whose command a line continuation splits, in bash or in PowerShell"; decided by the agent on 2026-10-30, on #293, for Gilles to review).
- It checks the repository of its input's `cwd`, which follows Claude into a worktree, and not the project root where `$CLAUDE_PROJECT_DIR` stays, so that a PR from a worktree gets that worktree checked (inferred; `docs/check-comments.md`, **The PR hook**).
- From a folder in no repository it refuses the PR, since it has nothing to check, rather than check the repository of its own copy (decided by the agent on 2026-10-30, on #19, for Gilles to review; "the PR hook refuses a PR from a folder that is in no repository, since it has nothing to check").
