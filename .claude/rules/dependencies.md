# Gotchas of the dependencies

- `@babel/parser`, which the comment check uses, stays on 7.x: 8.x requires Node `^22.18.0 || >=24.11.0` (`npm view @babel/parser@8 engines`, 8.0.8, 2026-10-29), which leaves out 24.0.0 to 24.10.x, within the `^24.0.0` that `engines` promises in `package.json`. CI would not catch the gap: it runs the latest 24.x (`.claude/rules/ci.md`, **CI**), 24.22.1 on 2026-10-29 (run 40898070133), which 8.x accepts. The hold goes once 8.x accepts the whole of 24, or `engines.node` starts at 24.11.0.
- `engines.node` names the one major the panel runs on, `^24.0.0` (**Node**), and each range the toolchain declares must hold it whole: Vitest 5 wants `^22.12.0 || ^24.0.0 || >=26.0.0`, ESLint 10 `^20.19.0 || ^22.13.0 || >=24` (`npm view <package> engines`, 2026-10-29). Read a new dependency's `engines` before adding it: jsdom 30, for one, wants `^22.22.2 || ^24.15.0 || >=26.0.0`, which leaves out 24.0.0 to 24.14.x (30.1.3, 2026-10-29).
- `typescript@7` on npm is the native compiler: its package exports no stable JavaScript API (only `./unstable/*`), so tooling that parses code cannot rely on it. That is why the comment check parses with Babel, and why TypeScript stays on `6.0.3`, under 6.1: typescript-eslint, which `eslint-config-next/typescript` uses, accepts `typescript >=4.8.4 <6.1.0` (8.72.0, `npm view typescript-eslint peerDependencies`, 2026-10-23). Next.js alone would accept 7, through its `tsc` CLI (https://nextjs.org/docs/app/api-reference/config/typescript, updated 2026-08-25).
- ESLint is on 10, since 9.x reached end-of-life on 2026-08-06 (https://eslint.org/version-support, read 2026-10-23). `eslint-config-next` supports 10 since 16.4.0 (https://nextjs.org/docs/app/api-reference/config/eslint, updated 2026-10-15), but three plugins it bundles, `eslint-plugin-import`, `eslint-plugin-jsx-a11y` and `eslint-plugin-react`, still cap their `eslint` peer at `^9`: hence the `peerDependencyRules` of `pnpm-workspace.yaml`. Drop each rule once its plugin lists 10.
- pnpm 12's `minimumReleaseAge` defaults to 1,440 minutes, and stays non-strict until the setting is written down (https://github.com/pnpm/pnpm/blob/v12.9.1/pnpm/crates/config/src/registry_options.rs#L200-L212): non-strict, when no version old enough fits, pnpm takes the young version and writes it into `minimumReleaseAgeExclude` in `pnpm-workspace.yaml` without asking (`minimum_release_age.rs:146-191`, same tag, under `pnpm/crates/package-manager/src/`), as `pnpm add` reported doing for Next.js 16.4.3 on 2026-10-23, on npm since 13:40 UTC that day (`npm view next time`). `pnpm-workspace.yaml` writes it down since #92, so pnpm is strict here (**Release age**). Without a terminal, as under Claude's Bash tool (`[ -t 0 ]`, 2026-11-02), `pnpm add` of a version under 7 days old fails with `ERR_PNPM_NO_MATURE_MATCHING_VERSION` and leaves `package.json`, `pnpm-lock.yaml` and `pnpm-workspace.yaml` as they were: so did `lucide-react@1.64.0`, 4 days old, which the default had let in, and `cn@0.5.2`, under a day old, in a throwaway copy of the repository's package files (2026-11-02, #92). At a terminal, pnpm asks before it takes such a version, and writes the exclusion only if told yes (`minimum_release_age.rs:146-191`, not tried at a terminal). A lockfile entry under 7 days old fails `pnpm install --frozen-lockfile` too, with `ERR_PNPM_MINIMUM_RELEASE_AGE_VIOLATION`, though the lockfile is up to date: the same copy did once it held `lucide-react@1.64.0`, added under the default (2026-11-02, #92). That error's help ends on « relax the policy that flagged them » (the same run), which **Release age** allows only through an exclusion for a security fix. pnpm records each lockfile it verified, by its hash and the policy, in `lockfile-verified.jsonl` of its cache, and answered « verified 16s ago » for a lockfile it had just checked (2026-11-02), so a local install proves a lockfile afresh only under an empty `--config.cache-dir` (inferred): the repository's 712 entries passed so (« ✓ Lockfile passes supply-chain policies (712 entries in 16.8s) », 2026-11-02, #92).
- `pnpm-workspace.yaml`'s `auditConfig.ignoreGhsas`, which `pnpm audit --ignore` wrote, holds GHSA-mrhx-c7xc-m3w5, against zod `<4.6.6`, for the zod 4.1.11 that every `@vercel/cli-config` pins, 0.1.0 to 0.3.3 (`npm view @vercel/cli-config@<version> dependencies.zod`, 2026-10-25), through `@vercel/functions` > `@vercel/oidc`. The panel cannot reach it: it imports only `waitUntil`, from `@vercel/functions`' `index.js`, which requires none of the `oidc/` files that alone load `@vercel/oidc`, and `.next/server` names neither package after `pnpm build` (2026-10-25). The entry goes once `@vercel/cli-config` takes zod `>=4.6.6`, and must go if the panel ever imports `@vercel/functions/oidc`.
- Vercel installs with pnpm 12 only through Corepack (`docs/delivery.md`, **Environments**), and Corepack "is distributed with Node.js from version 14.19.0 up to (but not including) 25.0.0" (https://github.com/nodejs/corepack, README, read 2026-10-27), so on Node 26 Vercel's `ENABLE_EXPERIMENTAL_COREPACK` may find none (inferred). Since #96, `engines.node` keeps Vercel on 24 (**Node**), so the move to 26 is a pull request, whose Vercel build log **Checks** reads. The line goes once Vercel picks pnpm 12 from the lockfile itself (https://vercel.com/docs/package-managers, updated 2026-08-11), or once Node 26 is shown to install with it.
