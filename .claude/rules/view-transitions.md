# Gotchas of React's view transitions

- The React DOM that Next.js 16.4.2 runs the App Router on, `19.3.0-canary-278794d7-20261002` (the `version` of `node_modules/next/dist/compiled/react-dom/cjs/react-dom-client.production.js`), hides the group of a `<ViewTransition>` that a transition leaves unchanged with an animation of no duration and `fill: "forwards"` on `::view-transition-group(<its name>)` (the same file, `:11023-11030`). With a `<ViewTransition>` around the header's name and its skeleton, in `src/app/(staff)/layout.tsx`, which stays mounted, each navigation hid that group, and each such animation stayed in `document.getAnimations()`, finished, once its transition had ended: 1, 2, then 3 after three navigations, while the current section's underline, which every navigation moves, left none. So the wait of `checkAccessibility` never ended, and the crossfade test under reduced motion caught the hidden pair's crossfade (throwaway Playwright test that logged `document.startViewTransition`, the `animate` calls on a `pseudoElement` and `document.getAnimations()`, 2026-10-27, #139). A new `<ViewTransition>` in the layout needs the same check. The blocked words', in the page, left none: after an add that moved no other word, React hid the groups of the three words that kept their place the same way, and `document.getAnimations()` was empty once the transition had ended (throwaway Playwright test, 2026-10-28, #166).
- A `<Suspense>` that reveals after a client navigation, as a record's does when Discord answers late, has React DOM `19.3.0-canary-278794d7-20261002` hide the page's own `<ViewTransition>` the same way, through an animation on a `::view-transition-group` that this view transition does not hold, so it outlives it, finished, in `document.getAnimations()`, and keeps the page's group at `opacity: 0` when a later navigation makes it exit (throwaway Playwright probe, each call to Discord delayed by 50 ms, on #211's branch and on `main`, 2026-10-28). On CI's runner, a record opened from the search met it once #177 added the history's calls to Discord: `checkAccessibility`, which then waited for an empty `document.getAnimations()`, timed out (run 40777294822), and now waits for no animation still running. The page that exits then vanishes rather than fading out (inferred): #212.
- React DOM `19.3.0-canary-278794d7-20261002` marks a `<ViewTransition>` as updated whenever a prop of an element inside it changes, not only when it moves: `setProp` flags every prop it sets (`node_modules/next/dist/compiled/react-dom/cjs/react-dom-client.development.js:21630`, `:22090`), and the commit then marks the nearest `<ViewTransition>` (`:16275-16278`). One whose `update` names a class then gets the browser's default crossfade of its old and new snapshots, under reduced motion too, where `globals.css` stops only the groups. With each blocked word's `update` set to `slide`, an add crossfaded each word it moved, under reduced motion too (a run of `e2e/blocked-words.test.ts` against `update="slide"`, 2026-10-28); and a removal, which enables every « Retirer » again, names every word, the one that keeps its place included, whose group then runs from and to the same place (throwaway Playwright test, 2026-10-28), so `slide` would crossfade it too (inferred, #166). So `slide-into-place` shows the new snapshot at once (**Motion**).
- React animates the `enter` or `exit` of a `<ViewTransition>` only when no DOM element sits between it and the top of what a commit inserts or deletes: the commit looks for one through a flag of the inserted or deleted fiber's `subtreeFlags` (`node_modules/next/dist/compiled/react-dom/cjs/react-dom-client.development.js:14378`, `:14597`), which every host element clears from its own (`:13141-13142`). On 2026-10-28, with each blocked word in a `<ViewTransition>` inside a `<ul>` that rendered only with words, the first word added and the last removed started no view transition, while a word added to or removed from a list that already held another started one (throwaway Playwright test that counted the calls to `document.startViewTransition` and logged the fibers React's commit walked, #138). So the list keeps its `<ul>` while it is empty, hidden by `empty:hidden`.
- An update that comes while a view transition runs, such as the toast a write's leaf adds from its effect once the result commits (**Forms**), has React DOM `19.3.0-canary-278794d7-20261002` take the `view-transition-name`s off the elements it named while their animations still run: on 2026-10-29, a throwaway Playwright probe that logged each frame of a word's add read no name on its `<li>` in any frame, though its `::view-transition-new` ran, and `e2e/blocked-words.test.ts`, which read the names off the `<li>`s as it had on `main`, mapped every animation of a write to no word (inferred: React restores the names once work spawned during the transition waits, `spawnedWorkCallback`, `node_modules/next/dist/compiled/react-dom/cjs/react-dom-client.production.js:15873`). So that test records each name as React writes it, through a `MutationObserver` that an init script installs on every page it opens.
- After a full page load, a test that watches the next view transition first waits for the content, then for `document.activeViewTransition` to be `null`: React's streaming runtime reveals what a `<Suspense>` streams through a view transition of its own, which runs `content-enter` since #139, and which the crossfade test with motion caught in place of the navigation's in 1 run of 3 (`--repeat-each 3`, 2026-10-27).
